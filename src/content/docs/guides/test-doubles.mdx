A **test double** replaces a dependency in a test so you can control its behavior. With Suites, retrieve the mock, set the value its method should return, and assert the result.

## Configure a Mock and Verify a Call

Using the classes from [Quickstart](/docs/get-started/quickstart/#step-1-creating-the-application-code), add this test. It runs with either Jest or the Vitest globals configuration from [Installation](/docs/get-started/installation/).

```typescript title="src/test-doubles.spec.ts"
import 'reflect-metadata';
import { TestBed, type Mocked } from '@suites/unit';
import { UserService } from './user.service';
import { UserRepository } from './user.repository';

it('returns a name using the repository', async () => {
  const { unit, unitRef } = await TestBed.solitary(UserService).compile();
  const repository: Mocked<UserRepository> = unitRef.get(UserRepository);

  repository.getUserById.mockResolvedValue({
    id: 1, name: 'Ada', email: 'ada@example.com',
  });

  expect(await unit.getUserName(1)).toBe('Ada');
  expect(repository.getUserById).toHaveBeenCalledWith(1);
});
```

Run `pnpm exec jest` or `pnpm exec vitest run`. This test should pass without executing the real repository method.

`repository` is the **mock**, a replacement for the dependency. Its `getUserById` method is a **stub**: `.mockResolvedValue()` supplies the response, and the runner records calls so you can verify how the service used it.

## Choose a Test Double

The terminology comes from [xUnit Test Patterns](http://xunitpatterns.com/Test%20Double.html) and [Martin Fowler's discussion of mocks and stubs](https://martinfowler.com/articles/mocksArentStubs.html). Libraries use these terms differently; Suites calls a replacement object a mock and its replacement methods stubs.

| Test double | Purpose | Example |
| --- | --- | --- |
| **Stub** | Supplies a controlled response | Return a user without querying a database |
| **Mock** | Supports checking expected interactions | Verify the repository received the requested ID |
| **Spy** | Records calls to an existing method; behavior can also be replaced | Observe a real collaborator with `jest.spyOn()` or `vi.spyOn()` |
| **Fake** | Provides a simplified working implementation | Store records in an in-memory repository |

Suites' doubles adapters create mocks and stub methods. Write a fake implementation yourself when the test needs stateful behavior, and use the runner's spy API when you need to observe an existing method.

## Verify Results and Interactions

The first example checks both:

- **Result verification:** The service returns `'Ada'`.
- **Interaction verification:** The repository receives ID `1`.

Choose assertions that describe the behavior you care about. An interaction assertion is useful when the interaction itself matters, such as sending an email or saving a record. You do not need to assert every internal call.

## Test an Error Response

Create a fresh TestBed for another scenario, then configure a rejected promise:

```typescript title="src/user.service.error.spec.ts"
import 'reflect-metadata';
import { TestBed } from '@suites/unit';
import { UserService } from './user.service';
import { UserRepository } from './user.repository';

it('propagates a repository error', async () => {
  const { unit, unitRef } = await TestBed.solitary(UserService).compile();
  unitRef.get(UserRepository).getUserById.mockRejectedValue(
    new Error('User not found'),
  );

  await expect(unit.getUserName(1)).rejects.toThrow('User not found');
});
```

This test passes when the service propagates the rejection. Fresh mocks keep return values and call histories from leaking between scenarios.

## Know Which Dependencies Suites Can Replace

TestBed resolves dependencies through the DI adapter: constructor parameters and supported injected properties. It does not intercept functions imported directly by the tested class, such as `import { sendEmail } from './email-utils'`.

For external I/O, inject a collaborator that the test can replace. Direct imports that remain in the code execute normally; TestBed does not prevent network or database calls inside them.

For code without a DI framework, import `mock()` from `@suites/doubles.jest` or `@suites/doubles.vitest`, then pass the mock into the function or constructor. See [Standalone Mocks](/docs/api-reference/mock/) for examples.

## Choose Configurable Mocks or Supplied Values

| Need | Approach |
| --- | --- |
| Change a response or inspect calls during a test | Retrieve the mock with `unitRef.get()` |
| Configure stub behavior before constructing the unit | `.mock(Dependency).impl(stub => ({ ... }))` |
| Inject a configuration value or a supplied implementation | `.mock(Dependency).final(value)` |
| Run selected real collaborators | `TestBed.sociable(...).expose(Dependency)` |

Values supplied with `.final()` and real classes selected with `.expose()` are not retrievable through `unitRef`. See [Mock Configuration](/docs/api-reference/mock-configuration/) for details.

## Summary

- Configure a stub's response to control the dependency's behavior.
- Assert returned results and the interactions that matter to the test.
- Keep external I/O behind dependencies you can replace.
- Use fresh mocks when scenarios need independent call histories and responses.
