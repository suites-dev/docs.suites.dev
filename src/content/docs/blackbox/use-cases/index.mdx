Blackbox is useful when a visible result can stay green while important behavior inside a running system changes.

## Choose the Risk

| Use case                           | Behavior to protect                                         | Read next                                                                             |
| ---------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Refactor a working system          | Selected boundary effects that must remain stable           | [Cover Behavior Before a Refactor](/docs/blackbox/use-cases/covering-before-refactor) |
| Modernize a legacy system          | Reviewed behavior while components move in stages           | [Modernize a Legacy System](/docs/blackbox/use-cases/legacy-modernization)            |
| Prevent an incident from returning | Effects that must occur and effects that must stay absent   | [Prevent an Incident Regression](/docs/blackbox/use-cases/incident-regression)        |
| Verify a distributed workflow      | Database, HTTP, cache, and queue behavior behind one result | [Verify a Microservice Workflow](/docs/blackbox/use-cases/microservices-regression)   |

## Use the Same Small Loop

1. Select one consequential executable flow.
2. Review the behavior the flow should protect.
3. Run the flow in an isolated capture cell.
4. Seal and analyze the runtime evidence.
5. Repair implementation against deterministic findings.
6. Let a person accept the result or return it to the agent.

EARS and Gherkin are optional governance layers. Use them when reviewed intent and traceability matter. Runtime effects remain independent from that choice.

Start with the [Blackbox Quickstart](/docs/blackbox/quickstart/) and choose the SUT source strategy that matches your project.
