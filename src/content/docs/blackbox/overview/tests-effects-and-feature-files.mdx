The Blackbox lifecycle is a **behavioral harness loop** around a software change. The goal is not to generate more artifacts. The goal is to make accepted behavior explicit, executable, observable, and reviewable.

<VerificationLoopDiagram />

## The Loop, Step by Step

1. **Express intent.** A person, ticket, Kiro document, OpenSpec artifact, Spec Kit spec, or design note describes the behavior.
2. **Propose requirements.** `$blackbox-requirements` converts selected obligations into EARS as an inferential proposal.
3. **Validate requirements.** `blackbox requirements validate` checks structure, IDs, and profile rules.
4. **Approve requirements.** A human reviews and approves the EARS meaning.
5. **Propose Gherkin.** `$blackbox-gherkin` translates approved requirements into a `.feature` file with `@flow` and `@requirement` tags.
6. **Validate features.** `blackbox features check` checks syntax, tags, and source relationships.
7. **Accept scenarios.** A human reviews and accepts the scenario language.
8. **Propose a suite patch.** `$blackbox-playwright` writes a native Playwright patch that declares the same flow ID.
9. **Approve the suite patch.** A human reviews the exact test change before it enters the suite.
10. **Run the suite.** `blackbox verify --flow <id> --json` runs the selected Playwright flow and captures runtime evidence.
11. **Propose effect assertions.** `$blackbox-effects` reads evidence and proposes required and forbidden effects.
12. **Accept the effect contract.** A human reviews and accepts the effect contract.
13. **Compute verdicts.** The CLI reports separate Playwright, feature, requirement, effect, and observable decision verdicts.
14. **Repair and rerun.** A coding agent repairs implementation findings against the accepted harness and reruns the loop.

The agent stops when success would require changing accepted behavior. A failing implementation can be repaired automatically. A changed requirement, feature, suite, or effect contract needs human review.

## Harness Responsibilities

| Responsibility           | Owner        | What can change                                                       |
| ------------------------ | ------------ | --------------------------------------------------------------------- |
| Inferential translation  | Skills       | Proposed EARS, Gherkin, suite patches, and effect contracts           |
| Deterministic validation | CLI          | Findings, reports, evidence, and verdicts                             |
| Meaning and behavior     | Humans       | Accepted requirements, scenarios, suite patches, and effect contracts |
| Implementation repair    | Coding agent | Product code and supporting implementation tests                      |

This separation is the core of the loop. The same agent should not silently rewrite the harness it is trying to satisfy.

## The Loop Has Multiple Entry Points

It is not a mandatory waterfall.

| Starting situation          | Where the loop begins                                                           |
| --------------------------- | ------------------------------------------------------------------------------- |
| Existing Playwright tests   | Discover a flow, capture evidence, review an effect contract, and add verdicts. |
| New spec-driven feature     | Start from requirements, Gherkin, and a proposed native Playwright flow.        |
| Refactor or rewrite         | Establish accepted evidence before changing internals.                          |
| Incident regression         | Capture the repaired path and add forbids for unsafe effects.                   |
| External specification tool | Import selected intent from Kiro, OpenSpec, Spec Kit, tickets, or design docs.  |

Every path eventually needs an executable run before Blackbox can make a runtime claim.

## Verdicts Answer Different Questions

Blackbox should not collapse the whole harness into one unexplained Boolean.

| Verdict surface              | Example result                                        | Meaning                                                             |
| ---------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------- |
| Playwright                   | passed or failed                                      | Did the explicit test assertions hold?                              |
| Feature check                | in sync or a drift finding                            | Does reviewed Gherkin still match the expected flow structure?      |
| Effect contract              | satisfied, failed, or uncovered                       | Did required and forbidden boundary behavior match?                 |
| Requirement coverage         | `proven`, `violated`, `unproven`, or `unbound`        | What does runtime evidence establish about approved intent?         |
| Observable decision evidence | `propagating`, `masking-candidate`, or `coverage-gap` | Did different decision arms leave distinguishable observed effects? |

A Playwright pass alongside an effect failure is not contradictory. It says the public assertion held while reviewed boundary behavior did not.

## Repair Automatically, Review Deliberately

Automation can repeat a bounded implementation loop:

```text
run flow -> read deterministic findings -> repair implementation -> rerun
```

It must stop when success would require changing:

- requirement meaning;
- a Gherkin scenario;
- the approved Playwright flow scope;
- a required or forbidden effect;
- the accepted effect contract;
- the final interpretation of evidence.

Those changes alter what the system is allowed to do. They are product or architecture decisions, not mechanical repairs.

<Aside type="warning" title="Do Not Let Automation Move the Goalposts">
  Keep accepted behavior changes visible in review. If an agent can rewrite
  requirements, scenarios, suites, and effect contracts until they agree, the
  harness no longer proves behavior independently.
</Aside>

## The Loop Creates Repository Memory

Reviewed requirements, feature files, stable flow tags, effect contracts, and selected reports survive individual development sessions. A future developer or agent can inspect what a flow means without reconstructing the system from a large diff.

Raw spans and generated reports usually remain run artifacts. Accepted behavioral artifacts belong in the repository.

## Run the Loop Again

The first successful implementation is not the end. The same flow and contract can verify:

- a later refactor;
- a service extraction;
- a dependency upgrade;
- a framework migration;
- an incident repair;
- an agent-authored optimization.

This repetition is the point: implementation can change while accepted behavior remains explicit and testable.
