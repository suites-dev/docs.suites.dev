The Blackbox lifecycle is a verification loop around a software change. Its goal is not to maximize the number of tests. Its goal is to produce enough reviewed evidence to trust that selected behavior did not break.

<VerificationLoopDiagram />

## The Loop, Step by Step

1. **Express intent.** A person or planning process defines the behavior and constraints. EARS can make normative requirements explicit, but it is optional.
2. **Choose a flow.** A stable flow ID names the behavior that will carry evidence, such as `subscribe-unknown-user`.
3. **Write or select a Playwright test.** The test drives the real system boundary and keeps its ordinary assertions.
4. **Implement the change.** A developer or coding agent changes the system.
5. **Run in a controlled environment.** The testbed starts the topology and injects test-time instrumentation into compatible Node SUT containers.
6. **Capture runtime effects.** Blackbox associates Postgres, Redis, HTTP, SQS, S3, and RabbitMQ observations with the active flow.
7. **Check reviewed behavior.** Inline matchers or the effect catalog evaluate required and forbidden effects.
8. **Produce verdicts.** Reports and stable JSON tell CI, agents, and reviewers what was satisfied, missing, violated, unproven, or unbound.
9. **Repair or ratify.** Implementation failures return to the author. New or ambiguous behavior returns to a human before the contract changes.

The loop can repeat under the hood in a local agent workflow or run visibly in CI. The trust boundary remains the same: implementation changes may be automated; changes to accepted behavior must be reviewable.

## Four Surfaces, Four Jobs

| Surface                      | Job                                                            | Required?          |
| ---------------------------- | -------------------------------------------------------------- | ------------------ |
| Playwright flow              | Execute selected behavior                                      | Yes                |
| Runtime effects and catalog  | Prove required and forbidden boundary behavior                 | Core Blackbox path |
| EARS requirement and binding | Connect normative intent to one or more flow IDs               | Optional           |
| Gherkin feature file         | Give executable behavior a readable projection and drift check | Optional           |

EARS and Gherkin are not competing sources of truth. An EARS statement can say what the system is required to do. A generated feature can show how a Playwright scenario exercises behavior. Runtime evidence decides what the system actually did in that run.

## Human Ratification Is the Stop Rule

Automation can safely repeat work when the accepted contract is unchanged:

```text
run flow -> read JSON verdict -> repair implementation -> rerun
```

Automation should stop when a failure suggests changing the contract:

- a previously unseen effect may be intentional or accidental;
- a required effect may no longer belong in the design;
- a forbidden effect may now be allowed under a new requirement;
- a requirement may need a new flow binding;
- generated Gherkin may expose ambiguous behavior language.

Those are product and architecture decisions, not mechanical repairs.

<Aside type="warning" title="Do Not Approve the Baseline Automatically">
  The first recording describes the current implementation, including its
  defects. Use it to discover candidate effects, then review the catalog before
  treating it as a gate.
</Aside>

## The Code-First Gherkin Loop

Classic BDD often starts with a feature file and asks teams to keep prose, step definitions, and tests synchronized. Blackbox supports a different default for existing system tests: emit Gherkin from executable test structure, review the result, and detect drift later.

<CodeFirstBddDiagram kind="staleness" />

This keeps feature files useful without making them mandatory. The supported path is test-to-feature generation and drift checking. Feature-to-test scaffolding exists under the experimental CLI surface and should not be presented as a stable workflow.

## The Agentic Development Extension

An agent can use the same loop in two directions:

- **Existing behavior:** read local requirements, bindings, feature files, catalogs, and reports before changing code; then repair against deterministic runtime verdicts.
- **New behavior:** draft a Playwright flow before implementation, optionally emit Gherkin for human review, implement the change, and run until the reviewed effects and requirement verdicts pass.

The artifacts stored in the repository are valuable because they survive agent sessions. A future developer or agent can understand named flows and reviewed behavior without reconstructing the entire system from test code and traces.
