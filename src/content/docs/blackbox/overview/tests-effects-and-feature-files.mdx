Blackbox connects three artifacts that are often reviewed separately: the test, the physical effects, and the behavior contract. The point is to make each artifact check the others.

In the `subscribe-flow` showcase, the test drives the workflow, the effects prove the **physical reality** of what the services did, and the feature file gives the architectural intent a readable Gherkin surface. That is the **combined loop**.

<CodeFirstBddDiagram kind="triangle" />

## The Three Artifacts (Test, Reality, Intent)

A test is the execution surface. It drives `subscribe-flow` or `subscribe-unknown-user` against the system and decides whether the ordinary assertions pass.

Effects are the **physical trace**. They come from spans emitted during the run, then Blackbox matches them against required and forbidden behavior. In the positive path, the run proves the physical reality appeared as expected. In the unknown-user path, it proves forbidden downstream behavior stayed absent.

A feature file is the reading surface. It turns the tested behavior into a scenario people can inspect in review, planning, or incident follow-up. Gherkin is compact and familiar, but the file is not the source of truth. The running test and captured effects are.

This separation matters. A green test can hide a missing effect. A hand-maintained feature file can drift. A physical trace can be precise but hard to scan.

## The Living-Documentation Hook (Intent inverted)

Classic BDD promised **living documentation**: write behavior in Gherkin, execute it, and keep the spec aligned with the system. In practice, that promise often broke when test code and feature files became separate maintenance jobs.

Blackbox inverts the direction. Instead of starting from Gherkin, the team starts from a test that already runs the system. Blackbox reads that executable behavior, matches the physical reality of the effects, and emits a feature file from evidence.

That inversion changes the maintenance contract. A human still has to translate product intent into a real scenario. For spec-driven development, the useful pattern is: translate selected intent into an executable flow once, then let runtime evidence and readable documentation regenerate from the run.

Documentation that regenerates from evidence has a different failure mode than a hand-maintained `.feature` file. If the test source changes, the emitted feature file changes. If the physical reality changes, the effects change. If the readable scenario no longer matches the source test, **Gherkin drift** becomes a gateable failure instead of a stale wiki sentence.

This does not make a generated feature file automatically correct. If the source test encodes the wrong behavior, Blackbox preserves that wrong intent. The value is narrower: documentation stays tied to executable behavior and runtime proof.

## The Combined Loop (Triangulation of confidence)

The combined loop is a **triangulation of confidence**.

1. The test proves the workflow executes.
2. The effects prove the physical reality at the boundary.
3. The feature file makes the architectural intent readable.

<OverviewDiagram kind="proof-loop" />

Each layer catches a different failure class. The test catches broken execution. The physical trace catches missing required behavior and unexpected forbidden behavior. The feature file catches reviewability failures. Drift checks catch stale documentation.

The `subscribe-unknown-user` showcase is the clearest negative example. A response assertion can say the user was rejected. Effects can also prove that the system did not continue into the forbidden downstream path. The feature file gives reviewers a readable scenario without asking them to inspect spans directly.

This is why Blackbox belongs next to system and E2E tests, not inside unit tests. The useful evidence appears when the composed system runs. A unit-level assertion cannot prove what the system emitted at its boundaries during the actual test.

The loop also gives AI-assisted development a firmer stop condition: the test ran, the declared intent matched, the feature file regenerated, and the synchronization gates passed.

## Verification Gates (From test pass to drift check)

Blackbox gates are layered. Teams can start with runtime proof, then add feature-file gates when readable behavior becomes part of review.

| Gate | Artifact | What it protects |
| --- | --- | --- |
| Project test pass | Test | The workflow still executes |
| Effect matchers | Physical Reality | Required effects appear and forbidden effects stay absent |
| Effect coverage | Physical Trace | Cataloged effects are exercised |
| Feature emit | Feature file | Scenarios regenerate from the test source |
| Feature lint | Feature file | Given/When/Then shape stays useful |
| Feature drift check | Feature file | The `.feature` file still matches the test |
| CI behavioral gate | Full loop | Proof and documentation stay aligned |

For the concrete CI workflow, see [CI Behavioral Gates](/docs/blackbox/guides/ci-behavioral-gates). For the drift model behind the feature-file gate, see [Code-First BDD](/docs/blackbox/concepts/code-first-bdd).

The important sequence is from execution to evidence to readable output. A plain test pass says the workflow completed. Effect matchers say the physical reality at the boundaries behaved as declared. Feature-file checks say the readable artifact still reflects the test source.

There are alpha limits. Blackbox is Playwright-only for the current feature-file path, and parallel execution should use the Blackbox isolation model so captured spans remain attributable to the scenario that produced them. Those limits are deliberate because the proof depends on associating captured evidence with the specific test that produced it.

## Adoption Paths (Using layers separately)

The layers are useful separately. Teams do not need the full combined loop on the first day.

| Path | Use it when | Add later |
| --- | --- | --- |
| Effects only | System tests need runtime proof | Feature emission |
| Feature files only | Tests need a Gherkin view | Effect matchers |
| Combined loop | Refactors, incident regressions, AI-assisted changes, or spec-driven work need stronger gates | Stricter CI gates |

Start with effects when the main risk is invisible runtime behavior. The system already runs, but a passing test does not show whether boundary behavior matched intent.

Start with feature files when the main risk is unreadable or stale behavior documentation. The team wants Gherkin, but does not want another hand-maintained artifact.

Use the combined loop when both risks matter. That is the mental model before the quickstart: tests execute behavior, effects prove runtime boundaries, feature files make behavior readable, and gates keep the artifacts in sync.

To try the loop end to end, follow [First Proven Feature](/docs/blackbox/quickstart/first-proven-feature).
