Determinism applies to analysis: the same accepted intent, selected realization, analysis rules, and sealed evidence return the same result. It does not mean a distributed application executes identically on every run.

## 1. Approve Product Intent

A coding agent can translate a product requirement into proposed Gherkin, or the team can use direct behavioral declarations. A person approves the concrete case and its claims.

```gherkin title="features/product-cache.feature"
Feature: Product cache
  Scenario: Reuse a cached product
    When product 42 is read twice
    Then both reads succeed
    And at most one Postgres product read occurs
```

Gherkin is a reviewed projection, not a requirement for effects-only authoring. Both modes converge on the same SuitePlan.

## 2. Realize the Selected Test

The coding agent completes the concrete Playwright actions and visible assertions through the generated binding surface.

```ts title="suite.spec.ts"
import { expect, test } from "@playwright/test";

test("reuses a cached product", async ({ request }) => {
  const first = await request.get("/products/42");
  const second = await request.get("/products/42");

  expect([first.status(), second.status()]).toEqual([200, 200]);
});
```

Blackbox keeps three responsibilities separate:

| Artifact         | Responsibility                                                                   |
| ---------------- | -------------------------------------------------------------------------------- |
| **SuitePlan**    | Owns accepted cases, claims, completion requirements, capabilities, and topology |
| **RunnerBundle** | Owns the exact Playwright realization and discovery relations                    |
| **RunPlan**      | Selects only declared realizations for this run                                  |

RunPlan does not invent meaning. [See the complete alignment and identity rules](/docs/blackbox/reference/plans-and-realizations).

## 3. Capture One Fresh Attempt

Blackbox allocates a fresh sandbox lease, attempt, window, capture sessions, and evidence for each physical attempt.

OpenTelemetry traces carry observed operations. A separate assurance control plane carries participant, capability, completion, loss, cutoff, settlement, and seal facts. Blackbox needs both to determine which effects are eligible and what the evidence can establish.

## 4. Normalize Effects and Analyze Claims

Eligible observations become portable effect facts. The Analyzer compares those facts with the approved claims offline, without querying or changing the running system.

The native assertion and effect claim remain independent. Here, Playwright passes while the upper-bound claim is violated.

## Let Evidence Limit the Claim

Incomplete evidence can still establish an observed positive, a forbidden effect that occurred, or a count that already exceeds its maximum. It cannot establish satisfaction of absence, an upper bound, or an exact count.

Blackbox returns one of five verdicts for every selected claim: `satisfied`, `violated`, `inconclusive`, `unsupported`, or `integrity-failure`. Only `satisfied` passes.

## 5. Repair and Run Again

A finding routes the permitted repair and earliest required rerun gate. An application or capture repair requires a fresh runtime execution.

The coding agent can fix Redis behavior and rerun the same approved case. If the proposed fix requires changing accepted behavior, control returns to a person.

Optional [Observable Decision Coverage](/docs/blackbox/concepts/omc-dc-coverage) runs from sealed offline inputs after ordinary effect analysis. It cannot change ordinary effects or verdicts.
