Blackbox connects an approved behavior to one real system flow, records what happened, and returns four separate results.

<BlackboxEvidenceChainDiagram />

Read the chain from left to right: **human intent → agent-built harness → real execution → runtime evidence → verdicts → agent repair**.

Three terms appear throughout Blackbox:

| Term                                   | Plain meaning                                                                                                                                      | Subscription example                                     |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| **System under test (SUT)**            | The application and services whose behavior Blackbox runs or connects to.                                                                          | The compiled subscription API.                           |
| **Effect**                             | A meaningful runtime action performed at a system boundary, such as reading a database, calling an API, changing a cache, or publishing a message. | `SELECT users` or `INSERT subscriptions`.                |
| **Observable decision coverage (ODC)** | A comparison of the effects produced when tests exercise different outcomes of a code decision.                                                    | A known user causes an insert; an unknown user does not. |

The agent is involved all the way through. [Blackbox Skills](/docs/blackbox/guides/agent-skills) help it structure requirements, propose Gherkin, build the runtime and effect layers, interpret ODC, and repair the implementation. People approve the artifacts that define success. Deterministic Blackbox commands validate those artifacts and compute every runtime verdict.

## Start With or Without a Test

Blackbox exercises running software through a system or E2E test. Runtime verification eventually needs one, but you do **not** need one before adopting Blackbox.

| Your situation                                  | Start here                                                                                                                                                                                              |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **I already have a passing system or E2E test** | Keep it. Give one important flow a stable `@flow:<id>` and optionally generate readable behavior from it.                                                                                               |
| **I have no system or E2E test yet**            | Start with one behavior in plain language. Blackbox Skills can help the agent propose requirements, Gherkin, and a tagged Playwright skeleton. Step 2 connects the application and makes the flow real. |

Both paths meet at the same checkpoint:

```text
Existing passing test ──> add a stable flow ID ───────────┐
                                                          ├──> one accepted, tagged system flow
No test yet ──> describe behavior ──> create a test shell ┘
                                                                     │
                                                                     ▼
                                       connect application → make it pass → capture → verdicts
```

## One Subscription Flow, End to End

The walkthrough below follows the longer path: there is an application and a behavior to build, but no system test yet. If you already have a passing test, keep it and join at step 2.

### 1. No Test Yet: Start With Human Intent

A person starts with a goal or change request in natural language. `$blackbox-requirements` can turn it into atomic EARS requirements for review:

```text title="requirements/subscriptions.ears"
REQ-001: When a known user subscription is accepted, the API shall persist an active subscription record.
REQ-004: When an unknown user subscribes, the API shall not request payment or persist a subscription record.
```

After approval, `$blackbox-gherkin` can fill the next gap: readable examples with one shared flow ID.

```gherkin title="e2e/features/subscribe-user.feature"
@flow:subscribe-user
Feature: Subscribe a user

  @requirement:REQ-001
  Scenario: Known user is subscribed
    When the client subscribes user "alice"
    Then the response status is 201

  @requirement:REQ-004
  Scenario: Unknown user is rejected
    When the client subscribes user "ghost"
    Then the response status is 404
```

The agent proposes these artifacts; a person approves their meaning. EARS and Gherkin keep the intent readable, but they are optional during runtime. They do not run the application.

### 2. Reach the Shared Checkpoint

Blackbox can generate the tagged Playwright structure. The stable `@flow:subscribe-user` identity connects the readable behavior to the future run. The completed flow will look like this:

```ts title="e2e/subscribe-user.system.test.ts"
import { expect, test } from "@playwright/test";

test.describe("subscribe user", { tag: "@flow:subscribe-user" }, () => {
  test("known user is subscribed", async ({ request }) => {
    const response = await request.post("/subscriptions", {
      data: { userId: "alice" },
    });

    expect(response.status()).toBe(201);
  });

  test("unknown user is rejected", async ({ request }) => {
    const response = await request.post("/subscriptions", {
      data: { userId: "ghost" },
    });

    expect(response.status()).toBe(404);
  });
});
```

If you started with an existing test, this is where you join: keep its working action and assertion, then add the stable flow ID. Both starting paths now have one accepted, tagged system flow.

### 3. Connect the Application and Make the Flow Pass

`$blackbox-runtime` helps the agent connect the application, capture, and isolation setup. For a new flow, the agent or developer completes the project-specific request, assertion, fixtures, and test data, then runs the native test until it passes.

The deterministic CLI then runs the accepted flow:

```bash
pnpm exec blackbox test --flow subscribe-user
```

### 4. See What Actually Happened

Blackbox connects every observation to the attempt that caused it. It turns trace-based observations into normalized [effects](/docs/blackbox/concepts/effects-and-catalogs), such as a database read, HTTP call, or published message. This example produces two different evidence signatures:

| Attempt      | Response | Observed effects                                                |
| ------------ | -------- | --------------------------------------------------------------- |
| Known user   | `201`    | `postgres SELECT users` → `postgres INSERT subscriptions`       |
| Unknown user | `404`    | `postgres SELECT users`; no subscription insert or payment call |

The native assertions check what the client sees. After the first run, `$blackbox-effects` helps the agent inspect these facts and propose which actions should become required or forbidden behavior:

```yaml title="e2e/features/subscribe-user.effects.yaml"
specVersion: "0.1"
flow: subscribe-user

requires:
  - { boundary: postgres, op: SELECT, key: users, service: api }

forbids:
  - { boundary: http, op: POST, key: /v1/payment_intents, service: api }
```

The agent proposes the contract; a person approves the policy. Observed actions do not automatically become requirements.

The effect contract checks required and forbidden work. [Observable decision coverage (ODC)](/docs/blackbox/concepts/omc-dc-coverage) compares the complete signatures for exercised decision outcomes. Here it asks: did the known-user and unknown-user outcomes leave distinguishable runtime effects?

### 5. Read Separate Verdicts

```text
FLOW subscribe-user
  tests       PASS    2 attempts
  integrity   PASS    capture complete
  effects     PASS    required and forbidden policy satisfied
  ODC         REPORT  user-exists outcomes produced distinct evidence
```

Each line answers a different question:

| Verdict       | Meaning                                                           |
| ------------- | ----------------------------------------------------------------- |
| **Tests**     | The client received the approved responses.                       |
| **Integrity** | The runtime evidence is complete enough to trust.                 |
| **Effects**   | Required work happened and forbidden work did not.                |
| **ODC**       | The exercised decision outcomes produced distinguishable effects. |

`$blackbox-odc` helps the agent interpret decision propagation. `$blackbox-repair` turns a deterministic finding into an implementation change, then runs the same accepted flow again. Changing the approved behavior or policy still requires human review.

## What Blackbox Does Around the Test

| Moment        | Blackbox action                                                                  |
| ------------- | -------------------------------------------------------------------------------- |
| **Before**    | Starts or connects to the SUT, isolates mutable state, and opens an attempt.     |
| **During**    | Propagates the flow and attempt identity; records effects and executed branches. |
| **At close**  | Waits for related work, validates capture, and seals the evidence.               |
| **Afterward** | Checks effects, reconstructs decisions, calculates ODC, and writes the verdicts. |

For Node.js, a small capture component uses OpenTelemetry for boundary effects and V8 for executed code. A cell-local sidecar validates identities and stores the evidence. Other languages can provide different capture and analysis components without changing this lifecycle.

<Aside type="note" title="Isolation Is Part of the Evidence">
  A fresh API process with a shared, dirty database is not isolated. Blackbox
  can prove that a forbidden effect was absent only when the flow's mutable
  state is isolated or reset.
</Aside>

Host commands, Compose, Dockerfiles, compiled artifacts, external SUTs, and custom provisioners all follow the same chain. Only SUT startup and lifecycle ownership change.
