The overview showed a checkout request return `201` while the running system sent two payment requests. Blackbox reaches
that finding through one directional chain from a human-approved behavioral contract to fresh runtime evidence.

Blackbox analysis is deterministic: an unchanged behavioral contract, test selection, analysis rules, and evidence
produce the same finding. The application itself may behave differently on another run.

## People Approve the Behavioral Contract

A coding agent translates a product requirement into a proposed behavioral contract. A person reviews and approves the
concrete case and its runtime-effect claims before implementation continues.

```gherkin title="features/checkout.feature"
Feature: Checkout completion
  Scenario: Charge a completed checkout once
    When checkout completes
    Then the response status is 201
    And no more than one charge request is sent
```

This example uses reviewed Gherkin. Direct behavioral declarations can enter the same verification chain. In either
mode, the behavioral contract stays upstream: the test and traces can verify it, but they cannot redefine it.

## The System Test Runs One Contract Case

The coding agent completes the Playwright actions and visible assertions for the approved contract case.

```ts title="suite.spec.ts"
import { expect, test } from "@playwright/test";

test("completes checkout", async ({ request }) => {
  const response = await request.post("/checkout");

  expect(response.status()).toBe(201);
});
```

The test performs the case, but it does not become the behavioral contract. Blackbox keeps the approved contract, the
Playwright realization, and run selection separate so downstream artifacts cannot invent new behavior. [Look up the
exact plan and identity responsibilities](/docs/blackbox/reference/plans-and-realizations).

## Every Attempt Gets Fresh Evidence

Each physical attempt receives a fresh runtime and evidence boundary. A retry or sequence member starts with a new
identity instead of inheriting observations from another attempt.

OpenTelemetry traces reveal supported runtime activity. Capture records establish which observations belong to the
attempt and which conclusions the evidence can support. [Look up the exact capture lifecycle](/docs/blackbox/reference/capture-lifecycle-and-correlation).

## Traces Become Effects

Blackbox normalizes supported observations into effects such as HTTP calls, database operations, cache operations, and
published messages. It compares those effects with the claims in the behavioral contract without querying or changing
the running system during analysis.

<BlackboxPlaywrightTerminal />

The native assertion and the effect claim remain independent. Here, Playwright passes while the payment-request limit is
violated.

## Evidence Limits the Finding

Evidence can establish only the part of a claim it supports. Observing a second payment request is enough to violate a
maximum of one, even if capture later becomes incomplete. Observing only one request with incomplete evidence cannot
establish that no second request occurred.

[Look up effect signatures, claim kinds, evidence rules, and verdicts](/docs/blackbox/reference/effects-and-claims).

## Findings Guide Repair

A finding returns the mismatch to the coding agent as a bounded repair problem. The agent can remove the duplicate
charge and run the same behavioral contract again with fresh evidence.

If the repair requires a different behavioral contract, control returns to a person for approval. Runtime observations
never authorize that change.
