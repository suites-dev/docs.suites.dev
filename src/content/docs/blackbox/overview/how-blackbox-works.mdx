Blackbox works by connecting an accepted behavior to one tagged system flow, running that flow against the real application, recording what happened, and calculating separate verdicts from sealed evidence.

<BlackboxEvidenceChainDiagram />

Read the chain from left to right: **human intent → agent-assisted harness → system execution → effects and decision evidence → verdicts → repair**.

## Two Starting Paths, One Runtime Chain

| Starting situation               | How it reaches Blackbox                                                                              |
| -------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **A passing system or E2E test** | Keep the test and give the behavior one stable `@flow:<id>`.                                         |
| **No system or E2E test yet**    | Describe one behavior. An agent can propose EARS, Gherkin, and a tagged test shell for human review. |

EARS and Gherkin keep intent readable, but they are optional at runtime. Both paths must eventually produce one accepted, passing system flow.

## 1. A Person Accepts the Target

The target may begin as a change request, an EARS requirement, a Gherkin scenario, or an existing test. Blackbox Skills can help a coding agent fill the gaps between those artifacts.

The person still approves what success means: the behavior, native assertions, stable flow ID, required and forbidden effects, isolation assumptions, and any coverage gate.

## 2. The Flow Exercises the Real Application

The **system under test (SUT)** is the application and services being verified. Blackbox starts it or connects to it, waits until it is ready, creates an isolated test cell, and opens a unique attempt for each Playwright test execution.

The `@flow:<id>` connects the accepted behavior to every attempt, retry, captured event, artifact, and report.

## 3. Capture Records Effects and Executed Code

An **effect** is a meaningful action at a system boundary: a database operation, API call, cache change, or published message. Blackbox also records the executed code and source maps needed to reconstruct decisions later.

One subscription flow might leave this trace:

| Attempt      | Visible result | Runtime effects                                                   |
| ------------ | -------------- | ----------------------------------------------------------------- |
| Known user   | `201`          | Read `users`, then insert `subscriptions`                         |
| Unknown user | `404`          | Read `users`; no subscription insert and no payment-provider call |

The test checks the visible result. Effects show what the application did behind that result.

## 4. Blackbox Seals First and Analyzes Offline

During the run, Blackbox correlates each observation with the attempt that caused it. At attempt close, it waits for related work, checks capture integrity, stores exact artifacts by digest, and seals the evidence.

Offline analysis then:

- Checks approved required and forbidden effects.
- Joins executed code to source maps.
- Reconstructs exercised decision outcomes.
- Calculates **observable decision coverage (ODC)**—whether different outcomes of a code decision produced distinguishable runtime effects.

Because analysis is offline, the same sealed run can be inspected again without restarting the application.

## 5. Each Verdict Answers One Question

```text
FLOW subscribe-user
  tests       PASS    approved responses observed
  integrity   PASS    capture complete
  effects     PASS    required work happened; forbidden work did not
  ODC         REPORT  exercised outcomes produced distinct evidence
```

| Verdict       | What it tells you                                                  |
| ------------- | ------------------------------------------------------------------ |
| **Tests**     | The system returned the expected visible result.                   |
| **Integrity** | The evidence is complete enough to support a conclusion.           |
| **Effects**   | The accepted required and forbidden runtime policy was satisfied.  |
| **ODC**       | Exercised decision outcomes propagated to distinguishable effects. |

## 6. The Agent Repairs Against a Fixed Target

Blackbox Skills can help the agent propose specifications, connect the runtime, review effects, interpret ODC, and repair implementation. Deterministic CLI, runner, capture, and analyzer components compute the gates.

```text
Skills propose → people approve the target → Blackbox computes
       ↑                                          ↓
       └──────── agent repairs implementation ← finding
```

The agent may change implementation and rerun the same flow. If passing requires changing the accepted behavior, assertion, effect policy, isolation promise, or coverage gate, control returns to a person.

<Aside type="note" title="Isolation Makes Negative Claims Trustworthy">
  A new API process that shares a dirty database is not an isolated system.
  Blackbox can conclude that a forbidden effect was absent only when the flow's
  mutable state is isolated or reset.
</Aside>
