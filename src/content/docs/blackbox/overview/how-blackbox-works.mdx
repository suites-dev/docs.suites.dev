An accepted checkout scenario says one completed order produces at most one charge request:

```gherkin
Scenario: Do not charge a completed order twice
  Given checkout encounters a transient timeout
  When the order completes after a retry
  Then one order is confirmed
  And no more than one charge request is sent
```

The system suite sees one confirmation and one order ID, but runtime evidence contains two charge requests. The native assertion passes; the Blackbox effect finding fails. The coding agent now has a clear repair problem without gaining permission to redefine success.

<Aside type="info" title="Alpha Status">
  Gherkin-to-suite alignment is an **Alpha target**. Effects are the **committed
  core** of behavioral assurance. Observable Decision Coverage is an **Alpha
  target** and remains separate from effect findings.
</Aside>

## One Chain, Two Correction Loops

Blackbox uses one accepted behavior across two connected loops:

- **Alignment loop:** Keep Gherkin, accepted meaning, and the executable system realization aligned before runtime work begins.
- **Verification loop:** Execute the declared realization, capture fresh evidence, analyze it, and return findings for repair.

A coding agent can work across both loops. A person approves accepted behavior and any policy that determines success. [See who proposes, computes, repairs, and approves](/docs/blackbox/concepts/human-agent-verification-loop).

[Use the alignment guide](/docs/blackbox/guides/recover-behavior-from-existing-tests) when Gherkin or the executable suite changes. [Look up the blocking checks](/docs/blackbox/reference/alignment-checks) when runtime cannot begin.

## 1. Accept the Behavior

A person reviews and approves the Gherkin scenario. Blackbox compiles that behavior into a **SuitePlan**, which owns its accepted meaning.

The agent may propose scenarios or corrections. Neither generated code nor observed runtime behavior can silently rewrite the SuitePlan.

[See how human intent becomes accepted meaning without moving authority](/docs/blackbox/concepts/specifications-flows-and-verdicts#keep-the-chain-directional).

## 2. Declare How the Behavior Runs

The system suite provides the concrete actions and checks that realize the accepted behavior. A **RunnerBundle** owns that realization.

A **RunPlan** selects the declared cases and realization for this run. It cannot add, weaken, or reinterpret accepted meaning.

[See how SuitePlan, RunnerBundle, and RunPlan keep meaning, realization, and selection separate](/docs/blackbox/reference/plans-and-realizations).

Stable identity binds the accepted case, declared realization, selected run, attempt, evidence, and finding. [See why titles and source order are not enough](/docs/blackbox/concepts/specifications-flows-and-verdicts#preserve-identity-across-representations), or [look up case and execution identity](/docs/blackbox/reference/scenario-dsl).

## 3. Capture a Fresh Attempt

Runtime opens a fresh managed-capture boundary for every case attempt, retry, and sequence member. It owns the attempt identities, capture lifecycle, correlation, and resulting evidence.

Here, a **retry** is another runner attempt of the case. An application-internal payment retry during the same checkout execution remains inside that attempt. [See how attempts and retries keep separate evidence](/docs/blackbox/concepts/runtime-evidence#bound-one-attempt-at-a-time).

During that attempt, the current Alpha prototype uses OpenTelemetry to observe supported HTTP and database work across service boundaries. OpenTelemetry supplies observations; it does not decide which effects are accepted or forbidden.

[Look up how Blackbox correlates distributed work, establishes completion, and seals one attempt](/docs/blackbox/reference/capture-lifecycle-and-correlation).

## 4. Normalize and Seal Observations

In the current Alpha prototype, Blackbox receives OpenTelemetry Protocol (OTLP) trace data, retains the raw capture, and normalizes eligible observations into **effects**. Other spans do not silently become effects or policy. [See how the effects catalog supplies shared vocabulary](/docs/blackbox/concepts/effects-and-catalogs#use-the-effects-catalog-as-shared-vocabulary).

[Look up the stable catalog responsibilities and current public-contract boundary](/docs/blackbox/reference/catalog-schema).

Runtime records capture capability, completion, loss, and integrity facts before sealing the evidence. Sealing fixes one attempt's evidence so later analysis cannot rewrite or combine its inputs. An observation proves what Blackbox saw; it does not by itself prove that nothing else happened. [See the four evidence conditions](/docs/blackbox/concepts/runtime-evidence#establish-four-evidence-conditions).

## 5. Analyze the Sealed Evidence

The Analyzer compares accepted meaning and analysis policy with the sealed evidence. The declared realization identifies which approved execution produced that evidence. With the same SuitePlan, realization, analysis policy, and sealed evidence, the Analyzer returns the same findings. This determinism applies to analysis, not to whether a distributed application behaves identically on every run.

## Read Each Finding Separately

| Result          | Question it answers                                                        |
| --------------- | -------------------------------------------------------------------------- |
| **Native test** | Did the system return the expected visible result?                         |
| **Integrity**   | Is the captured evidence eligible for this conclusion?                     |
| **Effects**     | Did required work happen, and did forbidden work remain absent?            |
| **ODC**         | Did exercised decision outcomes produce distinguishable effect signatures? |

These results remain independent. A native pass can coexist with a violated or inconclusive effect finding, and integrity failure never becomes a pass. [See how system assertions and Blackbox findings work together](/docs/blackbox/concepts/testing-layers#keep-both-results-independent).

**Effects are the committed core.** **[Observable Decision Coverage (ODC)](/docs/blackbox/concepts/omc-dc-coverage)** is an Alpha target. It remains separate and cannot change an ordinary effect finding.

[See how to keep ODC report-only or choose a deliberate CI policy](/docs/blackbox/guides/reports-and-ci-gates#choose-the-odc-policy-deliberately).

## Let Evidence Limit the Claim

Blackbox can report effects it observed even when other evidence is incomplete. It cannot establish a claim that depends on complete visibility when capture or isolation is insufficient, including:

- The absence of a forbidden effect.
- Satisfaction of an upper bound.
- Satisfaction of an exact count.

For a completeness-dependent claim, incomplete evidence produces an **inconclusive** finding; an unavailable required capability produces **unsupported**. Neither passes. [See all findings and verdicts](/docs/blackbox/concepts/effects-and-catalogs#read-findings-and-verdicts).

## Repair Without Moving the Target

A failed finding returns to the coding agent for implementation repair and another run. If passing requires changing accepted behavior or analysis policy, control returns to a person.
