Blackbox works through two connected loops. The **behavior-alignment loop** keeps human-readable intent and executable system tests together. The **runtime-verification loop** runs that same test against the real application and proves what happened.

One stable `@flow:<id>` joins the loops.

<BlackboxEvidenceChainDiagram />

## Loop 1: Keep Behavior and Tests Aligned

Teams can enter the alignment loop from either direction:

| Starting point                      | What Blackbox helps you do                                                                                     |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| **New behavior in human language**  | Structure the intent, review readable examples, and generate a tagged Playwright test shell.                   |
| **An existing passing system test** | Give it a stable flow ID, emit readable behavior from the executable test, and review what the test expresses. |

**EARS** is a small structured format for writing unambiguous requirements. **Gherkin** expresses behavior as readable scenarios. Both help people and coding agents discuss intent; neither is required to execute the runtime loop.

The alignment loop is deliberately two-way:

```text
human intent → optional EARS/Gherkin → tagged system flow
                         ↑                    │
                         └── emit and review ─┘
```

Static commands validate requirements, flow identities, feature-to-suite alignment, and drift. A coding agent may propose or repair the artifacts. A person approves their meaning.

This avoids two common failures:

- A readable specification that no longer matches executable tests.
- A passing test whose behavior is difficult for people or agents to review.

## The Shared Checkpoint: One Accepted Flow

Both starting paths must reach the same checkpoint: one passing Playwright flow with exactly one stable `@flow:<id>`.

For the subscription example, `@flow:subscribe-user` connects:

- The reviewed `subscribe-user.feature` file, when the team uses one.
- The `subscribe-user.system.test.ts` Playwright flow.
- Its known-user and unknown-user attempts.
- Every captured event, artifact, effect, and verdict from those attempts.

Changing a description does not change the identity. Reusing the same ID for unrelated behavior is rejected.

## Loop 2: Verify the Running System

The second loop starts from that accepted flow:

```text
tagged flow → isolated SUT → sealed evidence → separate verdicts
     ↑                                               │
     └──────────── agent repairs implementation ─────┘
```

Three terms matter here:

| Term                                   | Plain meaning                                                                                             |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| **System under test (SUT)**            | The application and services Blackbox starts or connects to for the flow.                                 |
| **Effect**                             | A meaningful boundary action, such as a database operation, API call, cache change, or published message. |
| **Observable decision coverage (ODC)** | Whether different outcomes of an exercised code decision produced distinguishable runtime effects.        |

Blackbox opens an attempt for each Playwright execution, propagates its identity into the SUT, records supported effects and executed code, waits for related work to settle, and seals the evidence with its integrity findings.

The subscription flow can produce two evidence signatures:

| Attempt      | Visible result | Observed runtime effects                                             |
| ------------ | -------------- | -------------------------------------------------------------------- |
| Known user   | `201`          | Read `users`, then insert `subscriptions`                            |
| Unknown user | `404`          | Read `users`; no subscription insert and no payment-provider request |

The native assertions check the responses. Effects show what the application did behind those responses. ODC compares the two complete signatures and asks whether the decision outcomes remained observable at the system boundary.

## Evidence Comes Before Policy

The first run records facts. An observed database write does not automatically become required behavior.

A person reviews the evidence and approves the smallest required-and-forbidden effect policy. Offline analysis then records both the immutable evidence identity and the reviewed policy identity in a derived verdict. Reanalysis does not rewrite the original run.

The next runtime run snapshots the accepted policy alongside its new evidence.

## Each Verdict Answers One Question

```text
FLOW subscribe-user
  tests       PASS    approved responses observed
  integrity   PASS    capture complete
  effects     PASS    required work happened; forbidden work did not
  ODC         REPORT  exercised outcomes produced distinct evidence
```

| Verdict       | What it tells you                                                  |
| ------------- | ------------------------------------------------------------------ |
| **Tests**     | The system returned the expected visible result.                   |
| **Integrity** | The available evidence is complete enough for this conclusion.     |
| **Effects**   | The accepted required and forbidden runtime policy was satisfied.  |
| **ODC**       | Exercised decision outcomes propagated to distinguishable effects. |

Blackbox does not turn missing capture or uncertain isolation into a passing result.

## The Agent Works Across Both Loops

Blackbox Skills help a coding agent propose requirements, review Gherkin, connect the application, inspect effects, interpret ODC, and repair implementation. Deterministic CLI, runner, capture, and analyzer components compute the gates.

The agent may repair implementation and rerun the same accepted flow. If passing requires changing the behavior, assertion, effect policy, isolation promise, or coverage gate, control returns to a person.

<Aside type="note" title="Isolation Makes Negative Claims Trustworthy">
  A new API process that shares a dirty database is not an isolated system.
  Blackbox can conclude that a forbidden effect was absent only when the flow's
  mutable state is isolated or reset.
</Aside>
