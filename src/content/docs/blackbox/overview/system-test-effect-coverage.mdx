Code coverage counts lines. **Effect coverage** counts proof: the physical runtime evidence that a system test produced the boundary behavior the workflow depends on.

Blackbox treats effect coverage as the missing system-test sibling to line, branch, and decision coverage. It answers the fundamental question: when the system ran, did the **physical reality** of the boundary actions match your architectural intent?

<OverviewDiagram kind="coverage" />

## Effect Coverage: The Missing Sibling

Most teams already use several kinds of coverage. Line coverage tells you which statements executed. Branch coverage tells you which branch arms ran. Effect coverage is the missing sibling because it covers what those signals do not name directly: **boundary actions**, the observable behaviors a real system run performs across storage, services, queues, caches, and APIs.

For Blackbox, that means a Playwright system test is no longer only a request and a response assertion. The test also leaves behind a **physical trace** of what the five-service topology did while satisfying that assertion.

That matters for `subscribe-flow`. A green `POST /subscriptions` response is useful, but it is not the whole proof. Reviewers also need to know whether the physical reality matched the intent: did the system look up `alice`, create the payment intent, and update Redis as required?

## Why Code Coverage is Not Enough (The input/output gap)

Code coverage is strong inside the implementation. It tells you that a test executed files, functions, lines, and branches. That signal helps teams find untested code and spot dead zones.

<InputOutputGapDiagram />

System behavior has an **input/output gap**. A test can send the expected input and receive the expected output while missing the physical reality of the behavior in between.

For example, `subscribe-flow` can still return `201 Created` if an implementation keeps the HTTP response stable while dropping a required SQS message. Line execution cannot tell you whether that boundary action happened; it can only tell you that the code ran. Effect coverage adds the system-level signal: what the running topology actually did.

## What Counts as an Effect (Boundary actions at runtime)

An **effect** is an observable runtime action that crosses a system boundary and expresses architectural intent.

In the subscription showcase, the physical trace includes:

1. Reading `alice` from Postgres.
2. Calling the Prism Stripe payment intent endpoint.
3. Inserting a subscription row in Postgres.
4. Writing the user's tier to Redis.
5. Calling the order service.
6. Sending the subscription message to SQS.

The transport is not the point. The point is that the action is observable during the test run and meaningful enough for review.

Blackbox usually derives effects from OpenTelemetry spans, then matches those effects against a reviewed catalog. Spans are raw runtime evidence. Effects are the behavior your team chooses to treat as part of the workflow contract.

Read [System Effects](/docs/blackbox/concepts/effects-and-catalogs) when you need the deeper model for effects, catalogs, matchers, and report states.

## Required vs Forbidden Coverage (Proving the negative)

Effect coverage is positive and negative.

Required coverage proves that expected behavior appeared. In `subscribe-flow`, the run should show the user lookup, payment intent, subscription insert, Redis write, order-service call, and SQS message.

Forbidden coverage proves that behavior stayed absent. This is **proving the negative**: the report is useful because a forbidden action has no matching runtime evidence.

The `subscribe-unknown-user` path makes the difference clear. When `ghost-user` is not found, the run should stop after lookup behavior. It should not create a payment intent, insert a subscription, update Redis, call the order service, or send the SQS message.

That negative space is where many system regressions hide. A response assertion can prove the user saw the expected error. It cannot, by itself, prove that the topology avoided every downstream action the error path must avoid.

Effect coverage turns both sides into reviewable evidence. A required effect that is missing is a coverage gap. A forbidden effect that appears is a behavioral failure.

## Decision Sensitivity (Introduction to OMC/DC)

Effect coverage tells you whether expected boundary actions happened. **OMC/DC** is the companion signal that asks whether *decisions* in the system produced distinguishable boundary behavior. In `subscribe-flow`, the `alice` path should reach payment, persistence, cache, order service, and SQS; the `ghost-user` path should not. If both paths return different HTTP responses but produce indistinguishable observed effects, the system-test evidence is too weak.

Read [OMC/DC Coverage](/docs/blackbox/concepts/omc-dc-coverage) for the report verdicts, math, and technical implementation.

## Evidence over Formal Proof (The practical engineering gate)

Blackbox reports evidence from real executions. It does not prove every possible input, environment, race, or future code path.

That limit is intentional. Effect coverage works as a practical engineering gate because it gives reviewers concrete facts from the run they are about to trust. The report can show that a required effect was observed, a required effect was missing, a forbidden effect appeared, or a decision was not distinguishable from the evidence collected.

Use the result to decide what to do next:

1. Add a scenario when an important path was not exercised.
2. Update the effect catalog when the intended behavior changed.
3. Fix instrumentation when no useful spans reached Blackbox.
4. Block the change when required behavior disappeared or forbidden behavior appeared.
5. Accept a known limit when the current evidence is enough for the risk.

This is why effect coverage belongs beside the test result, not hidden behind it. A passing Playwright run says the workflow executed. Effect coverage says which boundary behavior the run proved.

When you have generated artifacts, read [Reading Coverage Reports](/docs/blackbox/guides/reading-coverage-reports) to inspect `catalog/coverage.json`, `shape/coverage.json`, and the OMC/DC report family in the right order.

For how effect coverage interacts with the executable test, the effect catalog, and optional feature files, read [Tests, Effects, and Feature Files](/docs/blackbox/overview/tests-effects-and-feature-files).
