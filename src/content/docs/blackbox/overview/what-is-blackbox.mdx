**Suites Blackbox** is a system-testing framework for verifying that a running system produces the side effects its implementation claims. A `200 OK` response shows the system replied, but not that it produced the expected downstream effects.

While a passing E2E test proves your system *responded*, it does not prove it *behaved*. AI coding agents and human refactors can change implementations in seconds, and a green checkmark can easily hide a silent failure at your system boundaries.

<InputOutputGapDiagram />

Blackbox captures **physical runtime evidence** (database writes, HTTP calls, and queue messages) and turns it into a durable behavioral contract.

## Runtime Evidence vs. Reviewed Intent

Blackbox compares observed runtime effects against a reviewed catalog of required and forbidden effects.

<div style="margin: 1.5rem 0 2rem;">

### The Test Assertion
The Playwright flow still owns the visible assertion.

```ts
await expect(capture).toObserveEffects({
  requires: [
    effect.postgres('SELECT', { table: 'users' }),
  ],
  forbids: [
    effect.http('POST', { path: '/v1/payment_intents' }),
    effect.sqs('SendMessage', { queue: 'subscription-orders' }),
  ],
});
```

### The Contract (Intent)
The reviewed catalog of required and forbidden behavior.

```yaml
subscribe-unknown-user:
  requires:
    - { boundary: postgres, op: SELECT, key: users }
  forbids:
    - { boundary: http, op: POST, key: /v1/payment_intents }
    - { boundary: sqs, op: SendMessage, key: subscription-orders }
```

</div>

<Aside type="info" title="Test-Time Instrumentation">
Blackbox instruments compatible Node SUT containers during the test run. The compose testbed mounts a bootstrap volume, shadows the service's Node binary with `node-wrap`, and preloads the instrumentation before application code. You do not need to add OpenTelemetry SDKs or SDK imports to your production code.
</Aside>

## The Silent Failure Problem

Many serious behavior requirements are negative. The system must *not* create a subscription for `ghost-user`. It must *not* create a payment intent for a rejected user.

This is **proving a non-event**. Ordinary assertions check the response, not what the system avoided doing in the background. A response can confirm rejection while a forbidden side effect still occurs undetected.

Blackbox makes the negative space reviewable. It checks captured evidence for the **physical absence** of forbidden effects. If a flow rejects a user, the proof is not only the error response; the proof is that the cataloged forbidden Postgres, Redis, and SQS effects never appeared in the run evidence.

## Where it Fits

Blackbox sits at the "Evidence Boundary" of your testing strategy. It complements unit and integration tests by proving behavior that only appears when the composed system runs against real dependencies.

<TestingPyramidDiagram />

Use Blackbox when a green assertion is too thin for the risk: refactors, migrations, and AI-assisted implementation. It is strongest when the topology is controlled, the boundaries emit useful signals, and the team reviews the catalog instead of accepting every observed detail.

## How it Works

Blackbox follows a simple chain: evidence becomes effects, effects become a catalog, and the catalog becomes coverage.

<OverviewDiagram kind="workflow" />

The catalog is the durable contract. Runtime evidence is the fact base. Coverage is the result that tells you whether the run satisfied the contract.
