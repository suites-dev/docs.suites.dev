**Suites Blackbox is the deterministic behavioral verification layer in a coding-agent harness.**

It compares human-approved behavior with bounded runtime evidence from declared system and E2E flows, then returns findings that guide implementation repair without letting the coding agent redefine success.

## Why does Blackbox Exist?

**Because verification becomes the new constraint**

Coding agents can generate implementations and tests faster than people can establish that the result is correct. When one agent derives both from the same interpretation, the code and test can share the same blind spot.

This creates a **verification bottleneck**:

- **More candidates:** Code is cheap to generate but expensive to verify.
- **Review queues grow:** Pull requests arrive faster than people can assess runtime behavior.
- **Green tests miss effects:** Expected responses can hide missing or forbidden work.

Harness engineering addresses that problem with **feedforward guidance** that defines the target and constraints before the agent acts, and **feedback** that evaluates the result against them afterward.

## Who Blackbox is For?

Blackbox is for teams that use coding agents such as Claude Code, Codex, and others to build or change behavior across real service boundaries.

- **System and E2E verification:** Check selected flows through the running system.
- **Deterministic repair findings:** Give coding agents findings they can act on without redefining success.
- **Bounded runtime evidence:** Base verdicts on captured behavior within a declared evidence boundary.

## How does Blackbox work?

People decide what success means. A coding agent and its skills can propose, implement, diagnose, and repair. Blackbox executes the declared realization, manages the evidence boundary, and analyzes the result.

In the Alpha target flow, Gherkin expresses accepted behavior in a readable, reviewable form. The executable system suite realizes that behavior; Gherkin does not become runtime evidence or change effect findings.

## Verify What the System Did

A system or E2E flow can pass on its visible result while required work is missing or forbidden work occurs. Blackbox verifies those **effects**, such as database writes, published messages, and external calls.

OpenTelemetry is one capture source. Blackbox correlates supported observations with the current attempt and normalizes them into effects before analysis.

The passing assertion and failed effect finding answer different questions. The visible order is correct, but charging the customer twice is not.

**Effects are the committed core of Blackbox behavioral assurance.** **[Observable Decision Coverage (ODC)](/docs/blackbox/concepts/omc-dc-coverage)** is an Alpha target and remains separate: it cannot change ordinary effect findings.

## Keep Assurance Bounded by the Evidence

Blackbox establishes claims about declared behavior inside a managed evidence boundary. It does not prove that the approved target expresses what people truly wanted, and it does not prove the entire application correct.

Evidence quality limits the verdict. If capture is incomplete, Blackbox cannot establish claims that depend on seeing everything: the absence of a forbidden effect, an upper bound, or exactness. Missing observations never become proof of success.

Managed capture starts fresh for every case attempt, retry, and sequence member. That boundary prevents evidence from another execution from silently influencing the current finding.
