**Suites Blackbox provides behavioral verification for software developed with coding agents.**

With Blackbox, a coding agent turns product requirements into a proposed **behavioral contract**. A person approves
the contract, then the agent realizes it as a system or E2E test.

When the test runs, Blackbox adds verification of runtime effects from OpenTelemetry traces. Deterministic findings
guide repair without changing the approved behavioral contract.

behavioral contract allowed at most one. The agent removed the duplicate charge and ran the same contract again with
fresh evidence.

**People approve the behavioral contract. Agents implement and repair it. Blackbox verifies the run.**

## From Product Requirements to a Behavioral Contract

A behavioral contract describes the expected behavior for selected system flows. A coding agent can propose that
contract as Gherkin, including the visible result and the runtime-effect claims that matter. A person reviews and
approves it before the agent completes the Playwright test.

## Why Blackbox?

Coding agents can produce implementations and tests faster than people can verify runtime behavior. Pull requests
accumulate, while a passing response can still hide duplicate calls, missing writes, or forbidden messages.

Harness engineering surrounds an agent with guidance before it acts and feedback after it acts. Blackbox supplies the
behavioral verification part of that harness, so repair can move quickly while people retain authority over the
behavioral contract.

## Use Blackbox When

- Your team runs system or E2E tests across real service boundaries.
- Coding agents such as Claude Code or Codex implement and repair product behavior.
- A passing response can hide important HTTP, database, cache, or messaging work.

## Verify Runtime Effects

An **effect** records observed work at a supported system boundary, such as an HTTP call, database operation, cache
operation, or published message. A claim in the behavioral contract states whether that effect is required, forbidden,
ordered, compared, or limited.

The native assertion and the Blackbox finding answer different questions. The assertion checks the visible result.
Blackbox checks the runtime-effect claim against evidence from the same attempt.

Findings stay bounded by that evidence. Incomplete evidence cannot establish absence, upper-bound satisfaction, or an
exact count. [See how OpenTelemetry observations become effects](/docs/blackbox/concepts/effects-and-catalogs).

## Connect Code Decisions to Runtime Effects

Optional-per-run Alpha [Observable Decision Coverage](/docs/blackbox/concepts/omc-dc-coverage) compares declared code
outcomes with the runtime-effect pattern observed for each case. It helps show whether important outcomes remained
distinguishable at the system boundaries the tests observed.

ODC adds diagnostic coverage insight. It cannot change an ordinary effect finding and does not claim that an observed
association proves causation.
