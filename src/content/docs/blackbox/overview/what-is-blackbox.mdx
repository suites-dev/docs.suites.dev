**Suites Blackbox provides behavioral verification for software developed with coding agents. It turns human-approved product requirements into system and E2E tests, verifies the running system's effects from OpenTelemetry traces, and returns deterministic findings that guide repair without letting the agent redefine success.**

<CheckoutVerificationLoop />

The coding agent loads `@blackbox-gherkin` to propose an executable checkout scenario. A person approves that behavior before the agent creates the test or changes the implementation.

The first E2E run returns `201 Created`, but Blackbox observes two charge requests. The agent uses the deterministic finding to repair the implementation, then runs the same locked behavior again.

- **For people:** The result shows what happened inside the running system, not only what the test returned.
- **For coding agents:** The finding identifies what to repair while the approved requirement remains fixed.

## From Product Requirements to systen Tests

The `@blackbox-gherkin` Skill turns the product requirement into a proposed <TextLink href="https://cucumber.io/docs/gherkin/reference/" target="_blank" rel="noopener noreferrer"><strong>Gherkin</strong></TextLink> `.feature` file. A person approves the scenario and its effect claim before either can guide implementation.

The agent then runs `blackbox test` to execute the flow and seal runtime evidence. When the first run finds two charge requests, `blackbox analyze --run latest` reproduces the finding from that sealed evidence without restarting the application. The implementation changes; the approved feature does not.

[See how Blackbox Skills guide coding agents without deciding the result](/docs/blackbox/guides/agent-skills#know-what-computes-each-result).

## Why Blackbox?

Coding agents can generate implementations and tests faster than people can verify them. When one agent derives both from the same interpretation, the code and test can share the same blind spot. This creates a **verification bottleneck**: pull requests arrive faster than people can assess runtime behavior, while green tests can still hide missing or forbidden work.

Harness engineering addresses this bottleneck by surrounding the agent with guidance and feedback. Blackbox makes the behavioral feedback independent of the agent's judgment.

[See how people, coding agents, Skills, and Blackbox share this verification loop](/docs/blackbox/concepts/human-agent-verification-loop).

## Who Blackbox is For?

Blackbox is for teams that:

- Run system and E2E tests across real service boundaries.
- Use coding agents such as Claude Code and Codex in autonomous or semi-autonomous engineering loops.

Teams can use the same accepted behavior in local repair loops and CI.

[See how Blackbox becomes a CI gate](/docs/blackbox/guides/reports-and-ci-gates#add-the-runtime-gate).

## Verify Runtime Effects

**Effects** are system-visible actions Blackbox derives from supported OpenTelemetry trace evidence, such as outgoing HTTP requests, observed database operations, and published messages. They show what happened during the test, beyond its visible response. [See how observations become effects through the catalog](/docs/blackbox/concepts/effects-and-catalogs#from-observation-to-finding).

**Effects are the committed core of Blackbox behavioral verification.**

Only complete evidence can establish absence, upper bounds, or exact counts. Otherwise, Blackbox reports the finding as inconclusive. [See how evidence limits each claim](/docs/blackbox/overview/how-blackbox-works#let-evidence-limit-the-claim).

## See What Different Outcomes Did

Blackbox can also show which important code decisions the tests exercised and what the system did for each outcome. For example, one subscription branch may insert and charge, while another updates without charging.

**Alpha target:** [Observable Decision Coverage (ODC)](/docs/blackbox/concepts/omc-dc-coverage) compares those observable effect patterns after ordinary effect findings exist. It remains separate and cannot change an effect finding.
