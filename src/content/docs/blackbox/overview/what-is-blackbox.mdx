**Suites Blackbox is the deterministic behavioral verification layer in a coding-agent harness.**

It runs the declared system or E2E realization, manages a fresh evidence boundary, and compares human-approved behavior with the sealed runtime evidence. The resulting findings guide implementation repair without letting the coding agent redefine success.

Here, **deterministic** describes analysis: the same accepted meaning, declared realization, analysis policy, and sealed evidence produce the same finding. It does not mean a distributed application executes identically every time.

## Why does Blackbox Exist?

**Because verification becomes the new constraint**

Coding agents can generate implementations and tests faster than people can establish that the result is correct. When one agent derives both from the same interpretation, the code and test can share the same blind spot.

This creates a **verification bottleneck**:

- **More candidates:** Code is cheap to generate but expensive to verify.
- **Review queues grow:** Pull requests arrive faster than people can assess runtime behavior.
- **Green tests miss effects:** Expected responses can hide missing or forbidden work.

Harness engineering addresses that problem with **feedforward guidance** before the agent acts and **feedback** afterward. In Blackbox, approved Gherkin, effect claims, and analysis policy carry the guidance; deterministic findings from sealed runtime evidence provide feedback independent of the agent's judgment.

## Who Blackbox is For?

Blackbox is for teams that use coding agents such as Claude Code, Codex, and others to build or change behavior across real service boundaries.

- **System and E2E verification:** Check selected flows through the running system.
- **Deterministic repair findings:** Give coding agents findings they can act on without redefining success.
- **Bounded runtime evidence:** Base verdicts on captured behavior within a declared evidence boundary.

Teams can use the same accepted behavior in local repair loops and CI. [See how Blackbox becomes a CI gate](/docs/blackbox/guides/reports-and-ci-gates#add-the-runtime-gate).

## How does Blackbox work?

People decide what success means. A coding agent and its skills can propose, implement, diagnose, and repair. Blackbox executes the declared realization, manages the evidence boundary, and analyzes the result.

In the Alpha target flow, Gherkin expresses accepted behavior in a readable, reviewable form. The executable system suite realizes that behavior; Gherkin does not become runtime evidence or change effect findings.

[See how human intent, accepted meaning, realization, evidence, and findings keep separate authority](/docs/blackbox/concepts/specifications-flows-and-verdicts).

## Verify What the System Did

A system or E2E flow can pass on its visible result while required work is missing or forbidden work occurs. Blackbox verifies those **effects**, such as database writes, published messages, and external calls.

OpenTelemetry is one capture source. Blackbox correlates supported observations with the current attempt and normalizes eligible observations into effects before analysis. A span is evidence input, not automatically an effect. [See how observations become effects through the catalog](/docs/blackbox/concepts/effects-and-catalogs#from-observation-to-finding).

## Keep Assurance Bounded by the Evidence

Blackbox establishes claims about declared behavior inside a managed evidence boundary. It does not prove that the approved target expresses what people truly wanted, and it does not prove the entire application correct.

Evidence quality limits the verdict. If capture is incomplete, Blackbox cannot establish claims that depend on seeing everything: the absence of a forbidden effect, an upper bound, or exactness. Missing observations never become proof of success. [See how proof burdens differ for positive facts and absence](/docs/blackbox/concepts/effects-and-catalogs#positive-facts-and-absence-need-different-evidence).

Managed capture starts fresh for every case attempt, retry, and sequence member. That boundary prevents evidence from another execution from silently influencing the current finding. [See the attempt and evidence model](/docs/blackbox/concepts/runtime-evidence#bound-one-attempt-at-a-time).
