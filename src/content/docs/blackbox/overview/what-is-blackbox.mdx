**Suites Blackbox provides a verification layer for software developed with coding agents.**
It turns product intent into system tests and captures runtime telemetry as those tests run.

Where a traditional system test checks the visible output, Blackbox turns telemetry from databases, APIs, queues,
caches, and other system boundaries into evidence of the behavior behind that output. It then produces deterministic
findings.

Both product requests returned `200`, so the Playwright assertion was correct. Blackbox also found two Postgres reads where the approved behavior allowed at most one. The agent repaired Redis use and verified the same behavior again with fresh evidence.

- **For people:** The result shows whether the running system matched the behavior they approved.
- **For coding agents:** The finding identifies a bounded repair problem without letting the agent change the target.

## From Product Intent to a System Test

A coding agent can propose reviewed Gherkin or direct behavioral declarations. A person approves the behavior, then Blackbox maps that accepted intent into a Playwright realization without deriving new requirements from the test or traces.

## Why Blackbox?

Coding agents can produce implementations and tests faster than people can review runtime behavior. Pull requests accumulate, and a green test can share the same blind spot as the code it checks.

Harness engineering surrounds an agent with guidance before it acts and feedback after it acts. Blackbox supplies deterministic behavioral feedback from the running system, so repair can move quickly while people retain authority over success.

## Use Blackbox When

- Your team runs system or E2E tests across real service boundaries.
- Coding agents such as Claude Code or Codex implement and repair product behavior.
- A passing response can hide important database, HTTP, cache, or messaging work.

## Verify Runtime Effects

**Effects** are portable facts Blackbox derives from eligible runtime observations. They let a case require, forbid, order, compare, or limit system work beyond its visible result.

Findings stay bounded by the evidence. Incomplete evidence cannot establish absence, an upper bound, or an exact count. [See how OpenTelemetry observations become effects](/docs/blackbox/concepts/effects-and-catalogs).

Optional [Observable Decision Coverage](/docs/blackbox/concepts/omc-dc-coverage) can also compare which code outcomes ran with the effect pattern produced by each outcome. It remains separate from ordinary effect findings.
