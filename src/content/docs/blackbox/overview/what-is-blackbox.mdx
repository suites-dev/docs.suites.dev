**Suites Blackbox runs system flows, observes what the software actually did, and returns deterministic verdicts coding agents can act on.**

Blackbox combines **coding-agent skills**, a **deterministic CLI**, and **human review** in one verification lifecycle.

<HumanAgentVerificationLoopDiagram />

Blackbox closes the deterministic feedback loop between coding agents and running software while people remain in control at the beginning and end. This is what **behavioral verification framework for agentic software engineering** means in practice.

Five capabilities make the loop work:

- **Human review controls what counts as success.** People approve the behavior and effect contract, then accept the result or return it to the agent.
- **Blackbox agent skills translate intent.** They propose requirements and scenarios and guide the agent through implementation and repair.
- **The Blackbox CLI keeps verification deterministic.** It validates and aligns artifacts, executes flows, captures evidence, and computes verdicts.
- **[Runtime effects](/docs/blackbox/concepts/effects-and-catalogs) show what happened inside the system.** For supported Node services, Blackbox [automatically injects test-time OpenTelemetry instrumentation](/docs/blackbox/concepts/runtime-evidence), then checks that expected database writes, API calls, and messages happened and unwanted ones did not.
- **[Observable decision coverage](/docs/blackbox/concepts/omc-dc-coverage) shows whether important decisions changed what the system did.** Blackbox checks that different decision outcomes leave different runtime evidence.

The agent can repeat the inner loop without waiting for a person after every change. It must stop when passing would require changing what success means.

## Catch Green Tests That Miss the Behavior

An agent can implement and test the same mistaken interpretation. The test passes because the code and assertion agree with each other.

Blackbox adds an independent observation channel. For a rejected subscription, a Playwright flow can check the response and the effects behind it:

```ts
expect(response.status()).toBe(404);

await expect(capture).toObserveEffects({
  requires: [effect.postgres("SELECT", { table: "users" })],
  forbids: [
    effect.http("POST", { path: "/v1/payment_intents" }),
    effect.postgres("INSERT", { table: "subscriptions" }),
    effect.sqs("SendMessage", { queue: "subscription-orders" }),
  ],
});
```

- The assertion proves the caller received `404`.
- Runtime evidence proves the user lookup occurred during this run.
- The accepted effect contract forbids payment, persistence, and publication.

A green assertion with a failed effect verdict means the visible result was correct while the accepted boundary behavior was not.

## Keep Success Outside the Agent

Agents can change implementation. They cannot change accepted requirements, scenarios, suite assertions, effect contracts, or captured boundaries to make a failure disappear.

When one of those must change, Blackbox returns the work to human review instead of keeping it inside the autonomous loop.

## Start From What You Have

Blackbox does not require a particular specification framework or test runner. Start with the surface that already carries useful behavior:

- **Existing suite:** Recover readable behavior and align the accepted native flow.
- **New behavior:** Connect approved requirements and examples to a native flow.
- **Accepted flow:** Add runtime observation and a required-or-forbidden effect contract.

EARS requirements and Gherkin are optional. Specifications guide the agent; Blackbox verifies what the running system actually did.

<Aside type="note" title="Start Before Runtime">
  Without Docker or instrumentation, Blackbox can validate artifacts and align a
  native suite deterministically. That is useful governance, but it does not
  verify what the running system did.
</Aside>

Blackbox keeps test, feature, effect, requirement, and observable-decision verdicts separate. Missing evidence remains explicit instead of becoming confidence.
