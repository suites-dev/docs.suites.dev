**Suites Blackbox is a behavioral verification framework for software developed with coding agents.**

People approve what success means. Blackbox runs real system flows, captures and seals evidence of what the software did, and returns deterministic findings an agent can repair against without redefining the accepted target.

System and E2E tests provide the execution boundary. They are how Blackbox reaches the running software, not the whole product.

Blackbox connects accepted behavior, native execution, sealed runtime evidence, and deterministic analysis. [See how one flow moves through the complete system](/docs/blackbox/overview/how-blackbox-works).

## Catch Green Tests That Miss the Behavior

Suppose an unknown user receives the expected `404`, but the implementation also calls a payment API. The response assertion remains green because it cannot see that hidden **effect**—a meaningful runtime action performed by the application.

Keep the native assertion:

```ts title="e2e/subscribe-user.system.test.ts"
expect(response.status()).toBe(404);
```

Then approve the boundary behavior independently:

```yaml title="e2e/features/subscribe-user.effects.yaml"
specVersion: "0.1"
flow: subscribe-user

requires:
  - { boundary: postgres, op: SELECT, key: users, service: api }

forbids:
  - { boundary: http, op: POST, key: /v1/payment_intents, service: api }
```

Blackbox keeps the results separate:

```text
tests       PASS
integrity   PASS
effects     FAIL   forbidden payment call observed
ODC         REPORT opposite branch outcomes produced distinct effects
```

A green assertion with a failed effect verdict means the visible result was correct while the accepted boundary behavior was not. **[Observable decision coverage (ODC)](/docs/blackbox/concepts/omc-dc-coverage)** compares the effects produced by different code-decision outcomes; here it compares the unknown-user attempt with the known-user attempt.

## Keep Authority and Verification Separate

| Participant                              | Responsibility                                                                 |
| ---------------------------------------- | ------------------------------------------------------------------------------ |
| **People**                               | Approve the target, analysis policy, and final result.                         |
| **Coding agents and Blackbox skills**    | Propose artifacts, implement behavior, and repair findings.                    |
| **Blackbox CLI, runtime, and analyzers** | Execute flows, correlate and seal evidence, and compute deterministic results. |

The agent can repeat the implementation loop without waiting for a person after every change. It must stop when passing would require changing accepted requirements, scenarios, assertions, effect contracts, or verification policy.

<Aside type="note" title="Negative Claims Need Isolated State">
  The system under test (SUT) is the application and services being verified. A
  forbidden effect is conclusive only when the SUT and its mutable dependencies
  are isolated or reset for the attempt. Blackbox manages this boundary for
  owned lifecycles; external systems must provide an equivalent isolation
  guarantee.
</Aside>

## Start From What You Have

Blackbox does not require a particular specification framework or test runner. Start with the surface that already carries useful behavior:

- **Existing suite:** Recover readable behavior and align the accepted native flow.
- **New behavior:** Connect approved requirements and examples to a native flow.
- **Accepted flow:** Add runtime observation and a required-or-forbidden effect contract.

EARS requirements and Gherkin are optional. Specifications guide the agent; Blackbox verifies what the running system actually did.

<Aside type="note" title="Start Before Runtime">
  Without starting or attaching capture to the SUT, Blackbox can validate
  requirements, features, flow identities, and suite alignment. Those checks
  prove structural agreement, not runtime behavior.
</Aside>

Blackbox keeps test, feature, effect, requirement, and observable-decision verdicts separate. Missing evidence remains explicit instead of becoming confidence.

## Start With One Consequential Flow

Choose one system or E2E flow where wrong behavior would matter. First [understand how Blackbox runs and analyzes that flow](/docs/blackbox/overview/how-blackbox-works), then [build the complete loop in the Quickstart](/docs/blackbox/quickstart/).

If your starting point differs from the golden path:

- **Already have a passing system or E2E test:** Keep it and [give one flow a stable identity](/docs/blackbox/quickstart/build-behavioral-harness).
- **No system or E2E test yet:** Start with [one behavior in plain language and create the system flow](/docs/blackbox/guides/turn-requirements-into-system-test), then join the Quickstart.
- **Different SUT setup:** Build the harness first, then [choose how Blackbox starts or connects to your SUT](/docs/blackbox/guides/set-up-the-testbed).
