**Suites Blackbox turns Playwright system and E2E tests into behavioral verification gates.** It observes the running system's boundary effects and checks them against reviewed required and forbidden expectations, so a passing response is no longer the only proof behind a change.

<OpeningProofClip />

Your Playwright test still drives the workflow and checks its visible result. Blackbox adds evidence for what happened behind that result: database operations, cache access, outgoing HTTP calls, queue messages, and other supported boundary effects.

## The Problem It Solves

An assertion such as `expect(response.status()).toBe(404)` proves that the system rejected a request. It does not prove that the rejected request stopped before payment, persistence, and publication.

That distinction matters for behavior such as `subscribe-unknown-user`:

```ts
await expect(capture).toObserveEffects({
  requires: [effect.postgres("SELECT", { table: "users" })],
  forbids: [
    effect.http("POST", { path: "/v1/payment_intents" }),
    effect.postgres("INSERT"),
    effect.sqs("SendMessage", { queue: "subscription-orders" }),
  ],
});
```

The response assertion and the effect assertion answer different questions:

| Evidence                        | Question                                    |
| ------------------------------- | ------------------------------------------- |
| Playwright assertion            | Did the caller receive the expected result? |
| Runtime effects                 | What did the running topology actually do?  |
| Required and forbidden contract | Was the observed behavior acceptable?       |
| Coverage and verdicts           | Which reviewed behavior did this run prove? |

Blackbox does not replace the test runner or the test. It strengthens the test's conclusion.

## The Core Model

Blackbox uses five main objects:

1. A **flow** gives one system behavior a stable identity, such as `subscribe-flow`.
2. A **capture** contains runtime observations collected for that flow.
3. An **effect** is a normalized boundary operation, such as a Postgres `INSERT` or SQS `SendMessage`.
4. A **catalog** records reviewed required and forbidden effects for each flow.
5. A **report** explains whether the run satisfied, missed, or violated the contract.

<OverviewDiagram kind="workflow" />

The first run can record a catalog candidate. A reviewer decides which effects are contractual and which are incidental. Later runs compare fresh evidence with that reviewed catalog. New, missing, or forbidden behavior becomes a visible decision instead of a hidden implementation detail.

## Specifications Are Complementary

Runtime effects are the core capability. You can use them without adopting a specification format.

When a team wants to connect intent to evidence, Blackbox supports two complementary surfaces:

- **EARS requirements** use an optional constrained requirement syntax to give normative rules stable IDs. Bindings connect those IDs to flow IDs, and requirement coverage joins them with runtime results to produce `proven`, `violated`, `unproven`, or `unbound` verdicts.
- **Gherkin feature files** provide a readable behavior projection. Blackbox can emit them from executable Playwright or Blackbox BDD-DSL tests and detect drift. Feature files do not replace runtime proof.

EARS answers, "Which requirement does this flow verify?" Gherkin answers, "How can a person read the executable behavior?" Effects answer, "What did the running system actually do?"

OMC/DC sits one layer later. It uses the same captured evidence to ask whether important code decisions produced distinguishable boundary behavior.

## Why It Matters Now

The need predates coding agents: legacy refactors, service migrations, incident regressions, and distributed workflows have always needed stronger system-level evidence.

Agentic development raises the stakes because implementation and test code can change faster than a reviewer can reconstruct behavior from a diff. Blackbox produces evidence that both humans and automation can inspect, while keeping changes to reviewed intent under human control.

That makes the merge question more precise: not only "Did the tests pass?" but "Did the running system produce the required effects, avoid the forbidden effects, and prove the requirements attached to this flow?"

## Start With One Flow

Blackbox is most useful when the first contract is narrow and consequential. Choose a stable system flow, capture its effects, review one catalog entry, and rerun it.
