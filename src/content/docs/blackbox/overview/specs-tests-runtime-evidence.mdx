A specification can be clear and a Playwright test can pass while important boundary behavior remains unverified. The missing piece is evidence from the running system.

<OverviewDiagram kind="blind-spot" />

## Input and Output Are Not the Whole Behavior

Most E2E assertions observe the outside of a workflow:

```ts
const response = await request.post("/subscriptions", { data });
expect(response.status()).toBe(201);
expect(await response.json()).toMatchObject({ tier: "pro" });
```

Those assertions matter. They prove the public result. They do not necessarily prove that the system persisted the subscription, cached the tier, called the intended payment endpoint, published the order exactly once, or avoided a refund path.

<InputOutputGapDiagram />

Blackbox collects observations from the SUT during each isolated flow and makes those boundary effects inspectable. The test remains green only when both its ordinary assertions and its reviewed behavior contract are satisfied.

## Written Intent Can Drift Too

Specifications help humans and agents decide what to build. Their weakness is temporal: after implementation, a requirement, ticket, plan, or feature file can stop describing the system that actually runs.

Tests can drift in a different way. A test may continue checking the same `201` response after a refactor changes a queue, database, or vendor interaction that the assertion never named.

| Surface                       | Strength                                          | Blind spot                                           |
| ----------------------------- | ------------------------------------------------- | ---------------------------------------------------- |
| Requirement or product spec   | Explains intended behavior                        | Can become stale and is not executable proof         |
| Playwright system or E2E test | Exercises the running workflow                    | May assert only selected inputs and outputs          |
| Runtime evidence              | Records boundary behavior from the run            | Facts still need reviewed meaning                    |
| Effect catalog                | Declares required and forbidden effects           | Must be ratified when behavior legitimately changes  |
| EARS binding and verdict      | Connects a normative requirement to runtime proof | Only proves requirements with bound, executed flows  |
| Generated Gherkin             | Makes executable behavior readable                | Reflects its source test; it is not runtime evidence |

No single surface should pretend to answer all six jobs.

## Independent Evidence, Not Circular Confidence

In an agentic change, the same agent may read the requirement, write the implementation, and add a test. That accelerates delivery, but it can also make the validation circular: generated code is accepted by generated assertions that share the same mistaken interpretation.

Blackbox adds an independently observed input to the decision. The report is derived from what the instrumented system did during the flow, not from the implementation summary or the test name.

This does not make the evidence self-interpreting. A human still decides which effects are required, forbidden, incidental, or ambiguous. The useful division of labor is:

1. Humans ratify intent and behavior changes.
2. Playwright drives the workflow.
3. Blackbox records and classifies runtime facts.
4. CI and agents consume deterministic results.
5. Ambiguous or new behavior returns to review.

<Aside type="note" title="A Catalog Is Reviewed Intent">
  The first capture can reveal candidate effects, but observed behavior is not
  automatically correct behavior. Review catalog changes with the same care as
  an API or schema change.
</Aside>

## The Gap in Existing E2E Methodology

Traditional E2E testing is often described as a user journey through a deployed environment. That is useful for proving that a full path works, including unmanaged dependencies such as identity providers, email systems, or external vendors.

Blackbox is strongest first in a controlled **system test**, where the run owns the SUT and managed dependencies. The controlled topology makes missing and forbidden effects deterministic enough to gate a pull request. The same evidence model can support broader E2E flows, but shared and unmanaged dependencies introduce noise that must be accounted for.

The category is therefore not "another assertion library." It is a runtime-evidence layer for system and E2E verification.

## Close the Gap

The verification chain becomes:

```text
intent -> executable flow -> runtime effects -> reviewed contract -> verdict
```

Optional EARS requirements bind normative intent to the flow. Optional Gherkin files project executable behavior into a readable format. Neither is required to start capturing and checking effects.
