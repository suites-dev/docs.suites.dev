Blackbox verifies behavior at the **system** and **end-to-end (E2E)** layers. It complements unit and integration tests instead of replacing them.

<TestingPyramidDiagram />

## Choose the Layer by the Question

| Layer       | Main question                                                        | Typical scope                                    |
| ----------- | -------------------------------------------------------------------- | ------------------------------------------------ |
| Unit        | Does local logic behave correctly?                                   | One unit with collaborators replaced             |
| Integration | Do selected components or adapters collaborate correctly?            | A small set of real components                   |
| System      | Does the composed system behave correctly through a public boundary? | The SUT and controlled infrastructure            |
| E2E         | Does the deployed user journey work?                                 | The full system, including external dependencies |

Use lower layers for fast diagnosis. Use Blackbox when correctness depends on what a composed, running system does across database, HTTP, queue, cache, and other boundaries.

## What Blackbox Adds

A typical system test proves that an input produced an expected output. Blackbox also checks the behavior between them:

- Did every required effect occur?
- Did a forbidden effect occur?
- Could Blackbox determine whether an effect matched?
- Did exercised decisions remain observable at a boundary?

These verdicts come from captured runtime evidence, not from source-code inspection or an agent's explanation.

## Control Determines Confidence

A **capture cell** is the isolated runtime boundary that contains the sidecar, system under test, and required infrastructure. The configured isolation scope determines how much state a flow shares:

| Scope    | Use it when                                                            |
| -------- | ---------------------------------------------------------------------- |
| `flow`   | Each behavioral flow needs its own isolated cell. This is the default. |
| `worker` | A runner worker can safely share one cell across several flows.        |
| `test`   | Each individual test needs a fresh cell.                               |

Remote or shared dependencies can still participate in an E2E flow. Their results carry less deterministic confidence when Blackbox cannot control or reset their state.

## Runners and Languages Stay Independent

The test runner starts and ends the lifecycle. A language-specific capture implementation observes the SUT. Neither choice defines the other.

Playwright and Node are the first implementations. The architecture also supports other runner adapters and capture implementations without changing the sealed evidence format or analysis model.

## Suites Unit and Suites Blackbox

| Need                                          | Suites Unit | Suites Blackbox |
| --------------------------------------------- | ----------- | --------------- |
| Isolate a class or provider                   | Yes         | No              |
| Generate type-safe mocks and stubs            | Yes         | No              |
| Diagnose local logic quickly                  | Yes         | No              |
| Drive a composed system or E2E flow           | No          | Yes             |
| Verify required and forbidden runtime effects | No          | Yes             |
| Report observable decision coverage           | No          | Yes             |

Keep local correctness cheap. Add Blackbox where a running system must provide evidence of its behavior.
