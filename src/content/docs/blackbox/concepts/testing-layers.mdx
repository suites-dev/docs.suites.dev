Testing layers trade speed and failure locality for realism. Blackbox belongs where a running, composed system crosses boundaries whose behavior matters.

## Four Different Questions

| Layer       | Main question                                                       | Typical dependency shape                                      |
| ----------- | ------------------------------------------------------------------- | ------------------------------------------------------------- |
| Unit        | Does local logic behave correctly?                                  | Collaborators replaced with doubles                           |
| Integration | Do selected components or adapters collaborate correctly?           | A small number of real providers or infrastructure components |
| System      | Does the composed SUT behave correctly through its public boundary? | Topology and dependencies owned by the test                   |
| E2E         | Does the full deployed journey work?                                | May include shared, remote, or third-party dependencies       |

Use lower layers for fast feedback and precise diagnosis. Use system and E2E tests for behavior that only exists after services, stores, caches, queues, and remote calls are composed.

## Managed and Unmanaged Dependencies

A **managed dependency** is started, configured, reset, and cleaned up by the test environment. Examples include a Postgres container, Redis container, LocalStack queue, or payment stub in a per-worker Compose stack.

An **unmanaged dependency** is outside the run's control: a shared identity provider, a remote email service, a staging database, or a vendor endpoint.

The distinction affects confidence:

- controlled state makes missing and forbidden effects reproducible;
- per-worker stacks keep parallel flows isolated;
- shared dependencies add realism but can make failures environmental;
- remote side effects may be observable without being safely resettable.

## The Blackbox Sweet Spot

Blackbox is strongest around **controlled system tests**. Playwright drives a real public boundary while the testbed owns the SUT topology and managed dependencies. Runtime observations can then become deterministic catalog and coverage results.

The same model can support broader E2E tests. Treat those results according to the control you actually have. A remote vendor timeout and a missing queue publication in an isolated testbed do not carry the same diagnostic meaning.

## What Blackbox Adds

At the system and E2E layers, a test usually checks input and output. Blackbox adds four questions about the middle:

1. Which required boundary effects appeared?
2. Which required effects were missing?
3. Which forbidden effects appeared?
4. Which cataloged flows or effect shapes were not exercised?

OMC/DC adds a fifth, advanced question: did important decisions produce distinguishable observed behavior?

## Suites Unit and Suites Blackbox

Suites Unit and Suites Blackbox cover different confidence surfaces.

| Need                                           | Suites Unit | Suites Blackbox |
| ---------------------------------------------- | ----------- | --------------- |
| Isolate a TypeScript class or provider         | Yes         | No              |
| Generate type-safe mocks and stubs             | Yes         | No              |
| Diagnose local logic quickly                   | Yes         | No              |
| Drive a Playwright system or E2E flow          | No          | Yes             |
| Check required and forbidden runtime effects   | No          | Yes             |
| Produce system-level effect and OMC/DC reports | No          | Yes             |

The pyramid still matters. Keep local correctness cheap. Add Blackbox where composed behavior needs evidence from a real run.
