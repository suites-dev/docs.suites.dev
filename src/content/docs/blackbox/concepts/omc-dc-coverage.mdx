Observable decision coverage compares the runtime evidence produced by tests exercising each arm of a binary decision. It shows whether the arm evidence is distinguishable, indistinguishable, or incomplete.

> **Current support boundary:** Blackbox compares decision arms. It does not yet prove that every atomic condition inside a compound expression independently changes the decision outcome. The current implementation is observable decision coverage, not full observable MC/DC.

## From Branch Execution to Runtime Evidence

Consider a subscription endpoint with an early decision:

```ts
if (!user) {
  return reply.status(404).send({ error: "User not found" });
}

await createSubscription(user);
```

Ordinary branch coverage can show that tests ran both arms. Blackbox asks an additional question: did tests exercising those arms produce distinguishable captured runtime evidence?

Different evidence supports a `propagating` verdict. Indistinguishable evidence produces a `masking-candidate`: both arms ran, but this run did not reveal a meaningful distinction in their captured span signatures.

This is stronger evidence than knowing that both arms executed. It is not a causal proof that the decision alone produced every difference. Blackbox compares the full captured evidence attached to tests in each arm bucket; other behavior in those tests can also affect their signatures.

## What Blackbox Computes

For each endpoint represented in the run, the Node coverage producer:

1. Converts per-test V8 coverage into Istanbul branch maps and arm counters.
2. Groups tests that exercised the true and false arms of each binary decision.
3. Builds a canonical, multiplicity-preserving span signature for each arm bucket.
4. Compares the two signatures and emits a verdict.

A test can belong to both arm buckets when it exercises a decision both ways, such as through a loop or repeated call.

The signature can include canonical HTTP, database, and messaging spans. File-scoped internal function spans and otherwise untyped spans can also contribute. Blackbox deliberately compares stable span shapes rather than complete payload values, so two writes with the same operation and table but different values may collapse to the same shape.

## Observable Decision Coverage Is Not Effect Coverage

These reports answer different questions:

| Coverage view                | Question                                                                                | Inputs                                          |
| ---------------------------- | --------------------------------------------------------------------------------------- | ----------------------------------------------- |
| Catalog coverage             | Did the run satisfy the reviewed required and forbidden effects?                        | Catalog entries, matchers, and observed effects |
| Shape coverage               | Which catalog clauses participated in assertions?                                       | Catalog shapes and matcher results              |
| Observable decision coverage | Did tests exercising different decision arms produce distinguishable captured evidence? | Per-test spans and per-test branch-arm coverage |

The decision-coverage engine does not read effect-contract requirements or matcher results. Changing an effect contract does not strengthen a decision verdict. Better-discriminating scenarios or richer instrumentation can change the evidence it compares.

## Read the Verdicts

Verdicts describe the evidence available from the current run. They are not additional test pass or fail statuses, and they do not all indicate defects.

| Verdict             | What the engine observed                                                    | Typical next action                                                                            |
| ------------------- | --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `propagating`       | Both arms were exercised and their canonical span signatures differed.      | Inspect the differing evidence when the decision matters to review.                            |
| `masking-candidate` | Both arms were exercised and observed, but their signatures were identical. | Decide whether the equality is intentional; otherwise improve the scenario or instrumentation. |
| `coverage-gap`      | Exactly one arm was exercised.                                              | Add a case for the missing arm when the decision matters.                                      |
| `undecidable`       | The available observations do not support a sound comparison.               | Check run completeness, captured spans, and instrumentation.                                   |
| `multi-arm`         | The branch has more than two arms.                                          | Review it manually; per-arm-pair comparison is not implemented.                                |
| `unsupported-mcdc`  | Reserved for future condition analysis involving side-effecting operands.   | Do not expect the current comparator to emit this verdict yet.                                 |

There is no current `unobservable` verdict. Blackbox does not statically prove that no path exists from a decision to an observed effect.

## Why This Is Not Full MC/DC Yet

Modified Condition/Decision Coverage requires evidence that every atomic condition can independently affect its enclosing decision. For example:

```ts
if (authenticated && subscribed && !suspended) {
  enableFeature();
}
```

Full MC/DC must construct suitable execution pairs for `authenticated`, `subscribed`, and `suspended`, holding the other conditions fixed according to the selected MC/DC policy. Blackbox does not currently construct those condition-independence pairs.

Today, the engine works from Istanbul decision and branch-arm counters. Logical expressions can expose operand coverage, but condition independence is not computed. Decisions with more than two arms receive `multi-arm` rather than a condition-level verdict.

The package and report paths retain the `omcdc` name. Read that as the current artifact namespace and the direction of the analysis, not as a claim that full observable MC/DC is implemented.

## Read the Report

Start with the test result and effect reports. Open decision coverage when the review question concerns masking, missing decision arms, or whether different paths left distinguishable evidence.

1. Open `catalog/coverage.json` for required and forbidden effect results.
2. Open `shape/coverage.json` to see which catalog clauses were asserted.
3. Open `omcdc/verdict.md` for endpoint summaries, branch rows, verdict counts, and hints.
4. Open `omcdc/verdict.html` for interactive branch inspection and source snippets when available.
5. Use `omcdc/verdict.json` for automation and agent workflows.

For the subscription example, compare the rows reached by `subscribe-flow` and `subscribe-unknown-user`. The useful result is not merely that `/subscriptions` returned two different responses. It is that tests exercising the two arms left distinguishable runtime evidence.

## Current Limits

- The engine analyzes decisions exercised by the captured tests. It does not establish a complete denominator for unrun inputs or unexecuted code.
- Arm signatures are correlational evidence from test buckets, not decision-to-effect data-flow proofs.
- Canonical signatures preserve span shapes and counts but omit many payload values.
- Multi-arm decisions do not receive per-arm-pair analysis.
- `unsupported-mcdc` is reserved; the side-effecting-operand detector is not implemented.
- Detached asynchronous work can escape attribution when trace context is lost.
- Coverage currently targets JavaScript executing in supported Node SUTs, not native addons or other languages.

Blackbox supports Playwright parallelism through isolated per-worker SUT stacks. Each worker receives its own topology, so V8 counters and captured evidence do not mix. Concurrent tests sharing one SUT process cannot be separated reliably because V8 coverage counters are process-wide.
