Runtime evidence is the captured record of what the SUT did while one Playwright flow ran. It is a fact base for that run, not a claim that every behavior in the system was visible.

<InputOutputGapDiagram />

## Evidence Has a Scope

Blackbox associates observations with a stable flow ID and a per-test capture window. The standard testbed gives each Playwright worker its own SUT stack, clears observation buffers before a test, and drains them after the test. Supported boundary spans in that window become effects.

This scope matters. Without an isolated stack and capture boundary, background traffic or another worker's request could be mistaken for the behavior under test.

The standard testbed supports Playwright parallelism by provisioning an isolated SUT stack per worker. Tests inside a worker run in order and reuse that stack, while reset hooks and buffer boundaries separate individual flows.

The wrapped Playwright `request` fixture also propagates trace context so calls remain connected across services. For a raw HTTP client, use the Blackbox `traceparent()` helper when distributed trace relationships or trace-filtered `captureAcross()` calls matter.

## From Span to Effect

OpenTelemetry spans are the input. Catalog effects are the review vocabulary.

<Tabs groupId="evidence-normalization">
<TabItem value="span" label="Simplified span" default>

```json
{
  "name": "INSERT subscriptions",
  "attributes": {
    "db.system": "postgresql",
    "db.operation.name": "INSERT",
    "db.collection.name": "subscriptions",
    "service.name": "bff"
  }
}
```

</TabItem>
<TabItem value="effect" label="Normalized effect">

```yaml
boundary: postgres
op: INSERT
key: subscriptions
service: bff
```

</TabItem>
</Tabs>

Normalization removes trace-vendor detail that does not belong in a behavior contract. Matchers can still refine effects with keys, service names, status, TTL, bucket, routing key, or count constraints where the boundary supports them.

## Supported Boundary Vocabulary

The public `effect.*` builders currently cover:

- Postgres
- Redis
- outgoing HTTP
- SQS
- S3
- RabbitMQ

The catalog can only prove what the instrumentation and classifier observe. If an application writes through an unsupported driver, starts work in a detached context, or reaches a non-instrumented service, absence from the capture is not proof that the action never happened.

<Aside type="warning" title="Absence Is Relative to Observation">
  A forbidden effect is meaningful only when the relevant boundary is observable
  in the test environment. Prove the evidence path before relying on a negative
  contract.
</Aside>

## Evidence Is Not Intent

The first capture describes the implementation as it exists, including accidental behavior. It should not become an accepted baseline automatically.

The review step separates:

- **required effects**, whose absence would make the flow incorrect;
- **forbidden effects**, whose presence would make the flow incorrect;
- **incidental observations**, which may help diagnostics but should not become contract clauses.

Written specifications have the opposite limitation: they express intent but do not prove execution. Blackbox keeps the two surfaces separate and joins them through explicit flow IDs and reviewed bindings.

## Raw Evidence and Derived Artifacts

One run may produce several layers:

| Layer                      | Example                                | Purpose                                 |
| -------------------------- | -------------------------------------- | --------------------------------------- |
| Raw observation            | captured span JSON                     | Diagnose what was captured              |
| Normalized effect          | `postgres INSERT subscriptions`        | Compare behavior in stable vocabulary   |
| Effect catalog             | `requires` and `forbids` per flow      | Store reviewed intent                   |
| Catalog and shape coverage | satisfied, failed, uncovered, asserted | Report what the suite proved            |
| Observable decision report | propagating, masking candidate, gap    | Evaluate decision-sensitive evidence    |
| Requirement coverage       | proven, violated, unproven, unbound    | Join EARS bindings with runtime results |

Raw traces are usually build evidence. Catalogs, requirements, bindings, and intentionally reviewed feature files are repository artifacts. See [Reference](/docs/blackbox/reference) for retention and schemas.
