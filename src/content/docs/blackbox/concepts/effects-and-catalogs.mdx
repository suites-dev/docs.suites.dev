An **effect** is normalized boundary behavior from a running flow. An **effect contract** records which effects are required or forbidden. **Coverage** says whether the suite exercised and satisfied that reviewed contract.

<OverviewDiagram kind="coverage" />

## One Flow, One Contract

The effect contract sits beside the feature file and names one flow:

```yaml
specVersion: "0.1"
flow: subscribe-unknown-user
requires:
  - { boundary: postgres, op: SELECT, key: users, service: bff }
forbids:
  - { boundary: http, op: POST, key: /v1/payment_intents, service: bff }
  - { boundary: postgres, op: INSERT, service: bff }
  - { boundary: sqs, op: SendMessage, key: subscription-orders }
```

`requires` describes behavior that must be observed. `forbids` describes behavior that must be absent from the capture.

The unknown-user contract is stronger than a `404` assertion. It proves that the system looked up the user and did not continue into payment, subscription persistence, or queue publication.

## Recording Is Not Approval

`blackbox verify` writes runtime evidence, normalized observed effects, and reports. The first run can report `effects: not-configured`; it does not silently convert observations into an accepted effect contract.

Inspect the generated facts before proposing policy:

```bash
blackbox effects show --flow subscribe-unknown-user --run latest --json
```

Review a proposed contract before committing it. Remove incidental observations, make important clauses specific, and add forbids for dangerous behavior.

<Aside type="warning" title="A Baseline Can Preserve a Bug">
  The runtime knows what happened, not what should have happened. Effect-policy
  changes need human or designated reviewer approval.
</Aside>

## Inline and Catalog Matchers

Use inline effects when the contract belongs directly in the test:

```ts
await expect(capture).toObserveEffects({
  requires: [effect.postgres("INSERT", { table: "subscriptions" })],
  forbids: [effect.http("POST", { path: "/v1/refunds" })],
});
```

Or use the effect contract selected by the active flow ID:

```ts
await expect(capture).toMatchCatalog();
```

`toObserveEffects()` and `toMatchCatalog()` use the same evaluation kernel. Inline shapes are useful for focused assertions. Effect contracts are useful when the contract should remain a standalone review artifact.

## Three Coverage Views

Blackbox separates three related questions.

### Effect Coverage

`catalog/coverage.json` reports one state per effect contract:

- `satisfied`: at least one run passed the entry contract;
- `failed`: the entry ran but no run satisfied it;
- `uncovered`: the effect contract was not captured and checked in this run.

```json
{
  "catalog": {
    "service": "unknown",
    "entryCount": 1,
    "apiVersion": "effect-catalog/v0.2"
  },
  "totals": {
    "seen": 1,
    "satisfied": 1,
    "failed": 0,
    "uncovered": 0,
    "forbidden": 0
  },
  "perEntry": [
    {
      "id": "subscribe-unknown-user",
      "state": "satisfied",
      "runs": 1,
      "passes": 1,
      "failures": 0,
      "forbidViolations": []
    }
  ]
}
```

### Effect-Shape Coverage

`shape/coverage.json` asks whether individual contract clauses were asserted at least once. Its summary distinguishes contract shapes that were asserted, unasserted shapes, and inline-only shapes used by `toObserveEffects()` but not stored in a contract.

This is the closest Blackbox equivalent to "which reviewed effects are covered?" A contract can exist while one of its shapes never participates in an assertion path the suite ran.

### Observable Decision Coverage

Observable decision coverage is an enriched decision view. It joins branch-arm execution with captured span signatures to ask whether tests exercising different arms produced distinguishable evidence. It does not consume effect matchers, and it does not replace effect or shape coverage. The current engine does not compute the atomic-condition independence required for full OMC/DC.

## New and Missing Behavior

A later run can reveal:

- a missing required clause;
- a forbidden match;
- a new observed effect not represented in the accepted contract;
- an uncovered entry or shape.

The correct response is not always "update the contract." Repair the implementation when the contract is still right. Change the contract only when the behavior change is intentional and reviewed.
