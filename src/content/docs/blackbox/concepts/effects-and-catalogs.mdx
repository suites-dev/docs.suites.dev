An **effect** is normalized boundary behavior from a running flow. A **catalog** records which effects are required or forbidden. **Coverage** says whether the suite exercised and satisfied that reviewed contract.

<OverviewDiagram kind="coverage" />

## One Flow, One Contract

The effect sidecar follows the Playwright test file and stores entries by flow ID:

```yaml
specVersion: "0.1"
entries:
  subscribe-unknown-user:
    requires:
      - { boundary: postgres, op: SELECT, key: users, service: bff }
    forbids:
      - { boundary: http, op: POST, key: /v1/payment_intents, service: bff }
      - { boundary: postgres, op: INSERT, service: bff }
      - { boundary: sqs, op: SendMessage, key: subscription-orders }
```

`requires` describes behavior that must be observed. `forbids` describes behavior that must be absent from the capture.

The unknown-user contract is stronger than a `404` assertion. It proves that the system looked up the user and did not continue into payment, subscription persistence, or queue publication.

## Recording Is Not Approval

When a successful flow has no catalog entry, the default local update mode records a baseline at fixture teardown. Existing entries are not silently replaced. Playwright's snapshot update mode controls catalog writes:

- default/missing mode adds previously unseen flow IDs;
- `--update-snapshots` refreshes changed requirements while keeping forbids sticky;
- strict CI with `updateSnapshots: 'none'` refuses to baseline missing entries.

Review a new entry before committing it. Remove incidental observations, make important clauses specific, and add forbids for dangerous behavior.

<Aside type="warning" title="A Baseline Can Preserve a Bug">
  The recorder knows what happened, not what should have happened. Catalog
  changes need human or designated reviewer ratification.
</Aside>

## Inline and Catalog Matchers

Use inline effects when the contract belongs directly in the test:

```ts
await expect(capture).toObserveEffects({
  requires: [effect.postgres("INSERT", { table: "subscriptions" })],
  forbids: [effect.http("POST", { path: "/v1/refunds" })],
});
```

Or use the catalog entry selected by the active flow ID:

```ts
await expect(capture).toMatchCatalog();
```

`toObserveEffects()` and `toMatchCatalog()` use the same evaluation kernel. Inline shapes are useful for focused assertions. Catalogs are useful when the contract should remain a standalone review artifact.

## Three Coverage Views

Blackbox separates three related questions.

### Catalog Coverage

`catalog/coverage.json` reports one state per catalog entry:

- `satisfied`: at least one run passed the entry contract;
- `failed`: the entry ran but no run satisfied it;
- `uncovered`: the catalog entry was not captured and checked in this run.

```json
{
  "catalog": {
    "service": "unknown",
    "entryCount": 1,
    "apiVersion": "effect-catalog/v0.2"
  },
  "totals": {
    "seen": 1,
    "satisfied": 1,
    "failed": 0,
    "uncovered": 0,
    "forbidden": 0
  },
  "perEntry": [
    {
      "id": "subscribe-unknown-user",
      "state": "satisfied",
      "runs": 1,
      "passes": 1,
      "failures": 0,
      "forbidViolations": []
    }
  ]
}
```

### Effect-Shape Coverage

`shape/coverage.json` asks whether individual catalog clauses were asserted at least once. Its summary distinguishes catalog shapes that were asserted, unasserted shapes, and inline-only shapes used by `toObserveEffects()` but not stored in a catalog.

This is the closest Blackbox equivalent to "which reviewed effects are covered?" A catalog entry can exist while one of its shapes never participates in an assertion path the suite ran.

### OMC/DC Coverage

OMC/DC is an enriched decision view. It joins branch-arm execution with observed effect signatures to ask whether a decision produced distinguishable behavior. It does not replace catalog or shape coverage.

## New and Missing Behavior

A later run can reveal:

- a missing required clause;
- a forbidden match;
- a new observed effect not represented in the accepted contract;
- an uncovered entry or shape.

The correct response is not always "update the catalog." Repair the implementation when the contract is still right. Change the catalog only when the behavior change is intentional and reviewed.
