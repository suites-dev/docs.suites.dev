An **effect** is normalized boundary behavior captured from a running flow. An **effect contract** records which effects are required or forbidden. **Effect coverage** reports how analyzed attempts relate to that reviewed policy.

## Effects Are Blackbox's Trace-Based Testing Layer

Trace-based testing checks what happened throughout one execution, not only the final response. Ted Young's 2018 **Trace Driven Development** talk describes the core loop as: define a behavioral model, gather trace data, then check that data against the model.

Blackbox applies that loop to system tests:

```text
Playwright attempt
  → gather correlated runtime observations
  → normalized effects
  → check against the required and forbidden contract
  → sealed evidence and effect verdict
```

| Trace-driven step        | Blackbox term                                                         |
| ------------------------ | --------------------------------------------------------------------- |
| Define a behavior model  | Reviewed required and forbidden effect contract                       |
| Gather trace data        | Runtime observations correlated by run, cell, flow, and attempt IDs   |
| Interpret trace events   | Normalized effects such as `postgres INSERT` or `http POST`           |
| Check data against model | Offline effect analysis                                               |
| Retain the result        | Attempt-scoped events and artifacts inside the sealed evidence bundle |

Blackbox calls these observations **effects** because policy describes boundary behavior, not a telemetry implementation. Contracts do not depend on raw span IDs, span-tree shape, or a tracing backend.

For Node.js, OpenTelemetry supplies context propagation and many semantic HTTP, database, and messaging observations. It is one capture source, not the Blackbox architecture. Other language integrations can produce the same normalized effects without OpenTelemetry.

## One Flow, One Reviewed Contract

```yaml
flow: subscribe-unknown-user
requires:
  - { boundary: postgres, op: SELECT, key: users, service: bff }
forbids:
  - { boundary: http, op: POST, key: /v1/payment_intents, service: bff }
  - { boundary: postgres, op: INSERT, key: subscriptions, service: bff }
```

- `requires` lists effects that must appear in complete evidence.
- `forbids` lists effects that must not appear.
- Normalized effects that match neither list remain evidence without constraining the implementation.

The contract cannot prove behavior outside the capabilities declared by the capture producers in the bundle.

## Observation Is Not Approval

One recorded run describes the current implementation, including possible defects. It does not define desired behavior.

A reviewer decides whether each observation should be:

| Decision    | Meaning                                                                         |
| ----------- | ------------------------------------------------------------------------------- |
| Required    | The flow is incorrect when this effect is missing                               |
| Forbidden   | The flow is incorrect when this effect occurs                                   |
| Incidental  | The observation should not constrain implementation                             |
| Unsupported | Capture cannot normalize the observation soundly; resolve the integrity finding |

Moving an observed effect to `forbids` deliberately creates a failing repair target.

For example, this normalized insert remains visible in the sealed evidence even when the contract mentions only the user lookup and forbidden payment call:

```json
{
  "boundary": "postgres",
  "op": "INSERT",
  "key": "subscriptions",
  "service": "api"
}
```

Leaving the insert unlisted means it is incidental for policy purposes. It does not mean Blackbox discarded it or approved it as required behavior.

<Aside type="warning" title="A Baseline Can Preserve a Defect">
  Capture records facts. People approve policy. Do not let a coding agent turn
  one successful execution into accepted behavior automatically.
</Aside>

## Analysis Is Offline

The analyzer consumes the sealed evidence bundle and the reviewed effect contract. The SUT and test runner do not need to remain running.

The same complete evidence, contract, and analysis policy produce the same result. This makes verdict computation deterministic; it does not make the SUT deterministic.

## Keep Coverage Views Separate

| View           | Question                                                         |
| -------------- | ---------------------------------------------------------------- |
| Effect verdict | Did one analyzed attempt satisfy required and forbidden policy?  |
| Flow coverage  | Did selected attempts check the accepted contract for this flow? |
| Shape coverage | Which individual contract clauses participated in evaluation?    |
| ODC            | Did exercised decision outcomes leave distinguishable evidence?  |

ODC does not strengthen an effect verdict. Effect-policy changes do not strengthen ODC.

## Failure Semantics

Blackbox fails rather than silently accepting:

- a missing required effect;
- an observed forbidden effect;
- an incomplete or integrity-invalid bundle;
- an observation that the declared capture capability cannot normalize soundly;
- a contract mismatch or unsupported contract version.

An otherwise valid normalized effect that matches no clause is not a policy failure.

Changing implementation is the default repair. Change the contract only when the intended behavior changed and a person approved that change.

## Related Trace Terminology

- Ted Young's [Trace Driven Development: Unifying Testing and Observability](https://www.youtube.com/watch?v=NU-fTr-udZg) presents the model-data-check loop and the idea of applying the same behavioral assertions to trace data from different execution environments.
- The OpenTelemetry project defines [trace-based testing](https://opentelemetry.io/blog/2023/testing-otel-demo/) as triggering an operation and validating both its output and emitted trace; its demo uses this approach across integration and end-to-end flows.
- The [OpenTelemetry trace model](https://opentelemetry.io/docs/specs/otel/overview/#tracing-signal) defines a distributed trace as events from one logical operation correlated across component and process boundaries.
- [OpenTelemetry semantic conventions](https://opentelemetry.io/docs/specs/semconv/general/trace/) give common meanings to HTTP, database, messaging, and other span operations that a capture producer can normalize.

Blackbox shares this trace-based testing lineage, then adds its own attempt identity, effect vocabulary, sealed evidence, integrity result, and offline policy analysis.
