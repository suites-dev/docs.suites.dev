A product requirement says that reading the same product twice should use the cache after the first read. A coding agent may propose the behavior, build the test, implement the cache, and repair a failure. A person still decides whether that requirement is correct.

## Give Guidance Before the Agent Acts

**Feedforward** is approved guidance supplied before implementation. In Blackbox, it comes from human-approved behavior and effect claims.

You can express that behavior in either of two ways:

- Reviewed Gherkin linked to explicit Blackbox declarations.
- Direct behavioral declarations without Gherkin.

Both modes converge on the same accepted meaning. Runtime effects never become requirements by themselves.

## Return Evidence After the System Runs

**Feedback** is the result returned after the agent acts. Blackbox runs the selected system test, captures eligible OpenTelemetry evidence, and produces deterministic findings.

## Keep Decisions With Their Owners

| Change                                    | Owner                               | Required next step                                     |
| ----------------------------------------- | ----------------------------------- | ------------------------------------------------------ |
| Implementation or test realization        | Coding agent may propose and repair | Rerun from the earliest invalidated deterministic gate |
| Accepted behavior or claim                | Person                              | Review and approve the changed meaning                 |
| Runtime fact, effect, finding, or verdict | Deterministic Blackbox producer     | Preserve and route the producer result                 |

The agent cannot approve its own proposed behavior or rewrite a finding. A repair to application or capture behavior requires fresh runtime execution. Report-only reanalysis cannot certify it.
