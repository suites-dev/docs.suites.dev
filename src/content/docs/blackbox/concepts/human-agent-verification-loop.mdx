Imagine a system or E2E test that sees one confirmed order and passes. The accepted effect claim allows at most one charge request, but runtime evidence contains two.

An **effect** is a normalized runtime fact at a supported system boundary. Blackbox compares person-approved **effect claims** with sealed evidence under an **analysis policy**, the approved rule for producing findings.

Here, **deterministic** means the same accepted inputs, declared realization, analysis policy, and sealed evidence produce the same finding. It does not mean the running system behaves identically every time.

## Feedforward and Feedback

**Feedforward** gives the agent approved guidance before it acts. **Feedback** returns deterministic findings after the system runs.

This framing follows Birgitta Böckeler's <a href="https://martinfowler.com/articles/harness-engineering.html" target="_blank" rel="noopener noreferrer">Harness engineering for coding agent users</a>, which describes guides as feedforward controls and sensors as feedback controls. Blackbox applies that model to behavioral verification: accepted scenarios and effect claims guide the agent, while Analyzer findings drive repair.

## Route Feedback Without Moving Authority

Findings about the suite or implementation return to the coding agent as a repair problem. The agent reruns the same approved scenario and claims.

A proposed change to Gherkin, effect claims, or analysis policy returns to a person. Feedback can drive repair, but it cannot give the generator permission to redefine success.
