A product requirement says that a completed checkout must not be charged twice. A coding agent can propose the
behavioral contract, complete the system test, implement the behavior, and repair a violation. A person still decides
what the contract requires.

The loop has three clear responsibilities:

- **A person** approves the behavioral contract.
- **A coding agent** implements and repairs the application and system test.
- **Blackbox** evaluates runtime effects and returns deterministic findings.

## The Contract Guides the Agent Before It Acts

The approved behavioral contract guides implementation before the agent acts. Harness engineering calls this
**feedforward**.

The contract may come through reviewed Gherkin or direct behavioral declarations. Runtime effects can verify that
contract, but they cannot become requirements by themselves.

## Findings Guide Repair After the System Runs

Blackbox runs the selected system test, evaluates runtime effects from OpenTelemetry evidence, and returns a finding.
Harness engineering calls this **feedback**.

## Repair or Change the Contract

A violated finding returns to the coding agent as an implementation repair. A proposed change to the behavioral
contract returns to a person as a product decision.

Blackbox keeps those paths separate so repair can move quickly without allowing the agent to redefine success. Every
implementation or capture repair requires a fresh test attempt and fresh evidence.
