**Gherkin rot** is the failure mode where readable scenario text keeps looking useful after it no longer matches the executable behavior it claims to describe.

Feature files go stale when they disconnect from runtime truth. Blackbox treats drift as a build failure, so **living documentation**, documentation synchronized with the behavior it describes, cannot quietly become a stale promise.

## The Problem: Gherkin Rot

Gherkin is useful because it gives behavior a shared language. A reviewer can understand `subscribe-flow` without reading every fixture or assertion.

The risk starts when the `.feature` file becomes a separate artifact humans maintain by hand. It can still say that `alice` subscribes successfully while the test source, generated artifact, or runtime effects have changed.

That is Gherkin rot. The text still looks like behavior documentation, but no gate proves that the text, the test, and the observed effects agree.

## Two Kinds of Drift

Do not treat drift as one generic failure. A stale feature file and a changed runtime effect need different evidence.

| Drift type | What changed | What catches it |
| --- | --- | --- |
| **Feature-file drift** | The `.feature` file no longer matches the test source or cannot be checked cleanly | `blackbox features check` or `blackbox features drift` |
| **Behavioral drift** | The running system produced different required, forbidden, or observed effects | System tests, effect assertions, effect coverage, and observation comparison |

The difference matters in pull requests. Feature-file drift might mean `subscribe-flow.feature` was not updated after the test changed. Behavioral drift might mean `subscribe-unknown-user` still returns the same HTTP status but no longer keeps Stripe and SQS physically absent for `ghost-user`.

### Feature-File Drift (Syntax & Sync)

**Feature-file drift** is a syntax and synchronization problem. It asks whether the readable Gherkin artifact still represents the current test source.

Blackbox checks four failure modes:

| Finding | Meaning |
| --- | --- |
| `missing` | A test source exists, but the matching `.feature` file does not. |
| `stale` | The `.feature` file no longer matches the current test source. |
| `orphan` | A `.feature` file exists without a matching test source. |
| `unparseable` | Blackbox cannot parse the feature file or source input well enough to compare them. |

`features check` also validates Gherkin syntax with the Cucumber parser.

Run it in CI when feature files are part of the review surface:

```bash
pnpm exec blackbox features check --features ./e2e/features --tests ./e2e/tests --json
```

Use `features drift` when CI only needs the synchronization check:

```bash
pnpm exec blackbox features drift --tests ./e2e/tests --features ./e2e/features
```

Treat this as a documentation failure. The system test might still pass, but reviewers are reading stale behavior text.

### Behavioral Drift (Runtime Effects)

**Behavioral drift** is a runtime problem. It asks whether the system still did the required things and avoided the forbidden things while the scenario ran.

Feature-file drift cannot answer that. A synchronized file can still describe a weak or accidentally changed test.

For the showcase, `subscribe-flow` is not proven only by a `201` response. The run also needs the subscription write, cache update, payment call, and downstream order message. For `subscribe-unknown-user`, `ghost-user` must avoid payment and queue effects.

Blackbox catches behavioral drift through runtime gates:

1. The system or E2E test runs the real workflow.
2. Effect assertions check required and forbidden behavior.
3. Effect catalogs promote stable expectations into a reviewable contract.
4. Effect coverage reports show which declared behavior the run proved or missed.
5. Observation comparison can compare baseline and candidate runs during migration or reshape work.

## The Guardrails: Lint, Check, and Compare

Blackbox uses separate guardrails because each artifact can fail differently.

| Gate | Command | Blocks on |
| --- | --- | --- |
| Grammar lint | `blackbox features lint` | Missing action, missing assertion, invalid Given/When/Then order, opaque generated steps |
| Feature check | `blackbox features check` | Gherkin syntax failure or feature-file drift |
| Drift check | `blackbox features drift` | Missing, stale, orphaned, or unparseable feature files |
| System test | `pnpm test:system` or the project command | Test failures, required effects missing, forbidden effects observed |
| Observation compare | `blackbox features compare-observations` | Meaningful runtime differences between baseline and candidate runs |

Use the grammar gate before trusting generated Gherkin. The core shape is:

```text
Given*  When+  Then+
```

`Then` is the conclusion. A scenario that never reaches an observable assertion can look readable without proving behavior. The [Scenario DSL](/docs/blackbox/reference/scenario-dsl) gives this grammar explicit names in source code, which makes generation and linting more reliable.

## Living Documentation as a CI Gate

A **CI gate** is a command that can block a pull request when a required behavior artifact is invalid. For living documentation, the gate must protect both the readable text and the runtime behavior behind it.

A practical CI path looks like this:

```bash
pnpm exec blackbox features lint ./e2e/tests --fail-on error
pnpm exec blackbox features check --features ./e2e/features --tests ./e2e/tests --json
pnpm test:system
```

When the source test changes but the generated `.feature` file is stale, `features drift` makes the diff reviewable:

```diff
$ pnpm exec blackbox features drift --tests ./e2e/tests --features ./e2e/features
scanning 4 test files against 4 feature files...

STALE  e2e/features/subscribe-flow.feature
  test source:  e2e/tests/subscribe-flow.spec.ts
  scenario:     alice is an existing user with no active subscription

- Then the response status is 201
+ Then the response status is 201
+ And the subscription tier is cached for alice

drift summary: 1 stale, 0 missing, 0 orphan, 0 unparseable
exit 1
```

Treat the red diff as a normal review surface. Either regenerate with `features emit` after a real source change, or revise the source test if the hand-written feature is what the team actually wants.

Together, these commands check grammar, feature synchronization, and runtime effects. When all three pass, CI keeps the feature file attached to executable behavior.

Intentional behavior changes should update the relevant artifacts together. If `subscribe-flow` changes, review the test source, generated feature file, effect catalog, and coverage output as one behavior diff. If `ghost-user` behavior changes, check the readable scenario and the forbidden effects that prove payment and queue work stayed absent.

For the concrete workflow, use [Configure CI Gates](/docs/blackbox/guides/ci-behavioral-gates). For the exact source-level scenario grammar, use the [Scenario DSL](/docs/blackbox/reference/scenario-dsl).
