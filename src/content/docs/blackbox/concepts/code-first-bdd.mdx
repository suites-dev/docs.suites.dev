Classic BDD often failed when feature files became detached from the code and test runtime. Blackbox treats Gherkin as one reviewed artifact in a larger behavioral harness.

## The Supported Direction

The primary spec-driven direction is:

```text
approved EARS -> accepted Gherkin -> reviewed native suite alignment -> runtime evidence
```

For existing Playwright tests, `features extract` creates literal baseline Gherkin from the native suite AST. A Skill and human reviewer then sharpen the recovered behavior before `suites align` establishes the accepted binding.

## What Gherkin Does

Gherkin gives humans and agents a concise reading surface:

```gherkin
@flow:subscribe-unknown-user
@requirement:REQ-004
Feature: Reject an unknown subscriber

  Scenario: request stops before payment
    When the unknown user posts a subscription request
    Then the response status is 404
    And no payment request is sent
```

It does not prove runtime behavior by itself. Runtime evidence and effect contracts do that.

## What Playwright Does

Playwright remains the executable suite:

```ts
test.describe(
  "Reject an unknown subscriber",
  { tag: "@flow:subscribe-unknown-user" },
  () => {
    test("request stops before payment", async ({ request, capture }) => {
      const response = await request.post("/subscriptions", {
        data: { userId: "ghost-user", tier: "pro" },
      });

      expect(response.status()).toBe(404);
      await expect(capture).toMatchCatalog();
    });
  },
);
```

## Summary

- **Gherkin is a review artifact**, not the runtime proof.
- **Playwright is the executable suite.**
- **Runtime evidence decides whether accepted behavior was observed.**
- **Feature-to-test scaffolding is not the alpha anchor.**
