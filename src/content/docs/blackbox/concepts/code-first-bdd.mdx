Code-First BDD starts with executable system behavior. You write or keep the Playwright flow, capture runtime evidence, review the effect catalog, and let Blackbox emit a readable Gherkin projection from behavior that actually runs.

Classic BDD often starts with the `.feature` file. Blackbox keeps the useful language of Gherkin, but changes the source of truth: the system test and runtime evidence lead; the feature file follows.

## Why Flip BDD Around?

Gherkin is useful because it gives behavior a shared language:

```gherkin
Given ghost-user is not present in the system
When ghost-user POSTs /subscriptions
Then the request stops before downstream work
```

The problem is not the language. The problem is staleness. A readable feature file can keep looking correct after the test source, implementation, or runtime behavior moved away from it.

Blackbox uses the opposite direction:

1. The system test drives `subscribe-flow` or `subscribe-unknown-user`.
2. Runtime evidence records boundary behavior from BFF, Redis, Postgres, payment HTTP, and SQS.
3. The effect catalog records which effects are required or forbidden.
4. `features emit` produces a readable `.feature` file from the executable test.
5. `features check` gates syntax and feature-file drift.

That gives teams a path into BDD without making Gherkin the master artifact.

## Test Source And Feature Projection

The Scenario DSL names the same behavior grammar Gherkin uses, but keeps it inside executable test code.

<Tabs groupId="dsl-to-gherkin">
<TabItem value="dsl" label="Scenario DSL" default>

```ts
import { expect, scenario } from './testbed.js';
import { postJson } from './_http.js';

scenario('subscribe-flow', 'subscribing to the pro tier', ({ given, background }) => {
  background('the system is reset', async ({ system }) => {
    await system.reset();
  });

  given('alice is an existing user with no active subscription', async ({ system, capture, when }) => {
    await when('alice POSTs /subscriptions with a valid card', async ({ then }) => {
      const response = await postJson(`${system.bff.hostBaseUrl}/subscriptions`, {
        userId: 'alice',
        paymentMethodId: 'pm_card_visa',
      });

      await then('the response status is 201', async () => {
        expect(response.status).toBe(201);
        await expect(capture).toMatchCatalog();
      });
    });
  });
});
```

</TabItem>
<TabItem value="feature" label="Generated feature file">

```gherkin
@flow:subscribe-flow
Feature: subscribing to the pro tier

  Background:
    Given the system is reset

  Scenario: alice is an existing user with no active subscription
    When alice POSTs /subscriptions with a valid card
    Then the response status is 201
```

Read the generated feature file as a projection, not as the full proof. It makes the scenario readable. Runtime effects and the effect catalog carry the behavioral evidence.

## AAA And Given-When-Then

Blackbox maps the familiar test shape to Gherkin:

| Test structure | Gherkin shape | Job |
| --- | --- | --- |
| Arrange | `Given` | Prepare state and preconditions |
| Act | `When` | Exercise the behavior |
| Assert | `Then` | State the observable conclusion |

This matters because feature generation should not produce loose prose. A scenario needs setup, action, and an observable conclusion. Runtime effects can then strengthen the conclusion with required and forbidden behavior.

For example, a `201` assertion says the visible request completed. The effect catalog can also require the payment call, subscription insert, Redis tier write, and SQS message. In `subscribe-unknown-user`, the visible `404` can be paired with forbids that prove payment and queue work stayed absent.

## Feature Files Are Optional

Effects are the core Blackbox track. Feature files add a second value when readability and review matter.

| Use only effects when | Add feature files when |
| --- | --- |
| The team needs runtime proof but does not read Gherkin | Product, QA, platform, or agents need a compact behavior surface |
| The first goal is one catalog and one coverage signal | Feature diffs should appear in pull requests |
| The workflow is still being stabilized | Generated behavior specs should be checked in CI |

Do not generate feature files just to have more artifacts. Use them when they change how people review behavior.

## Feature-File Drift

Feature-file drift is a synchronization failure. It means the readable Gherkin layer no longer matches the executable test source or cannot be checked cleanly.

Blackbox reports four practical drift states:

| Finding | Meaning |
| --- | --- |
| `missing` | A test exists, but the matching `.feature` file does not |
| `stale` | The `.feature` file no longer matches the current test source |
| `orphan` | A `.feature` file exists without a matching test source |
| `unparseable` | Blackbox cannot parse the feature file or source input well enough to compare them |

Run the drift gate when committed feature files are part of review:

```bash
pnpm exec blackbox features check --features ./e2e/features --tests ./e2e/tests --json
```

Use the narrower command when CI only needs synchronization:

```bash
pnpm exec blackbox features drift --tests ./e2e/tests --features ./e2e/features
```

`features check` also validates Gherkin syntax through the Cucumber parser. It does not require Cucumber step definitions.

## Behavioral Drift

Feature-file drift is not the same as behavioral drift.

| Drift type | What changed | What catches it |
| --- | --- | --- |
| Feature-file drift | The readable `.feature` file is no longer synchronized with the test source | `blackbox features check` or `blackbox features drift` |
| Behavioral drift | The running system produced different required, forbidden, or newly observed effects | System tests, effect matchers, effect coverage, and observation comparison |

This distinction keeps BDD honest. A synchronized feature file can still describe a weak test. A passing response assertion can still miss a changed side effect. Runtime evidence and catalog coverage are the stronger gate for behavior.

## CI Shape

A practical feature-file gate runs before or beside the system-test command:

```bash
pnpm exec blackbox features lint ./e2e/tests --fail-on error
pnpm exec blackbox features check --features ./e2e/features --tests ./e2e/tests --json
pnpm test:system
```

Treat feature-file drift as a documentation failure. Treat catalog failures as behavior failures. Intentional behavior changes should update the test source, generated feature file, catalog, and reports together.
