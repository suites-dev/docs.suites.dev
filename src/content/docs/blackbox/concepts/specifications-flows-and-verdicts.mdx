An accepted checkout scenario says one completed order produces one charge:

```gherkin
Scenario: Charge one completed order once
  Given checkout encounters a transient timeout
  When the order completes after a retry
  Then one order is confirmed
  And one charge request is sent
```

Gherkin makes that intent readable. The system suite makes it executable. Runtime evidence records what the system did. None of those later stages may silently reinterpret the accepted target.

<Aside type="info" title="Alpha Target">
  The Alpha workflow uses Gherkin as the readable expression of accepted intent.
  Gherkin guides realization; it is not runtime evidence and cannot change an
  effect finding.
</Aside>

## Keep the Chain Directional

```text
accepted intent → Gherkin → SuitePlan → RunnerBundle → RunPlan
                                              ↓
                              fresh execution → sealed evidence → findings
```

Each artifact has one responsibility:

| Artifact             | Responsibility                                                     |
| -------------------- | ------------------------------------------------------------------ |
| **Gherkin**          | Express accepted intent in scenarios people can review.            |
| **SuitePlan**        | Own the accepted meaning compiled from that reviewed behavior.     |
| **RunnerBundle**     | Own the concrete actions and checks that realize the SuitePlan.    |
| **RunPlan**          | Select a declared realization without adding or weakening meaning. |
| **Runtime evidence** | Record bounded facts from one fresh execution.                     |
| **Findings**         | State what deterministic analysis concluded from accepted inputs.  |

## Preserve Identity Across Representations

Stable identities connect the accepted case, its declared realization, each runtime attempt, and the resulting evidence. Similar titles or nearby source order do not establish that relationship.

This prevents evidence from one case, retry, or sequence member from being used to complete another case's claim.

## Let the Suite Realize Intent

The executable system suite supplies concrete actions and native assertions. Those details belong to the RunnerBundle because they describe how the accepted case runs.

The realization can be repaired when it is missing, stale, or incorrect. Repair does not grant permission to change the SuitePlan.

## Let Evidence Record Facts

Runtime opens a fresh managed-capture boundary and records supported observations from the running system. Eligible observations become effects inside sealed evidence.

Evidence describes the execution, including defects. It never becomes accepted behavior automatically.

## Let the Analyzer Produce Findings

The Analyzer compares the accepted meaning and analysis policy with sealed evidence. It owns the findings; Runtime does not decide what passed, and the coding agent does not manufacture a verdict.

A failed finding normally returns to the agent for implementation repair. A proposed change to accepted intent or policy returns to a person.
