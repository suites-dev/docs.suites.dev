Blackbox connects reviewed intent to executable behavior through an explicit **flow ID**. It does not infer that two similar descriptions prove the same behavior.

<VerificationTriangleDiagram />

## One ID Connects the Chain

For `subscribe-unknown-user`, the same stable ID can appear in:

- `@flow:subscribe-unknown-user` in Gherkin.
- A runner-native flow tag. The default recognized prefix is `@flow:`.
- `subscribe-unknown-user.effects.yaml` in the configured features directory.
- The sealed runtime evidence and resulting reports.

The ID establishes identity. Each artifact still answers a different question.

| Artifact         | What it contributes                                |
| ---------------- | -------------------------------------------------- |
| EARS requirement | Reviewed normative intent with a stable `REQ-*` ID |
| Gherkin feature  | Readable scenarios and requirement bindings        |
| Executable flow  | Runner-native steps and assertions                 |
| Effect contract  | Required and forbidden boundary behavior           |
| Evidence bundle  | What the running system actually did               |
| Analysis report  | Deterministic effect and coverage verdicts         |

## Validate the Static Chain First

You can validate requirements, Gherkin, and generated suites without starting the SUT.

```bash
pnpm exec blackbox requirements validate requirements --json
pnpm exec blackbox features check e2e/tests --requirements requirements --json
pnpm exec blackbox requirements check requirements --tests e2e/tests --json
pnpm exec blackbox requirements drift requirements --tests e2e/tests --json
pnpm exec blackbox suites check e2e/tests --json
```

These commands prove that accepted files are parseable, IDs resolve, and suite structure agrees with Gherkin. They do not prove that the implementation behaves correctly.

## Express Intent in Reviewable Artifacts

An EARS requirement states the expected outcome:

```text
REQ-004: When an unknown user subscribes, the bff shall not request payment, persist a subscription record, or publish a subscription order.
```

Gherkin projects that intent into a flow people can review:

```gherkin
@flow:subscribe-unknown-user
@requirement:REQ-004
Feature: Rejecting unknown subscription users

  Scenario: ghost-user attempts to subscribe
    When ghost-user POSTs /subscriptions
    Then the response status is 404
```

Blackbox Skills can propose both artifacts. A person accepts or rejects them. The CLI validates their structure and relationship.

## Execute, Capture, and Analyze Separately

The runtime lifecycle keeps three responsibilities independent:

1. A **runner adapter** executes the tagged flow and reports native test results.
2. A **capture implementation** records supported SUT behavior inside an isolated capture cell.
3. The **offline analyzer** verifies the sealed evidence against the accepted effect contract and computes coverage.

This separation lets Playwright run a Node SUT today without making either technology part of the evidence protocol.

| Result                       | What it proves                                            |
| ---------------------------- | --------------------------------------------------------- |
| Native test status           | Runner assertions passed or failed                        |
| Feature and suite checks     | Accepted files and executable structure agree             |
| Effect verdict               | Required and forbidden boundary effects matched           |
| Evidence integrity result    | The bundle is complete enough for the requested analysis  |
| Observable decision coverage | Exercised decisions remained visible at a system boundary |

One green result never turns a missing layer into proof.

## Use Only the Layers You Need

You can adopt Blackbox with:

- Requirements, Gherkin, and suite checks without runtime execution.
- Runtime effect verification without EARS or Gherkin.
- The complete chain when intent, executable behavior, and runtime effects all need active review.

The complete chain is stronger only when each artifact has an owner. More files without review create ceremony, not verification.

## Keep Authority Explicit

Skills propose. The CLI validates and transforms. Runner and capture integrations collect evidence. The analyzer computes verdicts. A person decides which requirement, scenario, suite change, effect contract, or repair becomes accepted.

That boundary gives a coding agent deterministic findings to repair against without letting it silently redefine success.
