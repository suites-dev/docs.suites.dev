Blackbox connects specifications to runtime evidence through an explicit **flow ID**. It does not infer that natural-language intent was proven.

<CodeFirstBddDiagram kind="sdd" />

## The Nouns

| Noun                 | Meaning                                                        |
| -------------------- | -------------------------------------------------------------- |
| EARS requirement     | A normative `REQ-*` statement validated by `earsyntax`         |
| Gherkin feature      | A readable Given/When/Then projection of executable behavior   |
| Playwright flow      | A stable ID declared by `test.system(flowId, ...)`             |
| Requirement sidecar  | A reviewed mapping from EARS IDs to flow IDs                   |
| Effect catalog       | Required and forbidden runtime behavior per flow ID            |
| Catalog coverage     | Runtime result per effect-catalog entry                        |
| Requirement coverage | Requirement verdict derived from bindings and catalog coverage |

The flow ID is the join key. A flow such as `subscribe-unknown-user` can name the Playwright test block, the effect-catalog entry, the requirement binding, and the generated feature tag `@flow:subscribe-unknown-user`.

## EARS Is Normative Intent

```text
REQ-004: When an unknown user subscribes, the bff shall not request payment, persist a subscription record, or publish a subscription order.
```

Blackbox validates the requirement source and a strict binding sidecar:

```yaml
specVersion: "0.1"
entries:
  subscribe-unknown-user:
    requirements: [REQ-004]
```

The binding is deliberately explicit. It makes the semantic decision reviewable instead of asking a model or heuristic to infer that a similarly worded test proves the requirement.

## Gherkin Is a Behavior Projection

```gherkin
@flow:subscribe-unknown-user
Feature: rejecting unknown subscription users

  Scenario: ghost-user attempts to subscribe
    When ghost-user POSTs /subscriptions
    Then the response status is 404
```

Blackbox can emit this structure from Playwright or the Blackbox Scenario DSL and detect source-to-feature drift. The feature file helps people and agents read the behavior. It does not produce the runtime verdict by itself.

## Runtime Evidence Produces the Verdict

Requirement coverage joins bindings with `catalog/coverage.json`. The rules are deterministic:

| Verdict    | Rule                                                          |
| ---------- | ------------------------------------------------------------- |
| `proven`   | Every bound flow is `satisfied`                               |
| `violated` | At least one bound flow is `failed`                           |
| `unproven` | No flow failed, but evidence is missing, absent, or uncovered |
| `unbound`  | No flow is bound to the requirement                           |

When a requirement has multiple flows, the binding is conjunctive: every bound flow must be satisfied for the requirement to be proven.

Missing evidence does not become a false violation. It remains `unproven`, which distinguishes "the system contradicted the contract" from "this run did not prove it."

<Aside type="info" title="Two Kinds of Drift">
  `requirements drift` checks EARS IDs, flow bindings, and effect-catalog flow
  IDs. `features drift` checks generated Gherkin against test sources. They
  protect different relationships.
</Aside>

## Specifications Can Be Used Separately

You can adopt any of these shapes:

- effects and catalogs without EARS or Gherkin;
- EARS bindings and runtime requirement verdicts without feature files;
- generated Gherkin and drift checks without EARS;
- all three when requirements, examples, and runtime proof each have active reviewers.

The combined path is stronger only when every artifact has a clear owner and use. An unreviewed generated file or a binding nobody maintains adds ceremony, not confidence.

## Stable Output for Automation

The requirements and features CLIs support JSON envelopes with `schemaVersion`, `command`, `status`, and either `data`, `findings`, or `error`. Exit codes distinguish clean results, findings, and usage/environment errors.

Agents can use those deterministic outputs to repair implementation or documentation drift. They should stop when the proposed repair changes a requirement, binding, or accepted effect contract.
