Blackbox connects reviewed requirements to runtime evidence through an explicit **flow ID**. It does not infer that natural-language intent was proven.

<VerificationTriangleDiagram />

## The Nouns

| Noun                 | Meaning                                                           |
| -------------------- | ----------------------------------------------------------------- |
| EARS requirement     | A normative `REQ-*` statement checked by the requirements engine  |
| Gherkin feature      | A readable scenario file with `@flow` and `@requirement` tags     |
| Playwright flow      | A stable ID declared by native Playwright `test.describe` tags    |
| Effect contract      | Required and forbidden runtime behavior per flow ID               |
| Effect coverage      | Runtime result per effect contract                                |
| Requirement coverage | Requirement verdict derived from feature tags and effect coverage |

The flow ID is the join key. A flow such as `subscribe-unknown-user` can name the Playwright test block, the effect contract, and the feature tag `@flow:subscribe-unknown-user`.

Inspect the complete join without searching each file manually:

```bash
blackbox flows show subscribe-unknown-user --json
```

## EARS Is Normative Intent

```text
REQ-004: When an unknown user subscribes, the bff shall not request payment, persist a subscription record, or publish a subscription order.
```

Blackbox validates the requirement source. The feature file then makes the semantic connection explicit with `@requirement:<id>` tags instead of asking a model or heuristic to infer that a similarly worded test proves the requirement.

A clean EARS validation result establishes structure, not semantic truth. It does not say that the requirement is complete, approved, consistent with every other requirement, or implemented.

## Gherkin Is a Behavior Projection

```gherkin
@flow:subscribe-unknown-user
@requirement:REQ-004
Feature: rejecting unknown subscription users

  Scenario: ghost-user attempts to subscribe
    When ghost-user POSTs /subscriptions
    Then the response status is 404
```

Blackbox can validate this structure and detect source-to-feature drift. The feature file helps people and agents read the behavior. It does not produce the runtime verdict by itself.

## Runtime Evidence Produces the Verdict

Requirement coverage joins feature requirement tags with effect coverage. The rules are deterministic:

| Verdict    | Rule                                                          |
| ---------- | ------------------------------------------------------------- |
| `proven`   | Every bound flow is `satisfied`                               |
| `violated` | At least one bound flow is `failed`                           |
| `unproven` | No flow failed, but evidence is missing, absent, or uncovered |
| `unbound`  | No flow is bound to the requirement                           |

When a requirement has multiple flows, the binding is conjunctive: every bound flow must be satisfied for the requirement to be proven.

Missing evidence does not become a false violation. It remains `unproven`, which distinguishes "the system contradicted the contract" from "this run did not prove it."

<Aside type="info" title="Two Kinds of Drift">
  `requirements drift` checks EARS IDs, feature tags, and effect-contract flow
  IDs. `features drift` checks reviewed Gherkin against test sources. They
  protect different relationships.
</Aside>

## The Surfaces Support Different Claims

You can adopt any of these shapes:

- effects without EARS or Gherkin;
- EARS requirement verdicts with feature tags and runtime evidence;
- Gherkin checks without EARS;
- all three when requirements, examples, and runtime proof each have active reviewers.

The combined path is stronger only when every artifact has a clear owner and use. Requirements or Gherkin can improve governance without runtime observation, but they do not verify implementation. Runtime evidence is required before Blackbox can claim what the running system did.

## Stable Output for Automation

Blackbox commands return JSON envelopes with `schemaVersion`, `command`, `status`, structured `data`, optional `findings`, or an `error` when no trustworthy result can be produced. Exit codes distinguish clean results, findings, and usage or environment errors.

Agents can use those deterministic outputs to repair implementation or documentation drift. They should stop when the proposed repair changes a requirement, feature tag, suite flow, or accepted effect contract.
