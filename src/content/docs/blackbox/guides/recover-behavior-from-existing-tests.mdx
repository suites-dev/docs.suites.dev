Suppose an approved checkout scenario changes from “one charge request” to “no more than one charge request,” but the Playwright suite still implements the earlier contract. Blackbox must expose that mismatch before runtime evidence can be treated as proof of the new intent.

Use this guide whenever approved Gherkin, step bindings, effect claims, or the executable system suite changes.

<Aside type="info" title="Alpha Target">
  This page describes the accepted Alpha 3 alignment workflow. The final public
  commands, generated filenames, and package APIs are not committed here.
</Aside>

## Keep the Alignment Directional

```text
approved Gherkin
  -> SuitePlan
  -> generated type and runtime binding contracts
  -> project-owned Playwright suite
  -> RunnerBundle
  -> selectable RunPlan
```

Gherkin carries approved human intent. The generated contracts guide and check the executable suite. Neither the suite nor the generated artifacts may redefine the accepted meaning in the SuitePlan.

## 1. Review the Gherkin Change

Start with one concrete case and confirm that a person accepts:

- The scenario and examples.
- The required and forbidden effect claims.
- Any ordering, shared-state, or comparison relationship.
- The policy that determines success.

Formatting, comments, and presentation order may change without changing accepted meaning. A changed outcome, claim, case, or topology relationship must produce new SuitePlan identity.

## 2. Compile the Accepted Intent

Blackbox compiles approved Gherkin and its accepted declarations into a SuitePlan. Compilation must resolve every concrete scenario or Examples row, instruction binding, claim, contract, and topology relationship exactly once.

Stop when compilation reports missing or ambiguous meaning. A coding agent may propose a correction, but only a person can approve a change to intent or policy.

## 3. Use the Generated Contracts as Feedforward

The compiler projects the accepted plan into generated artifacts that constrain the system suite:

- A type contract exposes the accepted cases, instructions, claims, and required fixtures.
- A runtime registration binds the suite to the exact accepted plan identity.
- A plan projection carries the accepted semantic inputs into later runner lowering.

These artifacts provide feedforward guidance. The later typecheck, collection, lowering, and selection checks provide feedback. Regenerate generated artifacts from accepted inputs instead of editing them as a second source of meaning.

## 4. Implement or Repair the Playwright Suite

The project-owned suite supplies real actions and native assertions for each accepted case. A coding agent can implement or repair this realization while the generated type contract keeps its identities and bindings aligned.

The suite is not ready when it contains an empty body, unresolved action, missing assertion, skipped accepted case, or untyped binding.

## 5. Check the Complete Binding

Before runtime execution, Blackbox checks the alignment in order:

1. Typecheck the generated contract and project-owned suite together.
2. Collect the declared Playwright target without executing test bodies.
3. Confirm exactly one runnable binding for every selected case.
4. Lower those bindings into a RunnerBundle.
5. Select a non-empty RunPlan from the accepted cases and declared realization.

Collection evaluates test modules, so project setup must remain safe during discovery. Passing native tests does not replace this alignment check.

## Read the Expected Result

Alignment is ready for runtime when:

- Every selected accepted case has exactly one runnable test.
- Every required action, oracle, claim, and topology relation is bound.
- No missing, extra, duplicate, redirected, stale, or foreign identity remains.
- The SuitePlan and RunnerBundle identities match.
- A RunPlan can select the complete declared execution unit.

If a check fails, repair the earliest invalid stage and repeat the downstream checks. [Use the alignment failure guide](/docs/blackbox/troubleshooting/feature-drift) to choose the repair owner.

## Rerun After an Alignment Change

Repeat alignment when any of these inputs changes:

- Approved Gherkin or effect claims.
- Step bindings, decoders, contracts, fixtures, or topology declarations.
- Playwright actions, assertions, registration, or target configuration.
- Generated type, runtime, or plan artifacts.
- Runner adapter or compiler identity.

If the earlier version already ran, start a fresh runtime execution. Evidence remains pinned to the exact plan and realization that produced it.
