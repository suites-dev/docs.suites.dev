Spec-driven development makes intent explicit before implementation. Blackbox adds a verification step after selected intent becomes an executable Playwright flow: the running system must produce the reviewed boundary behavior.

## Keep the Surfaces Separate

| Surface                               | Owner                               | Job                                                 |
| ------------------------------------- | ----------------------------------- | --------------------------------------------------- |
| Product spec, ticket, or SDD artifact | Product and engineering             | Explain intent and constraints                      |
| EARS requirement                      | Human-ratified requirements process | Give normative behavior a stable ID                 |
| Requirement sidecar                   | Reviewer                            | Bind requirement IDs to explicit flow IDs           |
| Playwright flow                       | Developer or agent                  | Exercise the system through a real boundary         |
| Effect catalog                        | Reviewer                            | Declare required and forbidden runtime effects      |
| Runtime reports                       | Blackbox                            | Produce deterministic evidence and verdicts         |
| Generated Gherkin                     | Test source plus reviewer           | Project executable behavior into readable scenarios |

Blackbox does not replace planning specs, GitHub Spec Kit, Tessl, tickets, or design documents. It adds the missing verification relationship between selected intent and runtime evidence.

## Existing-Behavior Loop

Use this loop for refactors, migrations, and agent-authored maintenance:

1. Select a boundary-risk flow that already runs.
2. Capture and review its effect catalog.
3. Bind relevant EARS requirement IDs when normative traceability matters.
4. Let the developer or agent change the implementation.
5. Run the same Playwright flow in the isolated testbed.
6. Repair implementation failures from test output and JSON verdicts.
7. Stop for review when the repair would change a requirement, binding, or accepted effect.
8. Optionally emit Gherkin so the behavior remains easy to inspect later.

The agent can iterate on implementation because the accepted contract stays fixed. A new effect is not permission to rewrite the catalog automatically.

## New-Behavior Loop

For a feature that does not exist yet, an agent can draft the executable behavior before implementation:

1. A human expresses intent and constraints.
2. The agent proposes EARS requirements or reuses the team's existing spec format.
3. The agent writes a narrow Playwright flow with a stable flow ID.
4. Blackbox emits a Gherkin projection from the test for human review, when that reading surface is useful.
5. The human refines the behavior language and ratifies the requirement binding.
6. The agent implements the feature.
7. The testbed runs the system and Blackbox records effects.
8. A human reviews the first catalog contract.
9. The agent repairs implementation until runtime and requirement verdicts pass.

The current stable Gherkin direction is test-to-feature. Feature-to-test scaffolding is experimental and should be treated as a draft accelerator, not as proof.

## Deterministic Inputs for Agents

Use JSON command output instead of asking an agent to interpret colored terminal prose:

```bash
pnpm exec blackbox requirements check --tests e2e --json
pnpm exec blackbox requirements drift --tests e2e --json
pnpm exec blackbox requirements coverage \
  --tests e2e \
  --coverage e2e/.blackbox-coverage/catalog/coverage.json \
  --fail-on violated \
  --json
pnpm exec blackbox features check \
  --features e2e/features \
  --tests e2e/tests \
  --json
```

The envelope has `schemaVersion: 1`, a command name, a status, and structured `data`, `findings`, or `error`. Findings carry rule, severity, message, file, and line fields.

That gives an agent a bounded repair task:

- a `requirement-violated` finding points to implementation or accepted contract conflict;
- `unproven` points to missing runtime evidence;
- requirement drift points to missing or stale bindings;
- feature drift points to a stale readable projection;
- a catalog failure points to missing required or observed forbidden effects.

## Human Ratification Boundary

Agents may safely regenerate derived artifacts and repair code while the accepted behavior remains stable. Require review for:

- new or changed EARS text;
- requirement-to-flow binding changes;
- new or removed catalog clauses;
- a changed forbidden effect;
- ambiguous generated Gherkin;
- broadening the flow scope to make a verdict pass.

<Aside type="warning" title="Do Not Let One Agent Grade Its Own Intent">
  The value of runtime evidence is reduced when the same automation can silently
  rewrite requirements, tests, and catalogs until they agree. Keep accepted
  behavior changes visible in the diff and owned by review.
</Aside>

## What Belongs in the Repository

Repository memory helps both future humans and future agent sessions:

- requirement sources;
- requirement binding sidecars;
- Playwright flows and stable flow IDs;
- reviewed effect catalogs;
- generated feature files only when they are an active review surface.

Coverage JSON, OMC/DC reports, raw spans, and observation outputs are normally CI artifacts. Upload them with a useful retention policy rather than committing every run.
