Spec-driven development makes intent explicit before implementation. Blackbox turns selected intent into a behavioral harness that agents can work against without silently changing what they are supposed to prove.

<VerificationLoopDiagram />

## Keep the Harness Parts Separate

| Harness part                                      | Owner                                                         | Job                                             |
| ------------------------------------------------- | ------------------------------------------------------------- | ----------------------------------------------- |
| Product spec, ticket, Kiro, OpenSpec, or Spec Kit | Product and engineering                                       | Explain intent and constraints                  |
| EARS requirements                                 | Human-approved artifact proposed by `$blackbox-requirements`  | Give selected obligations stable IDs            |
| Gherkin feature                                   | Human-accepted artifact proposed by `$blackbox-gherkin`       | Make the selected behavior readable             |
| Playwright flow                                   | Human-approved suite patch proposed by `$blackbox-playwright` | Exercise the system through a real boundary     |
| Effect contract                                   | Human-accepted artifact proposed by `$blackbox-effects`       | Declare required and forbidden runtime behavior |
| Runtime reports                                   | Blackbox CLI                                                  | Produce deterministic evidence and verdicts     |

Blackbox does not replace planning tools. It supplies the harness that connects selected intent to executable flow evidence.

## Existing-Behavior Loop

Use this loop for refactors, migrations, and agent-authored maintenance:

1. Run `blackbox status --json` before changing implementation.
2. Select a boundary-risk flow and inspect it with `blackbox flows show <flow-id> --json`.
3. Run `blackbox verify --flow <flow-id> --json`.
4. Ask `$blackbox-effects` to propose an effect contract only if the flow has no accepted contract yet.
5. Review and accept the effect contract before using it as a gate.
6. Let the developer or agent change implementation.
7. Run `blackbox verify --flow <flow-id> --json` against the accepted harness.
8. Repair implementation findings and rerun.
9. Stop for review when passing would require changing a requirement, feature, suite flow, or effect contract.

The agent can iterate on implementation because accepted behavior stays fixed.

## New-Behavior Loop

Use this loop when the feature does not exist yet:

1. A human or planning tool expresses intent and constraints.
2. `$blackbox-requirements` proposes atomic EARS requirements.
3. `blackbox requirements validate` checks the requirement file.
4. A human reviews and approves requirement meaning.
5. `$blackbox-gherkin` proposes a feature file with `@flow` and `@requirement` tags.
6. `blackbox features check` validates Gherkin structure and tag consistency.
7. A human reviews and accepts scenario language.
8. `$blackbox-playwright` proposes a native Playwright suite patch.
9. A human approves the exact patch before it changes the suite.
10. A coding agent implements the behavior.
11. `blackbox verify --flow <flow-id> --json` runs the flow and captures evidence.
12. `$blackbox-effects` proposes required and forbidden effects from evidence.
13. A human reviews and accepts the effect contract.
14. The CLI computes separate verdicts and the coding agent repairs implementation until the accepted harness passes.

No step writes directly to the accepted suite or accepted behavior contract without review.

## Deterministic Inputs for Agents

Use JSON command output instead of asking an agent to interpret colored terminal prose:

```bash
pnpm exec blackbox status --json
pnpm exec blackbox flows show subscribe-unknown-user --json
pnpm exec blackbox requirements validate 'requirements/**/*.ears' --json
pnpm exec blackbox features check --features ./features --json
pnpm exec blackbox verify --flow subscribe-unknown-user --json
```

The envelope has `schemaVersion`, a command name, a status, structured `data`, optional `findings`, and an `error` when no trustworthy result can be produced. Findings carry layer, flow ID, rule, severity, message, file, and line fields when those locations exist.

That gives an agent a bounded repair task:

- a requirement violation points to implementation or accepted contract conflict;
- `unproven` points to missing runtime evidence;
- feature drift points to a stale readable behavior artifact;
- an effect failure points to missing required effects or observed forbidden effects;
- a decision `coverage-gap` points to missing branch-arm evidence;
- a `masking-candidate` says different decision arms produced the same evidence signature.

## Human Review Boundary

Agents may safely repair code while accepted behavior remains stable. Require review for:

- new or changed EARS text;
- new or changed Gherkin language;
- new or changed Playwright flow scope;
- any suite patch proposed by a Skill;
- new or removed effect clauses;
- a changed forbidden effect;
- broadening the flow scope to make a verdict pass;
- final interpretation of evidence before the agent stops.

<Aside type="warning" title="Do Not Let One Agent Grade Its Own Intent">
  Runtime evidence loses value when the same automation can silently rewrite
  requirements, tests, and effects until they agree. Keep accepted behavior
  changes visible in review and owned by a human gate.
</Aside>

## What Belongs in the Repository

Repository memory helps future humans and future agent sessions:

- `requirements/**/*.ears`;
- `features/**/*.feature`;
- `features/<flow>.effects.yaml`;
- Playwright flows with `@flow:<id>` tags;
- selected generated summaries when they are part of review.

Coverage JSON, observable decision reports, raw spans, and observation outputs are normally CI artifacts. Upload them with a useful retention policy rather than committing every run.

## Summary

- **Inferential harnesses** propose artifact changes through Skills.
- **Computational harnesses** validate, run, observe, and report through the CLI.
- **Human gates** approve accepted behavior.
- **Implementation agents** repair code against the fixed harness.

Read [Agent Skills](/docs/blackbox/guides/agent-skills) for the Skill contracts, then enforce the loop with [Reports and CI Gates](/docs/blackbox/guides/reports-and-ci-gates).
