Blackbox gives coding agents deterministic findings without giving them authority to redefine success.

```text
human-approved harness -> deterministic execution and analysis
          ^                            |
          |                            v
human accepts or returns <- agent repairs implementation
```

## Assign One Owner to Each Decision

| Responsibility       | Owner                         | Examples                                               |
| -------------------- | ----------------------------- | ------------------------------------------------------ |
| Inferential proposal | Blackbox Skills               | Requirements, Gherkin, effect contracts, repair plans  |
| Static computation   | Blackbox CLI                  | Validation, generation, drift, and alignment           |
| Flow execution       | Runner adapter                | Native hooks, assertions, flow and retry identity      |
| Runtime observation  | Language capture              | Supported effects and native coverage artifacts        |
| Evidence integrity   | Sidecar and protocol          | Identity, capabilities, artifacts, settle, and sealing |
| Offline analysis     | Effect and language analyzers | Effect verdicts, source joining, decisions, and ODC    |
| Behavioral authority | People                        | Accepted harness, policy, and final result             |

## Start From Existing Behavior or Approved Intent

Existing suites can produce a reviewable Gherkin baseline:

```text
passing suite -> features emit -> agent proposal -> human review -> suites check
```

New behavior can begin with approved EARS requirements:

```text
approved requirement -> features generate -> human review
    -> suites generate -> implement assertions -> suites check
```

Both paths join at one passing native flow with one stable `@flow:` identity. EARS and Gherkin remain optional during runtime execution.

## Run the Inner Repair Loop

```text
blackbox test
  -> test, integrity, effect, or ODC finding
  -> implementation repair
  -> blackbox test
```

The agent may change implementation and rerun the same harness without waiting for approval after every edit.

It stops when passing would require changing:

- Accepted requirements or scenarios.
- Stable flow identity.
- Native assertions.
- Required or forbidden effects.
- SUT source, isolation, or reset assurance.
- An explicit ODC gate.

Those changes redefine the target and return to human review.

Here, **SUT source** means the provisioning strategy and its configuration: command, Compose, Dockerfile, artifacts, external lifecycle, or custom provisioner. It does not mean ordinary application source files. The agent may edit application implementation inside the repair loop as long as the accepted harness and runtime policy stay fixed.

## Keep Evidence and Approval Distinct

A sealed bundle records what happened. An effect contract records what should happen. A generated feature records a reviewable projection. None becomes accepted merely because an agent wrote it.

Repository review, code ownership, and branch protection provide the enforcement boundary. Blackbox makes proposed changes and deterministic results visible.
