Choose the setup path that matches how your project already starts the running system. The path defines the application and dependencies that Blackbox must isolate, observe, and stop for each test attempt.

## Choose a Path

| Setup path                                                                 | Use it when                                                                   | Current status   |
| -------------------------------------------------------------------------- | ----------------------------------------------------------------------------- | ---------------- |
| [**Docker Compose**](/docs/blackbox/guides/use-existing-compose)           | The project already declares the application and its dependencies in Compose. | **Alpha target** |
| [**Testcontainers**](/docs/blackbox/guides/use-custom-provisioner)         | Project code already constructs the test environment with Testcontainers.     | **Experimental** |
| [**Dockerfile**](/docs/blackbox/guides/build-from-dockerfile)              | The project has a repeatable image build but no Compose topology.             | **Planned**      |
| [**Distribution artifacts**](/docs/blackbox/guides/run-compiled-artifacts) | The project tests already-built runnable artifacts outside containers.        | **Planned**      |

Check [Alpha Support Status](/docs/blackbox/status/alpha-status#application-setup-status) before adopting a path. Publishing a conceptual workflow does not mean that its public configuration or support boundary is final.

## Keep the Boundary Explicit

Whichever path you choose, identify:

- The services and dependencies the test can reach.
- The resources Blackbox owns and cleans up.
- The participants that must emit OpenTelemetry data.
- The condition that makes one attempt complete.

Blackbox must stop when it cannot establish the isolation or evidence boundary required by the behavioral contract. It does not silently fall back to a weaker setup.
