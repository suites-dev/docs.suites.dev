## Playwright Primitives Still Apply

Blackbox builds on Playwright Test rather than replacing it:

- `test()` defines a runnable case;
- `test.describe()` groups cases;
- `test.beforeEach()` and fixtures prepare state;
- `test.step()` names actions and assertions;
- `request` drives HTTP while carrying the active Blackbox trace;
- `expect` includes Blackbox matchers.

The Blackbox addition is `test.system(flowId, description, fn)`:

```ts
test.system("subscribe-unknown-user", "rejecting an unknown user", () => {
  test("ghost-user is rejected before downstream work", async ({
    capture,
    request,
    system,
  }) => {
    const response = await request.post(
      `${system.bff.hostBaseUrl}/subscriptions`,
      {
        data: { userId: "ghost-user", paymentMethodId: "pm_card_visa" },
      },
    );

    expect(response.status()).toBe(404);
    await expect(capture).toMatchCatalog();
  });
});
```

Every test inside the block inherits `@flow:subscribe-unknown-user`. The capture fixture uses that ID to load the matching effect-catalog entry, record coverage, and connect optional requirement bindings and generated feature tags.

## Parallelism Model

With the standard testbed:

1. Playwright starts N workers.
2. Blackbox starts one isolated SUT stack per worker.
3. The stack is reused by tests scheduled to that worker.
4. The configured reset function runs when the isolation group changes.
5. Each worker writes coverage partials.
6. global teardown merges partials into canonical reports.

Different `test.system` blocks may run in parallel across workers. Tests inside one `test.system` block use Playwright's default in-order mode so OMC/DC branch arms do not interleave inside the same worker SUT.

```bash
npx playwright test --config ./e2e/playwright.config.ts --workers 4
```

There is no `BLACKBOX_ISOLATION` switch. The worker count and testbed source determine the topology.

## State Isolation

Per-worker containers prevent workers from sharing databases, caches, queue state, debug buffers, and V8 counters. They do not reset state between every test automatically.

The testbed computes an isolation group key:

- Blackbox Scenario DSL cases carry an explicit group tag;
- plain Playwright tests fall back to file plus title path;
- a manual grouping policy can override the key.

When the key changes, the testbed calls your `reset({ connect, infra, groupKey, identity })` function for that worker's stack.

Reset all managed state that can affect the next flow. A database truncation without a queue purge is partial isolation.

## Evidence Isolation

The normal fixture resets each worker stack's observation buffers before a test and drains them after the test. Because one worker runs one test at a time against its own stack, that boundary isolates the captured evidence from other workers.

The wrapped Playwright `request` fixture also propagates `traceparent` into the SUT, preserving the distributed trace across services. Use explicit propagation with custom clients when trace relationships or `captureAcross()` filtering matter:

For a custom HTTP helper:

```ts
import { traceparent } from "@suites/blackbox/runners/playwright";

await fetch(url, {
  headers: { traceparent: traceparent() },
});
```

Prefer the wrapped `request` fixture. A raw client can still be observed inside the isolated reset-to-drain window, but without propagation its downstream trace graph may be incomplete.

<Aside type="warning" title="Detached Work Needs a Join Point">
  Fire-and-forget work can outlive the capture window or escape async context.
  Wait for a durable completion signal, poll the managed dependency, or expose a
  test synchronization point before asserting effects.
</Aside>

## Catalog and Feature Writes Under Parallelism

Effect sidecars follow the test file:

```text
tests/checkout.system.test.ts
tests/__effects__/checkout.system.effects.yaml
```

Keep one flow ID owned by one test file. Multiple workers writing the same catalog path create an avoidable ownership conflict.

Coverage does not have that problem. Workers write partial catalog and shape summaries, then teardown merges them with deterministic state priority: `failed` outranks `satisfied`, which outranks `uncovered`.

Generated feature files also need one owning source. Use the dedicated `features emit` step outside the parallel test run, or rely on Playwright snapshot update modes in a controlled update job.

## CI Verification Mode

Local development may baseline a missing catalog entry. CI should verify, not invent, accepted behavior:

```ts
export default defineConfig({
  updateSnapshots: process.env.CI ? "none" : "missing",
});
```

With `none`, a missing flow entry fails and the recorder does not write it. Intentional catalog updates happen in a reviewed local or dedicated update workflow.
