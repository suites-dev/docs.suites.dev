Blackbox supports parallel system tests by separating scheduling from evidence ownership.

Playwright decides which tests run at the same time. Blackbox gives those tests system-test semantics: worker-scoped testbeds, scenario isolation groups, trace attribution, effect catalogs, coverage partials, and merged reports.

## The Mental Model

Parallelism is scheduling. Isolation is ownership.

Playwright can run tests across worker processes, projects, shards, files, and `test.describe.parallel(...)` groups. That answers "what can run at the same time?"

Blackbox answers a different question:

> Which system state and runtime evidence belong to this behavior?

The supported path is to run Playwright through the Blackbox test API and testbed:

1. Playwright starts worker processes.
2. `createBlackboxTestbed()` prepares the system topology.
3. `defineSystemTest()` exposes the Blackbox-aware `test`, `expect`, `scenario`, and `outline` surfaces.
4. Each worker gets its own system boundary when compose isolation is enabled.
5. Each scenario or test receives an isolation group key.
6. `capture` attributes spans and effects to the active test.
7. Worker partials merge into the final reports during teardown.

That is why the docs should not tell users to disable parallelism as the default answer. The better answer is: use the Blackbox isolation model so parallel tests remain attributable.

## Playwright Test API Constructs

Playwright calls this surface the Playwright Test API. These are the constructs Blackbox cares about most:

| Playwright construct | What Playwright does | What Blackbox reads or adds |
| --- | --- | --- |
| `test(title, body)` | Registers one executable test | A behavior candidate with a label, catalog entry, trace, and effects |
| `test.describe(...)` | Groups tests | Context for grouping, tags, and feature generation |
| `test.describe.parallel(...)` | Allows sibling tests to run concurrently | Independent leaves map to plain `scenario(...)` entries with fresh isolation groups |
| `test.describe.serial(...)` | Runs sibling tests as a dependent chain | Reshape can emit `scenario.chain(...)` when shared state is intentional |
| `test.beforeEach(...)` | Runs setup before each test | Can become `background(...)` in the Scenario DSL |
| `test.step(...)` | Adds explicit named substeps | Useful signal for readable behavior traces |
| fixtures such as `request`, `system`, `capture`, `isolation` | Inject runner resources into tests | Drive the SUT, propagate trace identity, reset groups, and collect evidence |
| `expect(...)` | Makes assertions | Strong signal for `Then` and for effect matchers |
| `workers`, `fullyParallel`, projects, sharding | Controls scheduling | Determines how many worker testbeds and partial reports are produced |

Reference: [Playwright Test API](https://playwright.dev/docs/api/class-test), [Playwright parallelism](https://playwright.dev/docs/test-parallel).

## The Blackbox Test API Layer

Blackbox adds a system-test layer on top of Playwright.

```ts
const { test, expect, scenario, outline } = defineSystemTest({
  bootstrap: async ({ workerInfo, perWorker }) => {
    return connectToSystem(workerInfo, perWorker);
  },
});
```

The important parts are:

| Blackbox API | Role |
| --- | --- |
| `defineSystemTest(...)` | Creates the Playwright test fixture shape used by the suite |
| `bootstrap(ctx)` | Connects the worker process to the correct SUT boundary |
| `system` fixture | User-facing handle for the running system |
| `capture` fixture | Captures spans/effects for the active test and enables catalog matchers |
| `isolation` fixture | Forces the per-test isolation lifecycle even when no effects are captured |
| `scenario(...)` | Defines a behavior flow with a fresh isolation group |
| `scenario.chain(...)` | Defines an ordered shared-state chain that runs serially on one worker |
| `outline(...)` / `given.each(...)` | Runs one behavior shape across example rows |

Use this layer when the test is meant to produce Blackbox evidence. Plain Playwright can still run, but the Blackbox API is what gives system tests their isolation and artifact semantics.

## Worker Isolation

With compose isolation enabled, each Playwright worker gets its own composed system boundary.

```bash
BLACKBOX_ISOLATION=compose npx playwright test --workers 2
```

That means:

1. Worker 0 can run against one compose project.
2. Worker 1 can run against another compose project.
3. Docker-assigned host ports prevent worker port collisions.
4. `bootstrap(ctx)` receives worker context so test code connects to the right boundary.
5. Coverage, shape coverage, and feature traces are written as worker partials and merged later.

This is the core reason Blackbox can support parallel system tests. A parallel test is only trustworthy when its state and evidence are attributable.

## Scenario Isolation Groups

Worker isolation separates concurrent worker processes. Scenario isolation separates behavior inside a worker.

The Scenario DSL emits runtime tags such as:

```text
@flow:refund-flow
@isolation-group:bdd:refund-flow
```

The isolation group decides when the testbed should reset the SUT and when state should persist.

| Shape | Isolation behavior | Use it when |
| --- | --- | --- |
| `scenario(...)` | Fresh group for the scenario slug | Normal independent behavior |
| `scenario.chain(...)` | One shared group for all nested scenarios, co-located on one worker in serial order | A later scenario intentionally depends on state from an earlier scenario |
| `outline(...)` | One behavior shape over rows | The same rule should be exercised with examples |

This is how Blackbox connects Playwright scheduling to behavior ownership.

## Native Playwright Mapping

If you start from native Playwright tests, the feature tooling uses the Playwright structure to recover intent:

| Native Playwright | Blackbox scenario shape |
| --- | --- |
| `test.describe.parallel(...)` siblings | Plain `scenario(...)` per independent sibling |
| `test.describe.serial(...)` chain | `scenario.chain(...)` with ordered nested scenarios |
| `test.beforeEach(...)` | `background(...)` when it is part of the behavior setup |
| Repeated row tests | `outline(...)` or `given.each(...)` |
| `expect(...)` after an action | `then(...)` |

This mapping matters for generated feature files. Gherkin gives the readable language; Playwright gives the execution structure; Blackbox supplies the isolation and runtime evidence.

Reference: [Gherkin language reference](https://cucumber.io/docs/gherkin/reference/).

## Trace And Effect Attribution

For effects to be useful, Blackbox must know which test caused them.

The preferred path is to use the Blackbox-wrapped Playwright request path through `system` or the Playwright `request` fixture. Trace propagation is automatic there.

When a test uses a custom HTTP client, raw `fetch`, `axios`, or another client Blackbox does not wrap, add the Blackbox `traceparent()` header:

```ts
import { traceparent } from '@suites/blackbox/runners/playwright';

await fetch(url, {
  method: 'POST',
  headers: { 'content-type': 'application/json', ...traceparent() },
  body: JSON.stringify(payload),
});
```

That keeps runtime spans attributable to the active test even when the test does not use Playwright's request fixture.

## What Can Still Break Parallel Proof

Blackbox can provide worker isolation and group isolation. It cannot make an unmanaged shared external dependency deterministic.

Be careful when a parallel run touches:

1. A shared remote database that the testbed does not own.
2. A shared queue without per-worker queue names or per-worker stacks.
3. A shared cache namespace.
4. A third-party auth, email, payment, or vendor API.
5. A custom client that does not propagate trace identity.

This does not mean Blackbox lacks parallel support. It means the test environment must route state and evidence through the isolation model.

## Concurrent Runs on One Host

<Aside type="warning" title="Known limitation: two runs sharing the same projectNames base">
Each worker-process incarnation gets a unique compose project name in the form `<base>-w<parallelIndex>-i<workerIndex>`. At `globalSetup` and `globalTeardown`, Blackbox sweeps all compose projects matching that pattern and runs `docker compose down -v` on each match.

Project names are unique per incarnation within a single run, not across two overlapping runs on the same host.

**When the hazard triggers (all three must be true):**

- Two Blackbox runs are active at the same time on the same host.
- Both runs share the same `projectNames.baseline` (or `projectNames.functionSpans`) base string.
- One run's `globalSetup` or `globalTeardown` fires while the other run's workers are still up.

In that situation the sweeping run matches and downs the live stacks of the other run, deleting their volumes.

A single local run, or CI with one job per machine, is not affected.

**Mitigation:** set a distinct `projectNames` per concurrent run. For CI, inject the job identifier:

```ts
createBlackboxTestbed({
  projectNames: {
    baseline: `blackbox-e2e-${process.env.CI_JOB_ID ?? 'local'}`,
    functionSpans: `blackbox-fn-${process.env.CI_JOB_ID ?? 'local'}`,
  },
  // ...
});
```

With distinct base names the sweep for one run cannot match the other run's projects.
</Aside>

## Practical Defaults

For the strongest system-test gate:

1. Use `BLACKBOX_ISOLATION=compose` or an equivalent custom isolation adapter.
2. Prefer `system.request` or the wrapped Playwright `request` fixture.
3. Use plain `scenario(...)` for independent behavior.
4. Use `scenario.chain(...)` only when the dependency between flows is intentional.
5. Keep managed dependencies inside the testbed when the result should block CI.
6. Use remote E2E environments as evidence first, then gate only when the environment is stable enough.
