Add Blackbox to CI after one behavioral contract runs locally. CI should repeat the same validation and execution path, then preserve the result that explains any failure.

## 1. Validate Before Runtime Work

```text title="Conceptual pseudocode"
<validate behavioral contract>
<validate system-test binding>
```

Use the commands published for the installed Blackbox distribution. A direct declaration does not need Gherkin validation.

## 2. Run the Selected Contract Cases

```text title="Conceptual pseudocode"
<run selected contract cases with Blackbox>
```

Each physical attempt receives fresh runtime identity, capture, evidence, and teardown. Shards and workers cannot merge evidence between attempts.

## 3. Gate on the Process Exit

| Exit | CI action                                                             |
| ---- | --------------------------------------------------------------------- |
| `0`  | Continue.                                                             |
| `1`  | Fail the verification gate and route the finding.                     |
| `2`  | Fix the invocation, configuration, project root, or unreadable input. |

Exit `1` covers formed non-success outcomes, including violated, inconclusive, unsupported, integrity-failure, and unknown finding-code cases.

## 4. Preserve the Result

Store the report and exact evidence references for each attempt. Preserve verdicts, repair routing, and prior retry history.

Presentation and retention choices can change how a result is displayed or stored. They cannot change the canonical result.

## 5. Keep Observable Decision Coverage Separate

Observable Decision Coverage is optional per run and diagnostic. Its availability or classification cannot change an ordinary effect finding or the ordinary verification exit.

## Summary

- Validate the behavioral contract and system-test binding first.
- Give each physical attempt fresh evidence.
- Preserve the finding that explains a failed gate.
- Keep optional decision analysis outside the ordinary effect gate.
