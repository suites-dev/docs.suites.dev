Blackbox reports answer different questions. Read the narrowest failure first instead of treating `.blackbox-coverage/` as one score.

## Report Map

| Artifact                     | Question                                                                                    |
| ---------------------------- | ------------------------------------------------------------------------------------------- |
| `catalog/coverage.json`      | Which flow contracts were satisfied, failed, or uncovered?                                  |
| `shape/coverage.json`        | Which catalog clauses were asserted, unasserted, or inline-only?                            |
| `omcdc/verdict.md`           | Which decisions propagated to distinguishable effects, were masked, or lacked arm coverage? |
| `omcdc/verdict.html`         | Where in source did those decision verdicts occur?                                          |
| `omcdc/verdict.json`         | What structured OMC/DC data should automation consume?                                      |
| `requirements/coverage.json` | Which EARS requirements are proven, violated, unproven, or unbound?                         |
| reporter outputs             | What human summary, HTML, JUnit, or CI annotation should be published?                      |

Catalog and shape coverage are the default runtime-evidence views. OMC/DC is available when the Node adapter registers its coverage producer. Requirement coverage is written by the requirements CLI after the Playwright run.

## Reading Order

1. Start with the failing Playwright test and matcher message.
2. Open `catalog/coverage.json` to identify the affected flow.
3. Open `shape/coverage.json` when the issue is an unasserted clause or inline-only effect.
4. Inspect OMC/DC only when the review question concerns decision propagation or missing arms.
5. When using EARS, run requirement coverage to see which normative requirements inherit the runtime result.

Do not begin with a global percentage. A single forbidden payment call in a rejected-user flow matters more than a high aggregate count.

## Catalog Coverage

The terminal summary mirrors the JSON artifact:

```text
effect coverage
metric           value
catalog entries  2
satisfied        2  (100%)
failed           0
uncovered        0
```

For each entry, inspect `runs`, `passes`, `failures`, and `forbidViolations`. A `failed` entry means the flow ran but no captured run satisfied its contract. An `uncovered` entry means the current suite did not check it.

Configure the Playwright reporter to fail on either condition when the suite is mature:

```ts
blackboxReporter({
  outputDir: "./e2e/.blackbox-coverage",
  failOnUncovered: true,
  failOnAlwaysFailing: true,
});
```

## OMC/DC Reports

Read verdicts as evidence quality:

- `propagating`: both arms were exercised and their effect signatures differed;
- `masking-candidate`: both arms were exercised but the signatures were identical;
- `coverage-gap`: only one arm was exercised;
- `undecidable`: the run could not support a sound comparison;
- `multi-arm` and `unsupported-mcdc`: the decision needs manual treatment.

Use `verdict.md` for review, HTML for source inspection, and JSON for automation. Do not automatically fail every non-propagating branch. Choose critical decisions and make the policy explicit.

## Requirement Verdicts

After the Playwright run:

```bash
pnpm exec blackbox requirements coverage \
  --tests e2e \
  --coverage e2e/.blackbox-coverage/catalog/coverage.json \
  --fail-on violated \
  --json
```

`--fail-on violated` is the conservative first gate. Move to `unproven` or `unbound` only when every selected requirement is expected to have complete bindings and runtime evidence in that job.

## Minimal CI Sequence

The core gate is the project-owned Playwright command:

```bash
pnpm install --frozen-lockfile
pnpm build:instr-image
npx playwright test --config ./e2e/playwright.config.ts
```

Configure Playwright with `updateSnapshots: 'none'` in CI and fail on uncovered or failing catalog entries when the suite is ready. That creates an effects-only behavioral gate.

If EARS requirements and bindings are part of review, add the requirement gate after Playwright:

```bash
pnpm exec blackbox requirements check --tests e2e --json
pnpm exec blackbox requirements coverage \
  --tests e2e \
  --coverage e2e/.blackbox-coverage/catalog/coverage.json \
  --fail-on violated \
  --json
```

If committed Gherkin is part of review, add:

```bash
pnpm exec blackbox features lint ./e2e/tests --fail-on error --json
pnpm exec blackbox features check \
  --features ./e2e/features \
  --tests ./e2e/tests \
  --json
```

Do not add feature commands when the team does not maintain feature files.

## Prevent CI Baselines

CI verifies reviewed behavior; it should not create it.

```ts title="e2e/playwright.config.ts"
export default defineConfig({
  updateSnapshots: process.env.CI ? "none" : "missing",
});
```

In verify-only mode, a missing effect-catalog entry fails and the recorder does not write a baseline. Keep update jobs separate and review their catalog and feature diffs.

<Aside type="warning" title="Upload Evidence on Failure">
  Always retain `.blackbox-coverage/` when the job fails. Without the catalog,
  shape, OMC/DC, requirement, and diagnostic artifacts, a reviewer sees a red
  gate without the evidence needed to act.
</Aside>

## Reporter and Sink Behavior

The current default reporter is the effects report. The default sink writes files; GitHub Actions adds the GitHub Actions sink when that environment is detected. Additional registered reporters can produce HTML and JUnit views.

Use the [Reference hub](/docs/blackbox/reference) for the current reporter, sink, artifact, and exit-code contracts.

## Replay Saved OMC/DC Inputs

When a coverage directory contains the required saved inputs, regenerate OMC/DC outputs without rerunning the SUT:

```bash
pnpm exec blackbox coverage replay \
  --coverage-dir ./e2e/.blackbox-coverage \
  --out ./reports
```

Pass `--no-html` when automation needs only JSON and Markdown.
