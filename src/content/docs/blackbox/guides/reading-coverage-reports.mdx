## The two reports

Blackbox writes two summary reports for **effect coverage**, the report view that checks whether the run proved declared boundary behavior:

| Report | What it answers | Use it for |
| --- | --- | --- |
| `catalog/coverage.json` | Did each catalog entry pass, fail, or remain uncovered? | Reviewing the catalog rollup for CI and release gates |
| `shape/coverage.json` | Which boundary shapes were asserted, observed, declared, or only seen inline? | Finding missing behavior proof at the Redis, Postgres, HTTP, SQS, or other boundary-shape level |

`catalog/coverage.json` works at catalog-entry grain. A `subscribe-flow` entry can be satisfied as a whole, failed because required or forbidden behavior did not match, or uncovered because no passing run proved it.

`shape/coverage.json` works at boundary-shape grain. **Shape coverage** shows whether a specific shape, such as `postgres INSERT subscriptions` or `http POST /v1/payment_intents`, was declared in the catalog, named by a matcher, and observed during the run.

For the exact artifact list and stability notes, read [Report Formats](/docs/blackbox/reference/report-formats).

## Recommended reading order

Do not start with raw JSON. Open `omcdc/verdict.md` first to find the coverage gaps in a human-readable table, then use `omcdc/verdict.html` when you need to inspect a branch, source coordinate, or evidence trail.

Use this order when you review a Blackbox run:

1. Open `omcdc/verdict.md` and scan endpoint headings.
2. Find endpoints with `coverage-gap` or `masking-candidate` counts.
3. Open `omcdc/verdict.html` for a deeper branch-level view.
4. Check `catalog/coverage.json` to confirm whether the catalog entries passed, failed, or stayed uncovered.
5. Check `shape/coverage.json` to find declared shapes that were not asserted, inline shapes that should move into the catalog, and observed shapes that need a stronger behavior proof.
6. Use `omcdc/verdict.json` only when automation or an agent needs the structured OMC/DC result.

The `omcdc/verdict.md` report gives you a compact table before you inspect raw JSON. A `subscribe-flow` excerpt looks like this:

```markdown
## POST /subscriptions

_7 test(s) exercised this endpoint._

| Branch | True path verdict | False path verdict | Decision masked? |
| --- | --- | --- | --- |
| `if (isKnownUser)` | `propagating` - subscription effects continue | `propagating` - returns `404` before Stripe | No |
| `if (paymentIntentCreated)` | `propagating` - inserts subscription row | `coverage-gap` - payment decline path missing | No |
| `if (subscriptionInsertSucceeded)` | `propagating` - queues welcome message | `coverage-gap` - skipped insert path missing | No |
| `if (tierCacheWriteSucceeded)` | `coverage-gap` - Redis write observed once | `coverage-gap` - cache miss arm missing | No |
| `if (sqsQueued)` | `propagating` - `SubscriptionStarted` sent | `coverage-gap` - not-queued recovery missing | No |

Summary: 4 propagating, 0 masking-candidate, 9 coverage-gap.
```

The `omcdc/verdict.html` report shows the same evidence as an expandable branch hierarchy. The HTML view lets you open each decision, compare true and false arms, and inspect the effects attached to each verdict:

```text
omcdc/verdict.html
`- Scenario: subscribe-flow
   `- POST /subscriptions [7 tests]
      |- if (isKnownUser) [propagating]
      |  |- TRUE  [ok] postgres SELECT users, stripe payment intent
      |  `- FALSE [ok] response 404, no stripe, no sqs
      |- if (paymentIntentCreated) [coverage-gap]
      |  |- TRUE  [ok] postgres INSERT subscriptions
      |  `- FALSE [gap] not observed
      `- if (sqsQueued) [propagating]
         |- TRUE  [ok] sqs SendMessage SubscriptionStarted
         `- FALSE [ok] response 500, no cache write
```

If you need the model behind the verdicts before reading a report, start with [OMC/DC Coverage](/docs/blackbox/concepts/omc-dc-coverage).

## Reading OMC/DC verdicts

An **OMC/DC verdict** tells you whether the run proved that a decision changed observable behavior. The report groups verdicts by endpoint and then lists each branch with true-arm, false-arm, and not-observed counts.

| Verdict | Meaning | Typical action |
| --- | --- | --- |
| `propagating` | The branch arms produced distinguishable observed effects. | Usually good; review whether the effects are the intended ones. |
| `masking-candidate` | Both arms ran, but their observed effect signatures looked identical. | Add better tests, more distinguishing effects, or enable function spans when appropriate. |
| `coverage-gap` | One or more arms were not observed enough to make the decision useful. | Add or adjust a scenario. |
| `undecidable` | The engine could not make a useful decision from the available evidence. | Inspect instrumentation and source mapping. |
| `multi-arm` | The decision shape is more complex than the simple two-arm case. | Review manually and simplify or split if needed. |
| `unsupported-mcdc` | The current engine does not support this decision shape. | Treat as an alpha limitation, not a pass. |

Read `propagating` as proof strength, not as a blanket approval of the implementation. It means the observed evidence distinguished the arms.

Read `masking-candidate` as a prompt to improve the evidence. The application may be correct, but the current run made both arms look the same from the observed boundary effects.

Read `coverage-gap` as missing proof. It does not prove the behavior is wrong; it says the run did not exercise enough of the decision to make a useful claim.

## Case study: Subscription Flow

The showcase `subscribe-flow` run includes the `POST /subscriptions` endpoint from the pro-tier subscription workflow. The Markdown report makes the first useful fact visible before you open any raw artifact:

```markdown
_7 test(s) exercised this endpoint._

| verdict | count |
|---|---|
| propagating | 4 |
| masking-candidate | 0 |
| coverage-gap | 9 |
| multi-arm | 0 |
| undecidable | 0 |
```

The line `_7 test(s) exercised this endpoint._` tells you that seven tests reached `POST /subscriptions`. The verdict table tells you what those tests proved:

1. `4` branches were `propagating`, so the run distinguished those decision arms through observable effects.
2. `0` branches were `masking-candidate`, so no reached branch had both arms collapse into the same observed effect signature.
3. `9` branches were `coverage-gap`, so the team still needs scenarios that hit missing arms.

Read that next to the `subscribe-flow` catalog entry. The successful subscription path requires a Redis tier lookup, Postgres user lookup, Stripe payment-intent call, subscription insert, Redis tier cache write, order-service call, and SQS message. It forbids destructive or wrong effects such as Postgres `DELETE`, Postgres `TRUNCATE`, Redis `DEL`, Redis `FLUSHDB`, and refund creation.

That contract changes the review question. You are not only checking whether `POST /subscriptions` returned `201`. You are checking whether the run proved the promised cross-boundary behavior and avoided the forbidden effects.

The same showcase also includes `ghost-user`, where the system should consult Redis and Postgres, return `404`, and stop before Stripe or SQS. Use that path when you want to verify that the report proves a non-event, not only a successful write path.

## Finding the useful gap

The most useful shape-coverage signal is the difference between a shape that was declared, a shape that was asserted, and a shape that was observed.

In `shape/coverage.json`, watch for rows where `asserted` is `0` and `observed` is greater than `0`. That pattern means the run saw boundary behavior, but no matcher made it part of the behavior proof. Treat it as a missing assertion or a catalog ownership question.

Use the pattern this way:

1. Find the row with `asserted: 0` and `observed: N`.
2. Check the `shape` fields to identify the boundary, operation, and key.
3. Decide whether the behavior belongs in the catalog as a required or forbidden shape.
4. Add or update the matcher so the next run proves the behavior intentionally.

This is where `shape/coverage.json` complements the OMC/DC report. The OMC/DC verdict tells you whether decisions produced distinguishable effects. The shape report tells you whether important effects were actually asserted as behavior the team owns.
