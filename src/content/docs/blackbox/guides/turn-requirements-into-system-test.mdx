Use this guide as the alternate Quickstart Step 1 when you have no system or E2E test yet. Start with one behavior you can describe in plain language. You do not need an existing EARS requirement or Gherkin file. This guide creates the tagged test shell; Quickstart Step 2 connects the application and makes it runnable.

## Install Blackbox

Install the public facade, CLI, and Playwright:

```bash
pnpm add -D @suites/blackbox @suites/blackbox-cli @playwright/test
```

Keep all `@suites/blackbox*` packages on the same version.

If you want a coding agent to propose EARS or review Gherkin, [install the Blackbox Skills first](/docs/blackbox/guides/agent-skills). You can also author and review both artifacts directly.

## 1. Turn the Behavior Into a Reviewable Requirement

Give `$blackbox-requirements` the goal or change request, or write the EARS requirement directly. A coding agent can propose the wording; a person approves what it means:

```text title="requirements/subscriptions.ears"
REQ-004: While the subscriber is unknown, when a subscription request is posted, the API shall respond with 404.
REQ-005: While the subscriber is unknown, when a subscription request is posted, the API shall not call the payment provider.
```

```bash
pnpm exec blackbox requirements validate ./requirements --json
```

Validation proves structural correctness. A person approves meaning.

## 2. Generate and Review Gherkin

```bash
pnpm exec blackbox features generate \
  requirements/subscriptions.ears \
  --flow subscribe-unknown-user \
  --description "rejecting a subscription for an unknown user" \
  --requirement REQ-004 \
  --requirement REQ-005 \
  --out e2e/features \
  --write \
  --json
```

Ask `$blackbox-gherkin` to review the generated scenario. The Skill proposes wording; a person accepts the final behavior and stable flow ID.

```bash
pnpm exec blackbox features check ./e2e/features --requirements ./requirements --json
```

## 3. Generate the Playwright Skeleton

```bash
pnpm exec blackbox suites generate \
  e2e/features/subscribe-unknown-user.feature \
  --out e2e \
  --write \
  --json
```

Blackbox generates the tagged structure and visible TODO bodies:

```ts
import { expect, test } from "@playwright/test";

test.describe(
  "rejecting a subscription for an unknown user",
  { tag: "@flow:subscribe-unknown-user" },
  () => {
    test("the unknown user is rejected", async ({ request }) => {
      await test.step("WHEN a subscription request is posted", async () => {
        // TODO: perform the application action.
      });

      await test.step("THEN the API responds with 404", async () => {
        // TODO: assert the visible result.
      });
    });
  },
);
```

The generator creates the tagged structure, not a working system test. Your project must still supply the real application action, assertion, fixture, test data, and any startup or reset behavior. Quickstart Step 2 connects the application and changes the import to the Blackbox fixture; complete the TODOs there, then run Playwright until the native test passes.

## 4. Check the Chain

```bash
pnpm exec blackbox requirements check ./requirements --tests ./e2e --json
pnpm exec blackbox requirements drift ./requirements --tests ./e2e --json
pnpm exec blackbox suites check ./e2e --json
```

## Result

The approved requirement, reviewed scenario, and tagged Playwright shell now share one flow identity. Continue with [Quickstart Step 2: Connect a Host-Command SUT](/docs/blackbox/quickstart/add-to-existing-test), complete the application-specific TODOs, and run until the native test passes. You can replace that provisioning with another [SUT setup](/docs/blackbox/guides/set-up-the-testbed).
