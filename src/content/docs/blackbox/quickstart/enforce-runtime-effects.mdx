Step 3 captured what the running system did. This step decides which effects express behavior the team intends to protect.

<Aside type="info" title="Alpha Target">
  Effect semantics are the committed core. The public catalog and claim syntax,
  execution commands, report format, and certified support matrix are not
  frozen. This step documents the review workflow without inventing them.
</Aside>

## 1. Name the Effects That Matter

For the unknown-user case, the accepted response is `404`. The hidden behavior also matters:

| Effect intent                  | Accepted claim |
| ------------------------------ | -------------- |
| `user-record-read`             | At least once. |
| `payment-charge-request`       | Exactly zero.  |
| `subscription-record-written`  | Exactly zero.  |
| `subscription-order-published` | Exactly zero.  |

Use catalog vocabulary to name portable effects. Do not couple accepted claims to raw span names, trace IDs, or incidental attributes.

[See what the Effects Catalog contract owns](/docs/blackbox/reference/catalog-schema).

## 2. Approve Claims Per Concrete Case

Review each presence, absence, or cardinality claim as product policy. Do not copy every observed effect into the accepted target.

The known-user and unknown-user cases may share catalog vocabulary while accepting different claims. Keep those policies attached to their concrete cases instead of weakening one flow-wide rule.

Changes to accepted claims return to a person. A coding agent may explain observed behavior and propose a repair, but it cannot approve a new success condition.

## 3. Analyze the Sealed Attempt

The Analyzer compares the approved claim with eligible matching facts from the same sealed attempt. It preserves separate results for:

- The native system test.
- Evidence integrity.
- Each effect claim.
- Optional ODC analysis.

A planned report can connect those results, but one result does not rewrite another.

```text title="Illustrative report"
CASE unknown user is rejected
  native test        satisfied
  evidence integrity eligible
  user-record-read   satisfied   observed 1
  payment request    violated    observed 1, expected exactly 0
  ODC                separate Alpha finding
```

The report format above is illustrative. [See the current report contract boundary](/docs/blackbox/reference/report-formats).

## 4. Let Evidence Bound the Result

One observed forbidden payment request is enough to establish a violation. Zero observed payment requests establish satisfaction only when the required capture scope is complete.

[Look up the cardinality and completeness rules](/docs/blackbox/reference/matchers-and-effect-builders).

## 5. Repair Without Redefining Success

If the unknown-user case returns `404` but still requests payment, the coding agent repairs the implementation and runs the same accepted case again with fresh capture.

Changes to Gherkin, claims, lifecycle requirements, isolation, or gate policy return to human review because they change the target or proof burden.

## 6. Read ODC Separately

Observable Decision Coverage asks whether exercised decision outcomes produced distinguishable effect signatures. It cannot change the native result or an ordinary effect finding.

ODC is an Alpha target. Keep it report-only until its accepted policy and support cell deliberately make it a gate.

## Result

You have one approved case, explicit effect claims, sealed runtime evidence, deterministic findings, and a bounded implementation-repair loop.
