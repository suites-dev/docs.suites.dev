Step 3 recorded facts. This step decides which facts express behavior the team intends to protect, then applies that reviewed policy to the immutable run.

## 1. Approve the Effect Policy

An **effect contract** lists runtime actions that must happen and actions that must not happen. For this flow, require the user lookup and forbid a payment request:

```yaml title="e2e/features/subscribe-user.effects.yaml"
specVersion: "0.1"
flow: subscribe-user

requires:
  - { boundary: postgres, op: SELECT, key: users, service: api }

forbids:
  - { boundary: http, op: POST, key: /v1/payment_intents, service: api }
```

Review this file as policy. Do not copy every observation into it.

This contract contains rules shared by both attempts. The successful attempt's `INSERT subscriptions` remains useful decision evidence, but it is not required for the unknown-user attempt. Protect behavior that applies to only one case with a separately scoped flow or policy rather than weakening the meaning of `requires`.

## 2. Analyze Without Mutating the Run

```bash
pnpm exec blackbox analyze --run latest
```

The original evidence remains sealed. Blackbox writes a derived analysis result that identifies both inputs:

```text
evidence  sha256:7b1c…
policy    sha256:95af…

FLOW subscribe-user
  tests       PASS    2 attempts
  integrity   PASS    capture complete
  effects     PASS    required and forbidden policy satisfied
  ODC         REPORT  user-exists outcomes produced distinct evidence
```

Changing the contract creates a new policy digest and derived result; it does not rewrite what the application did. The next `blackbox test` run snapshots the accepted policy alongside its new evidence.

## 3. Read ODC as a Separate Signal

**Observable decision coverage (ODC)** compares the effect signatures associated with exercised decision outcomes. The report for this flow can show:

```text
DECISION user-exists
  known-user    SELECT users → INSERT subscriptions
  unknown-user  SELECT users
  result        PROPAGATING
```

`PROPAGATING` means the two outcomes produced distinguishable effects. Other results are:

- **Masking candidate:** both outcomes ran but their effect signatures matched.
- **Coverage gap:** only part of the decision was exercised.
- **Undecidable:** the available evidence cannot support a sound comparison.

A passing effect contract does not imply strong ODC, and a propagating decision does not prove that its behavior is correct.

## 4. Repair Without Redefining Success

Suppose the unknown-user attempt returns `404` but still calls the payment provider:

```text
FLOW subscribe-user
  tests       PASS
  integrity   PASS
  effects     FAIL

  forbidden effect observed
  http POST /v1/payment_intents service=api
```

The coding agent changes implementation and reruns the same accepted flow until the forbidden effect disappears.

```text
finding → repair implementation → blackbox test → new sealed evidence
```

Changes to the native assertion, flow identity, reviewed feature, effect contract, application lifecycle, isolation configuration, or ODC gate return to human review because they redefine success.

## 5. Gate ODC Only After Review

The Quickstart reports ODC first. When the team accepts this decision as a merge gate, make the policy explicit:

```ts title="blackbox.config.ts"
analysis: {
  effects: "check",
  odc: "check",
}
```

Keep ODC report-only while the team is still deciding which decision outcomes must remain observably different.

## Result

You completed both Blackbox loops with one stable flow: readable intent aligned to a passing system test, sealed runtime evidence, an approved effect verdict, an ODC report, and a bounded implementation-repair loop.
