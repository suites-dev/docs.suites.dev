Start with one product-cache requirement: both reads of product `42` succeed, and the second read reuses cached data so the case performs at most one Postgres read.

```text
approved behavior → Playwright realization → running Compose system
                  → fresh evidence → effect finding
```

## 1. Choose an Authoring Mode

Both authoring modes produce the same accepted SuitePlan meaning.

<Tabs groupId="blackbox-authoring-mode">
  <TabItem value="gherkin" label="Reviewed Gherkin" default>

Use Gherkin when a readable scenario helps people review the behavior.

```gherkin title="features/product-cache.feature"
Feature: Product cache
  Scenario: Reuse a cached product
    When product 42 is read twice
    Then both reads succeed
    And at most one Postgres product read occurs
```

Validate the authored feature:

```bash
blackbox features check
blackbox scenarios check
```

  </TabItem>
  <TabItem value="direct" label="Direct declarations">

Use direct declarations when the team does not use Gherkin. Approve the same case, visible result, effect claim, completion requirement, capabilities, and topology directly.

```text title="Conceptual declaration, not public syntax"
case: read product 42 twice
visible result: both reads return 200
effect claim: at most one Postgres SELECT on products
```

Validate the compiled semantic and executable closure:

```bash
blackbox scenarios check
```

  </TabItem>
</Tabs>

A person approves the behavior. Observed effects cannot create or silently change it.

## 2. Realize the Case in Playwright

Blackbox generates the accepted Playwright binding surface:

```text
suite.spec.ts
suite.runtime.ts
suite.d.ts
plan.json
```

The project completes the concrete requests, fixtures, and native assertions. Exactly one discovered Playwright test must bind the selected case.

```bash
blackbox suites typecheck
```

Already have a passing test? Follow [Start From an Existing Test](/docs/blackbox/quickstart/build-behavioral-harness) to bind it without treating current behavior as the requirement.

## 3. Connect the Running System

Use [Connect Your Application With Compose](/docs/blackbox/quickstart/add-to-existing-test) to give each attempt a controlled application, network, storage, and lifecycle boundary.

Blackbox runs the selected case only after semantic closure, runner alignment, provider capability admission, and participant readiness succeed.

## 4. Read the Result

The native test and effect claim remain separate:

```text
Native test       both GET /products/42 responses returned 200   PASS
Effect claim      Postgres SELECT products observed 2 times      VIOLATED
Approved limit    at most 1
```

The coding agent can repair Redis use and rerun the case with fresh evidence. Only a person can approve a different requirement.

## What Success Looks Like

- Authored behavior and generated realization close exactly.
- The selected Playwright test produces its native result.
- Fresh evidence is eligible for the claim scope.
- Every selected claim receives one of the five deterministic verdicts.
