Start here when you already have a system or E2E test for consequential behavior. The test shows how the system currently runs, but it does not become approved intent automatically.

If no system test exists, use [Step 1B: Start Without a Test](/docs/blackbox/quickstart/start-without-test).

<Aside type="info" title="Alpha Target">
  The Gherkin-to-suite alignment workflow is accepted for Alpha 3. Public
  commands, generated filenames, and package APIs are not frozen here.
</Aside>

## 1. Choose One Consequential Test

Use a case whose hidden behavior matters, such as rejecting an unknown subscriber without charging them.

Confirm that the native test passes before using it as recovery evidence. A green response assertion does not prove that the system avoided forbidden downstream work.

## 2. Recover a Gherkin Proposal

Read the existing test, known product intent, and observed runtime behavior. Draft one readable scenario:

```gherkin
Scenario: Reject an unknown user without creating downstream work
  When an unknown user submits a subscription request
  Then the response status is 404
  And no payment charge is requested
```

Treat the draft as a proposal. A person reviews the scenario, concrete case identity, effect claims, and success policy before Blackbox compiles them.

Do not infer accepted meaning only from test titles, source order, or what the current implementation happens to do.

## 3. Compile the Approved Intent

Blackbox compiles the approved Gherkin into a SuitePlan and projects generated type and runtime binding contracts for the executable suite.

Compilation stops when a scenario, Examples row, instruction, claim, contract, or topology relationship is missing or ambiguous.

## 4. Align the Existing Suite

Repair the project-owned test against the generated type contract. Preserve its real actions and native assertions while binding them to the exact accepted case and claims.

The suite is ready only when every accepted case has one complete runnable realization. Empty, skipped, stale, redirected, or duplicate bindings block runtime verification.

## 5. Read the Alignment Result

Before continuing, confirm that:

- The approved Gherkin produced one stable concrete case.
- The generated contract and project-owned test agree.
- Runner collection finds exactly one declared realization.
- A RunnerBundle can be lowered and a non-empty RunPlan selected.

[Use the full alignment guide](/docs/blackbox/guides/recover-behavior-from-existing-tests) when a check fails.

## Result

You have approved Gherkin and one aligned executable realization. Continue with [Step 2: Connect Your Application](/docs/blackbox/quickstart/add-to-existing-test).
