Start here when you already have a system or E2E test. The test can realize approved behavior, but it cannot define that behavior by itself.

```ts title="tests/product-cache.e2e.spec.ts"
import { expect, test } from "@playwright/test";

test("reuses a cached product", async ({ request }) => {
  const first = await request.get("/products/42");
  const second = await request.get("/products/42");

  expect([first.status(), second.status()]).toEqual([200, 200]);
});
```

This test establishes the visible result. It does not say whether the implementation may query Postgres twice.

## 1. Approve the Intended Behavior

Review the product requirement with a person. Express it as linked Gherkin or direct behavioral declarations.

For this case, approve:

- Both reads return `200`.
- The case performs at most one Postgres product read.
- The declared Postgres observation and completion capabilities cover that upper-bound claim.

Do not reverse-generate product meaning from the test, telemetry, or current implementation.

## 2. Validate Accepted Meaning

For Gherkin-linked authoring, run:

```bash
blackbox features check
blackbox scenarios check
```

For direct declarations, run `blackbox scenarios check`.

Blackbox refuses missing, ambiguous, stale, duplicate, or redirected semantic relations before runtime allocation.

## 3. Bind the Existing Test

The generated Playwright directory contains exactly:

```text
suite.spec.ts
suite.runtime.ts
suite.d.ts
plan.json
```

Use the generated TypeScript surface to bind the approved case to the existing requests and assertions. Do not add new behavior during runner realization.

```bash
blackbox suites typecheck
```

The selected case is ready when Playwright discovery finds exactly one matching test and every required relation resolves exactly once.

## Result

The existing test now realizes approved meaning without becoming its authority. Continue with [Connect Your Application With Compose](/docs/blackbox/quickstart/add-to-existing-test).
