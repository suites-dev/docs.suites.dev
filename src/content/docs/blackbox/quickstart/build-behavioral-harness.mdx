Start here when you already have a passing Playwright system or E2E test. Keep its working action and assertion, assign one stable `@flow:<id>`, then generate a readable behavior proposal from the executable flow.

If you do not have a system test yet, use [Step 1B: Start Without a Test](/docs/blackbox/quickstart/start-without-test).

## 1. Install Blackbox

Install the public facade, CLI, and Playwright:

```bash
pnpm add -D @suites/blackbox @suites/blackbox-cli @playwright/test
```

Keep all `@suites/blackbox*` packages on the same version.

## 2. Choose One Consequential Flow

Use a flow whose hidden behavior matters. This example checks both outcomes of the user-exists decision.

```ts title="e2e/subscribe-user.system.test.ts"
import { expect, test } from "@playwright/test";

test.describe("subscribe user", { tag: "@flow:subscribe-user" }, () => {
  test("known user is subscribed", async ({ request }) => {
    const response = await request.post("/subscriptions", {
      data: { userId: "alice" },
    });

    expect(response.status()).toBe(201);
  });

  test("unknown user is rejected", async ({ request }) => {
    const response = await request.post("/subscriptions", {
      data: { userId: "ghost" },
    });

    expect(response.status()).toBe(404);
  });
});
```

The flow ID is an identity, not prose. Keep `subscribe-user` stable when descriptions change.

## 3. Confirm the Native Test Passes

Run the test with the command your project already uses:

```bash
pnpm exec playwright test e2e/subscribe-user.system.test.ts
```

Expected result:

```text
2 passed
```

The assertions prove the visible responses. They do not yet prove what the application did behind those responses.

## 4. Generate and Review Readable Behavior

The runtime loop does not require Gherkin. This Quickstart includes one feature so you can experience the behavior-alignment loop before runtime capture.

Emit a proposal from the executable suite:

```bash
pnpm exec blackbox features emit ./e2e --out ./e2e/features
```

Review the generated behavior:

```gherkin title="e2e/features/subscribe-user.feature"
@flow:subscribe-user
Feature: Subscribe a user

  Scenario: Known user is subscribed
    When the client subscribes user "alice"
    Then the response status is 201

  Scenario: Unknown user is rejected
    When the client subscribes user "ghost"
    Then the response status is 404
```

Generated wording is a proposal, not accepted product intent. Edit it until a person agrees that it describes the executable behavior without exposing implementation detail.

## 5. Check the Alignment

```bash
pnpm exec blackbox features check ./e2e/features --json
pnpm exec blackbox suites check ./e2e --json
```

Expected result: both commands exit successfully and report one aligned `subscribe-user` flow. The feature and Playwright test use the same stable identity.

For bulk recovery, alignment writes, requirement binding, and drift handling, use [Add Readable Behavior Specifications](/docs/blackbox/guides/recover-behavior-from-existing-tests) after the Quickstart.

## Result

You have one passing Playwright flow and one reviewed readable feature joined by `@flow:subscribe-user`. The behavior-alignment loop is ready to enter runtime verification.

Continue with [Step 2: Connect Your Application](/docs/blackbox/quickstart/add-to-existing-test).
