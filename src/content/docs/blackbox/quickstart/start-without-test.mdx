Start here when the team knows the intended behavior but has no system or E2E test for it yet. A coding agent can propose the scenario and implementation, while a person approves the intent before runtime verification begins.

<Aside type="info" title="Alpha Target">
  The Gherkin-to-suite compiler and generated binding workflow are Alpha 3
  targets. Public commands, filenames, and package APIs are not frozen here.
</Aside>

## 1. Write One Reviewable Scenario

Express the behavior in Gherkin before implementing the system test:

```gherkin
Scenario: Reject an unknown user without creating downstream work
  When an unknown user submits a subscription request
  Then the response status is 404
  And no payment charge is requested
  And no subscription record is written
```

Keep the scenario focused on public behavior and consequential effects. Do not encode Playwright details, service topology, or telemetry structure into the prose.

## 2. Approve the Intent and Claims

A person approves:

- The concrete case and stable identity.
- The visible outcome.
- Required and forbidden effect claims.
- Any ordering, shared-state, or comparison relationship.
- The analysis policy that determines success.

A coding agent may propose these inputs. It cannot accept its own interpretation as product intent.

## 3. Compile the Binding Contracts

Blackbox compiles the approved Gherkin into a SuitePlan. It projects generated type and runtime binding contracts that guide the project-owned Playwright suite.

Compilation must resolve every scenario, instruction, claim, contract, and topology relationship exactly once. Missing or ambiguous meaning stops before suite implementation or runtime work can be treated as assurance.

## 4. Implement the System Suite

Use the generated type contract as feedforward for the test implementation. Add the real application actions and native assertions required by the accepted case.

The agent can repair the suite until it typechecks and binds exactly. Changes to Gherkin, effect claims, or policy return to a person.

## 5. Close the Alignment Gates

Blackbox checks the generated contract and suite together, collects the declared runner target, lowers one exact RunnerBundle, and selects a non-empty RunPlan.

The alignment is ready when no missing, extra, duplicate, redirected, stale, foreign, empty, or skipped relation remains.

[See the exact blocking conditions](/docs/blackbox/reference/alignment-checks).

## Result

You have one approved behavior and one declared executable realization. Continue with [Step 2: Connect Your Application](/docs/blackbox/quickstart/add-to-existing-test).
