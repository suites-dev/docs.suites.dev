Continue with one tagged flow that passes through the configured Blackbox environment. This step turns runtime observations into a reviewed effect contract and a deterministic effect verdict.

## 1. Capture What the System Did

Run the flow:

```bash
pnpm exec blackbox verify --flow checkout-payment --json
```

The first run can pass without an effect contract:

```json
{
  "status": "passed",
  "data": {
    "flow": "checkout-payment",
    "verdicts": {
      "test": "passed",
      "effects": "not-configured"
    },
    "observedEffects": 6
  },
  "findings": []
}
```

`test: passed` means the native assertions passed. `effects: not-configured` means Blackbox captured evidence but has no approved effect contract to evaluate yet.

## 2. Inspect the Observations

```bash
pnpm exec blackbox effects show \
  --flow checkout-payment \
  --run latest \
  --json
```

Observed effects are generated facts for this run. They can include database operations, HTTP calls, queue messages, cache access, and other supported boundaries.

The command returns normalized effects joined to the flow and run:

```json
{
  "status": "ready",
  "data": {
    "flow": "checkout-payment",
    "runId": "run_01J_CHECKOUT",
    "effects": [
      {
        "boundary": "postgres",
        "op": "INSERT",
        "key": "orders",
        "service": "api"
      },
      {
        "boundary": "http",
        "op": "POST",
        "key": "/inventory/reservations",
        "service": "api"
      }
    ]
  },
  "findings": []
}
```

This excerpt omits incidental observations. Inspect the complete command output before deciding what belongs in policy.

## 3. Propose an Effect Contract

For the supported agentic workflow, ask the Blackbox effect skill to classify the observations:

```text
$blackbox-effects

For flow checkout-payment, inspect the latest observed effects.
Propose the smallest required and forbidden effect contract.
Do not treat every observed effect as required behavior.
Stop for human review before the policy is accepted.
```

You can also author the same YAML manually. In either workflow, a person reviews the proposal at `features/checkout-payment.effects.yaml`:

```yaml
specVersion: "0.1"
flow: checkout-payment
requires:
  - { boundary: postgres, op: INSERT, key: orders, service: api }
  - { boundary: http, op: POST, key: /inventory/reservations, service: api }
forbids:
  - { boundary: http, op: POST, key: /payments, service: api }
```

Review the diff. Keep only effects that define the behavior you intend to protect.

<Aside type="warning" title="The First Run Is Evidence, Not Truth">
  A passing baseline can contain a defect. A person decides which effects are
  required, forbidden, or incidental before the contract becomes accepted
  policy.
</Aside>

Validate the reviewed contract:

```bash
pnpm exec blackbox effects check --flow checkout-payment --json
```

Expected result:

```json
{
  "status": "valid",
  "data": { "flow": "checkout-payment", "requires": 2, "forbids": 1 },
  "findings": []
}
```

See the [Effect Contract Schema](/docs/blackbox/reference/catalog-schema) for matching fields, patterns, and count constraints.

## 4. Compute the Effect Verdict

Run the same flow again:

```bash
pnpm exec blackbox verify \
  --flow checkout-payment \
  --require-effects \
  --json
```

The result now includes an effect verdict:

```json
{
  "status": "passed",
  "data": {
    "flow": "checkout-payment",
    "verdicts": {
      "test": "passed",
      "effects": "passed"
    }
  },
  "findings": []
}
```

Blackbox exits with code `1` when the native test passes but the accepted effect contract fails:

```json
{
  "status": "failed",
  "data": {
    "flow": "checkout-payment",
    "verdicts": { "test": "passed", "effects": "failed" }
  },
  "findings": [
    {
      "code": "effect.forbidden-observed",
      "effect": { "boundary": "http", "op": "POST", "key": "/payments" }
    }
  ]
}
```

Here, **deterministic** describes the evaluation: the same normalized observations and accepted contract produce the same verdict. It does not make the system under test deterministic or turn unobserved boundaries into proof. [Runtime Evidence](/docs/blackbox/concepts/runtime-evidence) explains capture scope and blind spots.

Read the layers separately:

| Verdict | What it proves                                                  |
| ------- | --------------------------------------------------------------- |
| Test    | The native system-test assertions passed                        |
| Effects | Required runtime effects occurred and forbidden effects did not |

Optional layers make different claims. Gherkin adds structural conformance and drift checks. Requirement coverage derives verdicts from accepted flow bindings and runtime results. Observable decision coverage adds diagnostic classifications unless the team explicitly gates them. None replaces the test or effect verdict.

Inspect the joined state for the flow:

```bash
pnpm exec blackbox flows show checkout-payment --json
```

When the flow is eligible, [Observable Decision Coverage](/docs/blackbox/concepts/omc-dc-coverage) reports whether exercised decisions produced distinguishable boundary evidence. Treat it as a separate diagnostic, not as part of the effect verdict.

## 5. Give the Verdict to the Agent

A coding agent can repair implementation against the fixed harness:

```text
verify -> read deterministic finding -> repair implementation -> verify
```

The **flow boundary** is the tagged `test.describe` block and the accepted artifacts joined by its `@flow:<id>`. The agent must stop when passing requires changing that test, effect contract, requirements, Gherkin, or stable ID.

Blackbox makes these changes visible and never records an agent action as human approval. It is not a filesystem permission system. Use agent tool restrictions, code ownership, or branch protection when the agent must be technically prevented from editing accepted harness files.

A person reviews the result and either accepts it or returns the work to the agent.

## Result

You now have one flow connected to current runtime evidence and a reviewed effect contract. Blackbox can return a deterministic verdict that agents can repair against but cannot redefine.
