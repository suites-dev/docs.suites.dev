Every Blackbox test run records evidence. Run first, inspect what happened, and only then approve which runtime actions become policy.

An **effect** is a meaningful action your application performs at a system boundary, such as reading a database row, calling another API, changing a cache, or publishing a message.

## 1. Run the Flow

```bash
pnpm run db:test:reset
pnpm exec blackbox test --flow subscribe-user
```

Blackbox performs one lifecycle:

```text
create cell -> start application -> run Playwright attempts -> settle capture
    -> seal evidence -> check effects -> analyze decisions -> report
```

The result keeps its claims separate. On this first run, no effect contract has been accepted yet, so Blackbox records effects without treating them as required or forbidden.

**Observable decision coverage (ODC)** compares the effects associated with different outcomes of a code decision. It reports whether those outcomes left meaningfully different evidence.

```text
FLOW subscribe-user
  tests       PASS  2 attempts
  integrity   PASS  capture complete
  effects     NOT CHECKED  no accepted contract
  ODC         REPORT  user-exists outcomes produced distinct evidence
```

## 2. Inspect the Sealed Run

Blackbox stores immutable inputs and derived analysis separately:

```text
.blackbox/evidence/<run-id>/
  manifest.json
  config.snapshot.json
  cells/
    <cell-id>/
      manifest.json
      events.jsonl
      attempts/
        <attempt-id>/events.jsonl
  artifacts/sha256/<digest>
  derived/
    effects/<attempt-id>.json
    decisions/<attempt-id>.json
    odc/verdict.json
  reports/summary.json
```

The manifest records flow, worker, retry, cell, service, producer capabilities, artifact hashes, isolation assurance, and integrity findings. The artifact store contains the exact executed JavaScript and source-map bytes used by offline analysis.

## 3. Read One Effect

An effect observation tells you what this execution did. A reviewed effect contract later tells Blackbox what the flow must or must not do.

The successful attempt can include this normalized observation:

```json
{
  "boundary": "postgres",
  "op": "INSERT",
  "key": "subscriptions",
  "service": "api"
}
```

This observation is a fact from one attempt. It is not automatically a requirement. Decide which observations express behavior you intend to protect.

## 4. Approve the Effect Contract

An **effect contract** lists runtime actions that must happen and actions that must not happen. For this flow, require the user lookup and forbid payment:

```yaml title="e2e/features/subscribe-user.effects.yaml"
specVersion: "0.1"
flow: subscribe-user

requires:
  - { boundary: postgres, op: SELECT, key: users, service: api }

forbids:
  - { boundary: http, op: POST, key: /v1/payment_intents, service: api }
```

Review this file as policy. The observed subscription insert remains evidence, but it is not required for every attempt. Do not copy every observation into the contract.

The inline `toObserveEffects()` form and this YAML use the same required-and-forbidden vocabulary. The Quickstart uses YAML because Blackbox snapshots reviewed policy into the sealed run and can reapply it offline. Keep one accepted contract for the flow instead of maintaining divergent inline and YAML rules.

## Result

You now have one immutable run, inspected effects, and a reviewed effect contract. The next step applies that contract to the sealed evidence and explains the ODC report without restarting the application.
