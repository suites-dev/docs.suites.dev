Feature files should be a reflection of reality, not a separate maintenance burden. Blackbox generates Gherkin `.feature` files from system and E2E tests, then checks whether those files drift from the test source.

Use this page when you already have a Playwright system test and want a **readable behavior layer** for review. The current alpha path is focused on Playwright-style tests and Blackbox BDD-DSL sources. You can use Blackbox without feature files, but generated Gherkin helps when product, QA, platform, or agent workflows need behavior expressed in a stable text format.

This is **code-first BDD**: the executable test remains the source of truth, and the `.feature` file follows it. The feature file is not runtime proof by itself. Runtime proof still comes from the system test, effect assertions, effect catalogs, and coverage reports.

## The Code-First BDD Loop

Blackbox keeps the loop small:

1. Start with a real system or E2E test, such as `subscribe-flow`.
2. Run `features emit` against the test source.
3. Review the generated Gherkin syntax.
4. Commit the `.feature` file only if it is part of your review surface.
5. Run `features check` in CI so feature-file drift cannot linger.

The important decision is where authorship lives. You do not hand-maintain the feature file as a parallel spec. You keep the test readable, generate the behavior file from it, then let drift checks tell you when the generated artifact no longer matches the test.

That means the generated file should read like behavior, not implementation trivia. If the output is too vague, improve the scenario names, action labels, or assertions in the source test, then run `features emit` again.

## Generate Your First Feature File

Run `features emit` against the showcase system tests:

```bash
pnpm exec blackbox features emit ./e2e/tests --out ./e2e/features
```

The command reads test files from `./e2e/tests` and writes generated `.feature` files under `./e2e/features`. For `subscribe-flow`, the generated artifact is the behavior file your reviewers can read without opening the Playwright source.

A small generated slice looks like this:

```gherkin
@flow:subscribe-flow
Feature: subscribing to the pro tier

  Scenario: alice is an existing user with no active subscription
    When alice POSTs /subscriptions with a valid card
    Then the response status is 201
```

Read this as a projection from the test source. It is useful because it puts behavior into a familiar shape, but it still depends on the test staying meaningful. If the source test only says "works", Blackbox cannot infer product intent that the test never expressed.

Review the generated file before committing it. Keep it when the `.feature` file will help humans or automation discuss behavior. Leave it uncommitted when the team only needs local inspection.

## Check for Feature File Drift

Run `features check` after generation:

```bash
pnpm exec blackbox features check --features ./e2e/features --tests ./e2e/tests
```

`features check` is read-only. It validates the generated Gherkin syntax and compares the feature files against the test source. If `subscribe-flow` changes in `./e2e/tests` but `./e2e/features/subscribe-flow.feature` is stale, the command reports feature-file drift.

A failing drift check looks like this:

```diff
$ pnpm exec blackbox features check --features ./e2e/features --tests ./e2e/tests
checking 1 feature file against 1 source test...

DRIFT  e2e/features/subscribe-flow.feature
  test source:    e2e/tests/subscribe-flow.spec.ts
  scenario:       alice is an existing user with no active subscription

- Then the response status is 201
+ Then the response status is 201
+ And the subscription tier is cached for alice

1 feature file drifted from its test source.
exit 1
```

Treat that diff as a normal review surface. Either the source test changed and the generated feature is stale, or the feature file was hand-edited and no longer matches the test. Regenerate with `features emit` to bring them back in sync.

Use JSON output when CI, scripts, or agents need structured results:

```bash
pnpm exec blackbox features check --features ./e2e/features --tests ./e2e/tests --json
```

For a dedicated drift gate, run:

```bash
pnpm exec blackbox features drift --tests ./e2e/tests --features ./e2e/features
```

Drift findings are practical review signals:

| Finding | Meaning |
| --- | --- |
| `missing` | A test source exists but the matching `.feature` file does not. |
| `stale` | A `.feature` file no longer matches the current test source. |
| `orphan` | A `.feature` file exists without a matching test source. |
| `unparseable` | Blackbox cannot parse the feature file or source input well enough to compare it. |

Treat drift as a documentation failure, not a test failure. The test may still pass, but the readable behavior layer is no longer synchronized with the executable behavior.

## When to Use Feature Files

Use generated feature files when they create a real review surface:

- You want reviewers to read `subscribe-flow` and `subscribe-unknown-user` in behavior terms.
- You want a Gherkin syntax artifact for product, QA, platform, or agent handoff.
- You want CI to catch feature-file drift before stale behavior text reaches a pull request.
- You want a concise behavior index next to effect catalogs and coverage artifacts.

Skip feature files when nobody will read or gate them. A generated artifact that no one reviews becomes noise, even if it is technically accurate.

Also skip them when you need runtime proof. Feature files describe behavior from the test source. They do not prove that alice caused Postgres, Redis, SQS, or Stripe effects during a run. Use effect assertions and coverage reports for that proof.
