Use this path when reviewed intent should guide implementation. You will take two requirements through one Gherkin feature, one native Playwright flow, one effect contract, and one runtime verdict.

<VerificationTriangleDiagram />

This is not a requirement-to-code generator. Skills perform inferential translation. The CLI performs computational validation and evidence capture. Humans approve the artifacts that define accepted behavior.

## Before You Start

Complete [Install Blackbox](/docs/blackbox/quickstart/install), then run:

```bash
pnpm exec blackbox init
pnpm exec blackbox doctor
```

The exact `init` flow is intentionally deferred for this docs wave. `doctor` is the first fully documented readiness contract.

This quickstart uses `subscribe-unknown-user` throughout. Keep that flow ID in the feature file, Playwright `test.describe` tag, effect contract, and reports.

## 1. Propose EARS Requirements

Start from a product specification, ticket, Kiro document, OpenSpec artifact, Spec Kit spec, or design note. Ask `$blackbox-requirements` to propose only the obligations this flow will verify.

```text
$blackbox-requirements

Input:
- docs/subscriptions.md
- target flow: subscribe-unknown-user

Task:
Propose atomic EARS requirements. Do not edit the repository directly.
```

The Skill returns an exact patch for `requirements/subscriptions.ears`:

```text
REQ-004: When an unknown user requests a subscription, the billing system shall reject the subscription.
REQ-005: When an unknown user requests a subscription, the billing system shall not request payment.
```

Validate the proposed file:

```bash
pnpm exec blackbox requirements validate 'requirements/**/*.ears' --json
```

A clean validation result establishes structure, not truth. A human still reviews and approves the requirement meaning.

## 2. Propose Gherkin

After the requirements are approved, ask `$blackbox-gherkin` to propose the readable behavior.

```text
$blackbox-gherkin

Input:
- requirements/subscriptions.ears
- flow: subscribe-unknown-user

Task:
Propose a feature file. Use feature-level @flow and @requirement tags.
Do not edit accepted requirements or suite files.
```

The proposed file is `features/subscribe-unknown-user.feature`:

```gherkin
@flow:subscribe-unknown-user
@requirement:REQ-004
@requirement:REQ-005
Feature: Reject an unknown subscriber

  Scenario: request stops before payment
    When the unknown user posts a subscription request
    Then the response status is 404
    And no payment request is sent
```

Validate the feature:

```bash
pnpm exec blackbox features check --features ./features --json
```

The human reviews and accepts the scenario wording before the suite is changed.

<Aside type="note" title="Do Not Hide Product Decisions in Gherkin">
  If the scenario chooses `404` instead of `401` or `403`, treat that as an
  explicit behavior proposal. Review it before implementation work continues.
</Aside>

## 3. Propose the Playwright Flow

Ask `$blackbox-playwright` to propose a native Playwright patch. The suite uses standard Playwright APIs. Blackbox reads the `@flow` tag.

```ts
import { expect, test } from "./blackbox-testbed";

test.describe(
  "Reject an unknown subscriber",
  { tag: "@flow:subscribe-unknown-user" },
  () => {
    test("request stops before payment", async ({ request, capture }) => {
      await test.step("submit the subscription request", async () => {
        const response = await request.post("/subscriptions", {
          data: { userId: "ghost-user", tier: "pro" },
        });

        expect(response.status()).toBe(404);
      });

      await test.step("verify the response and captured effects", async () => {
        await expect(capture).toMatchCatalog();
      });
    });
  },
);
```

The human approves the exact suite patch before it is applied. The agent must not write directly to the accepted suite without that approval.

## 4. Run and Capture Evidence

After implementation exists, run the selected flow:

```bash
pnpm exec blackbox verify --flow subscribe-unknown-user --json
```

The first run may fail because no effect contract exists yet or because the implementation is incomplete. That is expected. The runtime evidence gives the next harness step a fact base.

## 5. Propose the Effect Contract

Ask `$blackbox-effects` to read the evidence and propose required and forbidden effects. This is the only Blackbox-owned public YAML artifact.

```yaml
specVersion: "0.1"
flow: subscribe-unknown-user
requires:
  - { boundary: postgres, op: SELECT, key: users, service: bff }
forbids:
  - { boundary: http, op: POST, key: /v1/payment_intents, service: bff }
  - { boundary: postgres, op: INSERT, key: subscriptions, service: bff }
  - { boundary: sqs, op: SendMessage, key: subscription-orders }
```

Save the accepted contract as `features/subscribe-unknown-user.effects.yaml` after review. The CLI validates that the feature basename, YAML flow, and Gherkin `@flow` agree.

<Aside type="warning" title="The First Capture Can Preserve a Defect">
  Review the effect contract independently of the implementation author. If a
  payment call appeared during rejection, do not accept it merely because
  Blackbox recorded it.
</Aside>

## 6. Compute the Verdict

Run the flow again after the effect contract is accepted:

```bash
pnpm exec blackbox verify --flow subscribe-unknown-user --json
```

The CLI returns separate layer verdicts. A useful result distinguishes:

- Playwright assertion pass or failure;
- feature validity and flow-tag consistency;
- effect contract satisfaction or violation;
- requirement verdicts for `REQ-004` and `REQ-005`;
- observable decision evidence when enough branch-arm evidence exists.

## 7. Repair and Rerun

A coding agent can repair product implementation against the accepted artifacts:

```text
read findings -> change implementation -> run verify -> repeat
```

The agent stops when it would need to change an approved requirement, accepted scenario, approved suite flow, or accepted effect contract. A human verifies the final evidence and result.

## Summary

- **Skills infer** requirements, Gherkin, Playwright patches, and effect contracts.
- **The CLI computes** validation, evidence, coverage, and verdicts.
- **Humans approve** the artifacts that define accepted behavior.
- **Agents repair implementation** without silently changing the harness.
