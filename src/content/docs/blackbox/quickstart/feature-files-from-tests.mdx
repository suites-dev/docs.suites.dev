Prerequisite: have an executable Playwright flow. EARS requirement coverage also requires that flow to produce catalog coverage; Gherkin emission does not.

If you have not captured effects yet, complete the [5-Minute Quickstart](/docs/blackbox/quickstart/first-proven-feature) before taking the EARS path. Specifications add context around the core proof, but both specification paths remain optional and can be adopted separately.

| Path                               | Use it to answer                                                      |
| ---------------------------------- | --------------------------------------------------------------------- |
| EARS requirements and bindings     | Which normative requirement does this runtime flow prove?             |
| Generated Gherkin and drift checks | How can a reviewer read the behavior encoded by this executable test? |

## Path A: Bind an EARS Requirement

EARS gives requirements a constrained, identifiable form. A source file can express both positive and negative behavior:

```text
REQ-001: When a known user subscription is accepted, the bff shall persist an active subscription record.
REQ-004: When an unknown user subscribes, the bff shall not request payment, persist a subscription record, or publish a subscription order.
```

Create a requirement binding beside the test's effect catalog:

```yaml
specVersion: "0.1"
entries:
  subscribe-flow:
    requirements: [REQ-001]
  subscribe-unknown-user:
    requirements: [REQ-004]
```

The binding is human-ratified repository intent. Blackbox does not infer that `REQ-004` belongs to `subscribe-unknown-user`; a person or agent proposes the mapping and review accepts it.

Validate the requirement syntax, IDs, sidecar shape, and references:

```bash
pnpm exec blackbox requirements check --tests e2e
```

With the canonical example, a successful check reports:

```text
4 requirement(s) across 1 source file(s), 2 binding(s) in 1 sidecar(s), 0 finding(s)
```

Then join the bindings with the catalog coverage produced by the Playwright run:

```bash
pnpm exec blackbox requirements coverage \
  --tests e2e \
  --coverage e2e/.blackbox-coverage/catalog/coverage.json \
  --fail-on violated
```

The command writes `e2e/.blackbox-coverage/requirements/coverage.json`. Each requirement receives one verdict:

- `proven`: every bound flow has satisfied runtime evidence;
- `violated`: at least one bound flow failed its effect contract;
- `unproven`: a binding exists, but the current coverage does not prove it;
- `unbound`: the requirement has no flow binding.

Use `--fail-on unproven` or `--fail-on unbound` only when the suite and binding set are mature enough for stricter gating.

<Aside type="warning" title="Current Drift Scope Matters">
  `requirements drift` reports effect-catalog flows that have no requirement
  binding. In a repository that mixes product flows with infrastructure or
  OMC/DC fixtures, point `--tests` at the intended scope or expect those extra
  flows to appear as findings.
</Aside>

## Path B: Emit Gherkin From the Test

Blackbox can decompile Playwright or Blackbox BDD-DSL test sources into Gherkin. This is a code-first path: the executable test is the source, and the feature file is a readable projection.

<CodeFirstBddDiagram kind="triangle" />

Generate the feature file:

```bash
pnpm exec blackbox features emit ./e2e/tests --out ./e2e/features
```

A generated file follows normal Gherkin structure:

```gherkin
@flow:subscribe-flow
Feature: subscribing a user to the pro tier

  Scenario: alice subscribes with a valid card
    When alice POSTs /subscriptions with a fresh card
    Then the HTTP response describes a created pro-tier subscription
    And the subscription is persisted in postgres
```

Review the language. If the result exposes vague test names, improve the executable source and emit again. Do not hand-edit the generated file as a second, independent implementation of the scenario.

<BddReverseDemo />

Check syntax and source-to-feature drift:

```bash
pnpm exec blackbox features check \
  --features ./e2e/features \
  --tests ./e2e/tests
```

Use `--json` when CI or an agent needs the stable command envelope. A drift finding means the readable projection is missing, stale, orphaned, or unparseable; it does not replace the Playwright result or the runtime effect verdict.

<Aside type="note" title="Spec-First Scaffolding Is Experimental">
  The `features experimental scaffold` and `features experimental wrap` commands
  explore feature-to-test workflows. Their command names, output, and semantics
  may change. The stable documented path is test-to-feature emission and drift
  checking.
</Aside>

## Use Both Without Conflating Them

The complete chain can be:

```text
EARS requirement
  -> reviewed flow binding
  -> Playwright system test
  -> runtime effects and catalog verdict
  -> requirement coverage
  -> optional generated Gherkin
```

EARS remains normative intent. Gherkin remains a readable behavioral example. The Playwright test remains executable. Runtime evidence remains the observed fact base.
