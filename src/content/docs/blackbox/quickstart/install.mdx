Installation is the first step toward visibility. A **project-local install** adds Blackbox to the workspace package that owns your system tests, not to a global toolchain or production dependency set.

Blackbox has two install surfaces:

1. `@suites/blackbox` plus a runtime adapter and test dependencies for Playwright system tests.
2. `@suites/blackbox-cli`, the package that provides the framework facade and specialized engine commands.

Your **system under test (SUT)** is the service or topology Blackbox observes during the run. Install the packages, then verify the binary before you run a proof flow.

<Aside type="info" title="Test-Time Instrumentation">
  Blackbox instruments compatible Node SUT containers during the test run. The
  compose testbed mounts the bootstrap, shadows the service's Node binary with
  `node-wrap`, and preloads `bootstrap.cjs` before application code. Service
  source and production Dockerfiles do not need OpenTelemetry imports.
</Aside>

## Project-Local Install

Install Blackbox in the same package where you run Playwright or your system-test command. This keeps `pnpm exec blackbox` on the same version your tests use.

### Core Runtime

For the documented Node testbed path, install the runtime, Node adapter, bootstrap payload, Playwright, and Testcontainers as development dependencies:

<Tabs groupId="pkg">
<TabItem value="pnpm" label="pnpm" default>

```bash
pnpm add -D @suites/blackbox @suites/blackbox-adapter-node @suites/blackbox-instr-node @playwright/test testcontainers
```

</TabItem>
<TabItem value="npm" label="npm">

```bash
npm install --save-dev @suites/blackbox @suites/blackbox-adapter-node @suites/blackbox-instr-node @playwright/test testcontainers
```

</TabItem>
<TabItem value="yarn" label="yarn">

```bash
yarn add --dev @suites/blackbox @suites/blackbox-adapter-node @suites/blackbox-instr-node @playwright/test testcontainers
```

</TabItem>
</Tabs>

`@suites/blackbox-adapter-node` registers Node observation and observable decision producers. `@suites/blackbox-instr-node` supplies the bootstrap payload used by the test image. Add database, cache, queue, or LocalStack Testcontainers packages only when the test fixture imports them directly.

You usually do not need to add OpenTelemetry packages manually for the default testbed path. The package surface is alpha, so pin it through the lockfile and update intentionally.

### CLI Tooling

Add the CLI package when you want the `blackbox` command:

<Tabs groupId="pkg">
<TabItem value="pnpm" label="pnpm" default>

```bash
pnpm add -D @suites/blackbox-cli
```

</TabItem>
<TabItem value="npm" label="npm">

```bash
npm install --save-dev @suites/blackbox-cli
```

</TabItem>
<TabItem value="yarn" label="yarn">

```bash
yarn add --dev @suites/blackbox-cli
```

</TabItem>
</Tabs>

`@suites/blackbox-cli` provides `init`, `doctor`, `status`, `verify`, `explain`, flow inspection, and the `requirements`, `features`, `coverage`, and `otel` command families. The requirements engine is included. Keep the CLI version aligned with `@suites/blackbox` so the facade, runtime, and artifact formats agree.

## Verification

### Checking the Binary

Run the binary from the package that owns the install:

```bash
pnpm exec blackbox --help
pnpm exec blackbox verify --help
```

A successful run prints framework commands and engine topics:

```text
Suites Blackbox verifies reviewed behavior against executable flows and runtime evidence.

USAGE
  $ blackbox [COMMAND]

COMMANDS
  doctor    Check whether configured verification layers can run.
  explain   Explain a Blackbox diagnostic code.
  init      Configure Blackbox for this project.
  status    Read repository and retained-run verification state.
  verify    Run the configured verification loop.

TOPICS
  coverage      Observable decision coverage analysis and reports.
  features      Derive, lint, drift-check, and reshape feature traces.
  flows         Inspect flow IDs and their connected artifacts.
  otel          Static OpenTelemetry source instrumentation.
  requirements  Extract, validate, connect, and verify requirements.
```

This confirms that the CLI is installed in the right workspace package. It does not prove that the SUT is observable.

If `pnpm exec` cannot find `blackbox`, check the current directory first. In a multi-package workspace, installing the CLI at the root does not always make it available inside the package that runs your system tests.

### Initialize and Validate the Environment

Begin onboarding, then check the selected environment:

```bash
pnpm exec blackbox init
pnpm exec blackbox doctor
```

The exact `init` flow is intentionally not documented in this wave. `doctor` is the first fully documented readiness contract. It checks the test runner, Docker, instrumentation, discovered artifacts, and artifact paths without running the SUT.

Before the first proof run, confirm that the install can reach the required tools:

1. `node --version` satisfies your project requirements.
2. Docker is running and can build or pull images.
3. Playwright can run at least one system test against the SUT.
4. The SUT starts through a Node command that the testbed can wrap.
5. The repo has a writable artifact directory, usually `.blackbox-coverage/`.

Playwright still executes the tests. `blackbox verify` invokes the configured Playwright project and then coordinates feature, effect, requirement, and decision verdicts around that run.

## The Bootstrap Image

The **bootstrap image** carries the OpenTelemetry preload code and wrapper files that Blackbox mounts into Node service containers. It lets the testbed inject observability without changing the service Dockerfile.

If your repo exposes a local build script for the image, run it before the first testbed proof:

```bash
pnpm build:instr-image
```

Local development commonly uses `blackbox-instr-node:local`. CI can pull a published image instead, or set `BLACKBOX_INSTR_IMAGE` to the image your pipeline should use.

Treat this image as test infrastructure. Rebuild or repull it when you upgrade Blackbox packages, when bootstrap files are missing, or when no spans arrive even though the SUT started.

## Troubleshooting the Install

If the CLI is missing, install `@suites/blackbox-cli` where you run `pnpm exec blackbox`, then reinstall dependencies from the lockfile.

If command topics look different from the docs, align `@suites/blackbox` and `@suites/blackbox-cli` to the same release range:

```bash
pnpm up @suites/blackbox @suites/blackbox-cli --latest
```

If the test starts but no runtime evidence appears, the install is not the likely failure point. Check the bootstrap image, the SUT startup command, and whether spans can reach Blackbox during the test.

If you need to remove Blackbox, remove the runtime, adapter, instrumentation payload, and CLI packages from the system-test package:

```bash
pnpm remove @suites/blackbox @suites/blackbox-adapter-node @suites/blackbox-instr-node @suites/blackbox-cli
```

Then review project scripts, generated feature files, and `.blackbox-coverage/` artifacts separately. Package removal should not delete evidence that may still help debugging.
